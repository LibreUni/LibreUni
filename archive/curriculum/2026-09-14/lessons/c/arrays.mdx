# Arrays, Extents, and Contiguous Representation

An array is an object containing a fixed number of adjacent elements of one type. The important contract is not “arrays are fast”; it is that the object has an extent and that each element has a well-defined position relative to the first. A caller that loses the extent can still hold an address, but it no longer has enough information to prove an access is valid.

## Element addresses and pointer arithmetic

For an array `T a[n]`, the expression `a[i]` is defined in terms of pointer arithmetic: `*(a + i)`. The address calculation is scaled by `sizeof(T)`, so `a + 1` advances one element, not one byte. Pointer arithmetic is defined within the same array object (or one position past its end); dereferencing that one-past pointer is invalid.

For `int values[4]` starting at address `1000`, with `sizeof(int) == 4`, `&values[2]` is `1008`. This arithmetic is a model of an object, not permission to manufacture arbitrary addresses and dereference them. A pointer one past `values[3]` may be compared or used as a loop sentinel, but not read.

## Extents are part of the interface

The following interface is incomplete:

```c
int sum(const int *values) {
    /* No portable way to know how many int objects are available. */
}
```

Use an explicit count, a sentinel with a documented invariant, or a view type that couples pointer and extent:

```c
struct int_view {
    const int *data;
    size_t length;
};

int sum_view(struct int_view view) {
    int total = 0;
    for (size_t i = 0; i < view.length; ++i) total += view.data[i];
    return total;
}
```

The view does not make a dangling pointer safe. Its caller still owns the proof that `data` points to at least `length` readable `int` objects for the duration of the call. If the function stores the view, the lifetime obligation must extend beyond the call.

## Multidimensional arrays

An object declared `int matrix[2][3]` contains two adjacent arrays, each containing three `int` objects. In row-major layout, the element at row `r` and column `c` has linear offset `r * 3 + c`. The second dimension is required when a pointer walks rows:

```c
void clear_rows(size_t rows, size_t columns, int matrix[rows][columns]) {
    for (size_t r = 0; r < rows; ++r)
        for (size_t c = 0; c < columns; ++c)
            matrix[r][c] = 0;
}
```

The parameter is still adjusted to a pointer, but its pointed-to type is “array of `columns` int”. If the stride is wrong, accesses can land in a different row even when every index appears small. A dynamically allocated `int **` is not automatically interchangeable with a contiguous `int [rows][columns]`; it may describe separately allocated rows.

## Counterexamples and boundary cases

- `sizeof values` yields the whole array size only while `values` is an array expression that has not decayed; in a function parameter, it yields pointer size.
- `values[8]` for an eight-element array is undefined behavior even if the adjacent bytes look readable in one build.
- `memcpy` can copy an array's representation, but it does not establish a valid object lifetime for every possible destination type.
- A variable-length array's bound is evaluated at run time, but it still has no automatic bounds checking.

### Diagnostic solutions

1. `samples[4]` is at `2032`; the one-past pointer is at `2040`. The latter may be formed but not dereferenced.
2. A pointer carries an address and type, not the number of elements in the original object. The count must be passed or encoded by a sentinel/view contract.
3. Pass `data`, `rows`, and `columns`; first check that multiplication fits the chosen size type and that the caller owns at least that many elements. Use checked arithmetic when dimensions are external input.
4. A contiguous matrix has one allocation with a fixed row stride. An `int **` points to pointer objects, each of which may point to a separate row; the pointer array and row allocations are additional objects.
