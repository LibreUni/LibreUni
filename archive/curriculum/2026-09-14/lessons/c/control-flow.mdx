# Control Flow and Branch Semantics

Control flow is a semantic choice: for each reachable state, which statement executes next? Performance is a later, measured question. A compiler may transform an `if`, use a jump table for a `switch`, or remove a branch entirely if its conditions are provably constant.

## Selection and the dangling `else`

An `else` binds to the nearest unmatched `if`. Braces make the intended structure visible and prevent a later insertion from changing control flow:

```c
if (authenticated) {
    if (authorized) {
        grant_access();
    }
} else {
    deny_access();
}
```

Do not use indentation as evidence. Construct a decision table for boundary inputs such as an empty string, a negative count, or an authorization failure.

## `switch` and deliberate fall-through

`switch` selects among integral or enumeration values. A `case` label does not create an implicit block and execution continues into later cases until a `break`, `return`, or other transfer occurs. Deliberate fall-through should be adjacent, documented, and tested:

```c
switch (command) {
case 'q':
case 'Q':
    quit = 1;
    break;
case 'h':
    help();
    break;
default:
    report_unknown(command);
    break;
}
```

Compilers may implement dense cases with a jump table or sparse cases with comparisons. Neither choice is a portable O(1) guarantee; the number of cases, value distribution, target, and optimization settings matter.

## Branch behavior is not a language guarantee

Modern processors predict control flow, but a C author should first establish defined behavior and a correct invariant. A data-dependent branch can have timing implications, and a compiler can lower equivalent source forms differently. Measure with a controlled workload before making a performance claim, and do not use branch “hints” as a substitute for a clear contract.

### Diagnostic solutions

1. The cases are negative, zero, and positive; zero belongs only to the equality case. Test the boundaries `-1`, `0`, and `1`.
2. Start at the matching label and continue line by line until a transfer; labels do not stop execution. A table of state after each statement catches accidental fall-through.
3. For example, reject unauthenticated input first, then reject unauthorized input, then grant access. Each return removes one nesting level while preserving the mutually exclusive conditions.
4. A sparse or large label range can make a table too large; code size, profile data, target architecture, and optimization policy all influence the lowering.
