# Error Contracts and Cleanup in C

C makes failure part of the ordinary control-flow contract. A function must tell its caller which results are valid, how failure is represented, and which resources remain owned after a failure. The caller cannot infer this safely from a return type alone.

## Result conventions

Common conventions include a status return with an output parameter, a pointer result where `NULL` signals failure, or a value plus an out-of-band status such as `errno`. None is universally best. Document whether a function may partially modify an output object, whether failure preserves the old value, and who releases resources created before the error.

`errno` is thread-local in hosted implementations that provide it, but it is meaningful only after a library or system call documents that it sets it on failure. Save it immediately if cleanup calls might overwrite it:

```c
int saved_errno = errno;
close(fd);
errno = saved_errno;
```

Do not inspect `errno` after a successful call as if it described that call. It may contain an older error.

## One cleanup path, explicit ownership

For functions acquiring several resources, a forward-only sequence of returns often leaks. A cleanup label is not inherently bad; an unstructured cleanup graph is. Make the acquisition order and guards visible:

```c
int load_config(const char *path, struct config **out) {
    int result = -1;
    FILE *file = NULL;
    char *buffer = NULL;
    struct config *config = NULL;

    file = fopen(path, "rb");
    if (file == NULL) goto cleanup;
    buffer = malloc(4096);
    if (buffer == NULL) goto cleanup;
    config = parse_config(file, buffer);
    if (config == NULL) goto cleanup;
    *out = config;
    config = NULL;             /* ownership transferred */
    result = 0;

cleanup:
    free(config);
    free(buffer);
    if (file != NULL) fclose(file);
    return result;
}
```

The example needs a real parser contract and a size-aware buffer in production; its point is the ownership proof. Every acquired resource appears exactly once in cleanup, and transfer is represented by setting the local owner to null.

## Validation, assertions, and sanitizers

Validate external input and recoverable environmental failures. Use `assert` for programmer assumptions that should terminate a debug build, not for user input or routine I/O failure. Sanitizers and static analyzers find classes of memory errors; they do not prove that a protocol's error policy is complete.

`setjmp`/`longjmp` can bypass normal block exits and therefore skip cleanup, invalidate assumptions about automatic objects, and obscure ownership. Use it only with a deliberately documented control-flow boundary, not as a drop-in exception mechanism.

### Diagnostic solutions

1. Return a status and write the pointer through an output parameter, or return a tagged structure containing `found` and `value`. A bare `NULL` would be ambiguous.
2. Each failure after acquisition must release every resource acquired before that edge; the success edge transfers or releases all resources. A reverse-order cleanup label makes the graph auditable.
3. A packet is external input and malformed data is an expected environmental condition. Reject it and report a protocol error; do not terminate the process as if an internal invariant failed.
4. ASan can catch many out-of-bounds and use-after-free accesses at runtime. It cannot prove that every legal state transition is handled or that a user is authorized.
