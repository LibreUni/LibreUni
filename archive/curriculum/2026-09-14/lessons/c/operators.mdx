# Operators, Evaluation, and Defined Behavior

An operator describes a computation, but punctuation alone does not tell you when every operand is evaluated. Three ideas must stay separate: precedence groups syntax, associativity resolves some equal-precedence syntax, and the language's sequencing rules determine when side effects become observable.

## Arithmetic and conversions

Integer division truncates toward zero: `-5 / 2` is `-2`, and the remainder satisfies `(a / b) * b + a % b == a` when the quotient is representable and `b` is nonzero. Division by zero is undefined. Before arithmetic, the usual conversions may change a small integer to `int` or convert an operand to an unsigned type; audit the types rather than relying on visual literals.

Bitwise operators operate on integer representations. Use masks to set, clear, or test flags, but choose an unsigned type for portable shifts and make the width explicit:

```c
uint8_t flags = 0;
flags |= (uint8_t)1u << 3;  /* set bit 3 */
flags &= (uint8_t)~(1u << 3); /* clear bit 3 */
```

Signed right shift and shifts by a negative or too-large count have portability or undefined-behavior concerns. A left shift is not a universal “multiply by two” when signed overflow is possible.

## Short-circuit logic

`&&` and `||` evaluate left to right and may skip the right operand. This is useful for guards:

```c
if (node != NULL && node->value == wanted) { ... }
```

The guard is a semantic dependency, not a style trick. Replacing `&&` with bitwise `&` evaluates both operands and can dereference a null pointer. The conditional operator `condition ? yes : no` evaluates only the selected arm, while the comma operator sequences its left operand before its right operand; use the latter sparingly because hidden side effects reduce auditability.

## Sequencing and side effects

An expression such as `i = i++ + 1` modifies `i` more than once without a permitted sequencing relationship and has undefined behavior. Parenthesizing it does not repair the problem. Split the operations into statements with a clear order:

```c
int old = i;
++i;
i = old + 1;
```

The safe rewrite must still match the intended result; “make it compile” is not the same as preserving behavior.

## Transfer exercises

1. Explain why `ptr && ptr->value` is a valid guard but `ptr & ptr->value` is not.
2. Compute `-5 / 2` and `-5 % 2`, then verify the identity.
3. Classify `f(i++, i++)` without assuming a particular compiler.
4. Rewrite a flag update so it changes only bit 2 and preserves all other bits.

### Diagnostic solutions

1. Logical AND may skip the second operand after a false pointer test; bitwise AND evaluates both integer operands and does not provide a null guard.
2. The results are `-2` and `-1`; `(-2)*2 + (-1) == -5`.
3. The argument evaluation order is not a portable left-to-right contract, and modifying the same scalar in both arguments creates undefined behavior.
4. Set with `flags |= (1u << 2)` or clear with `flags &= ~(1u << 2)` after choosing an unsigned type of known width.
