# Scope, Storage Duration, Linkage, and Qualifiers

Four questions are often conflated: where can a name be used (scope), how long does an object exist (storage duration), which declarations denote the same entity across translation units (linkage), and may an access expression modify or omit an object access (qualifiers)? The keywords become predictable when these dimensions are separated.

## Scope, duration, and linkage

An automatic local object exists while execution is inside its block. A static local object has block scope but static storage duration and retains its value between calls. A file-scope `static` name has internal linkage; a non-static file-scope definition may have external linkage and be declared with `extern` elsewhere.

```c
/* counter.c */
static int internal_count;
int public_count;

/* other.c */
extern int public_count; /* same external object */
```

`extern` is a declaration, not an allocation instruction. Define external objects once and prefer functions or opaque modules over shared mutable globals when ownership matters.

## `const` is a view, not ownership

`const int *p` prevents modification of the int through p; `int *const p` prevents changing p; `const int *const p` does both. `const` does not prove the underlying object was originally declared const, does not make an object thread-safe, and does not specify lifetime.

## `volatile` and observable accesses

`volatile` tells the implementation that accesses to the qualified object are observable and must not be optimized away or merged as ordinary accesses. It is appropriate for memory-mapped registers or an object changed by an interrupt mechanism defined by the platform. It is not a mutual-exclusion primitive, atomicity guarantee, memory-ordering protocol, or replacement for a lock.

```c
volatile unsigned status;
while ((status & READY) == 0u) { /* poll a device register */ }
```

For threads, use the C atomic types and a synchronization design. For hardware, use the vendor's register width, ordering, and acknowledgement rules; a volatile qualifier alone does not make a device protocol correct.

## Transfer exercises

1. Classify a function-local static's scope and storage duration.
2. Explain why `volatile int ready` does not make `ready++` atomic between threads.
3. Design a header declaration for a file-private helper and a public API function.
4. Identify which qualifier is needed for a function that reads but does not modify a caller-owned buffer.

### Diagnostic solutions

1. Block scope; static storage duration. The object persists for the program's execution but the name is visible only in the block.
2. The increment is a read-modify-write sequence and can interleave. Volatile affects optimization/observable access, not atomicity or inter-thread ordering.
3. Put only the public function declaration in the header; define the helper with `static` in the implementation file. This prevents external linkage to the helper.
4. Use a parameter such as `const unsigned char *data` plus an extent. Document the borrow lifetime.
