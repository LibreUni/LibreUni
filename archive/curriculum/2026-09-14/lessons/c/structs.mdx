# Structures, Unions, and Representation Invariants

A `struct` groups member objects with a defined order; it does not promise that the bytes are packed with no gaps. A good structure lesson begins with the logical invariant—what values are meaningful together—and treats layout as a separate implementation/ABI question.

## Structs and invariants

```c
struct interval {
    int start;
    int end;
};
```

If the intended invariant is `start <= end`, the type declaration does not enforce it. Constructors, validators, or carefully documented update functions must establish it. A public struct with freely writable fields exposes the invariant to every caller; an opaque pointer can centralize validation.

## Alignment and padding

An implementation may insert padding between members or at the end so each object in an array meets alignment requirements. For example, a `char` followed by an `int` often has a gap, but the exact size is implementation-defined. Reordering fields can reduce size, yet that is an ABI and measurement decision, not a semantic rule. Use `sizeof`, `_Alignof`, and static assertions for a target-specific layout contract.

## Unions need a tag

A union gives several members the same storage. The program must track which variant is active:

```c
enum value_kind { VALUE_INT, VALUE_TEXT };
struct value {
    enum value_kind kind;
    union {
        int number;
        const char *text;
    } data;
};
```

Read `data.number` only when `kind == VALUE_INT`, and define who owns `data.text`. Reading an inactive member to reinterpret representation is a specialized, implementation-sensitive technique; it is not a general serialization method.

## Bit-fields and enums

Bit-field allocation order, alignment, and addressability are implementation-defined; use them for a documented target ABI, not as a portable wire format. An enum provides named integer constants and improves intent, but its underlying representation and range should not be assumed for storage protocols without a specified format.

### Diagnostic solutions

1. For example, denominator is nonzero and the sign is normalized. Construction and arithmetic must reject or normalize zero denominators.
2. Padding may be inserted for member alignment and array-stride requirements; the standard does not require a packed sum.
3. Cleanup checks the tag: free the string only for the owned-string variant, and do nothing for the integer variant. A borrow/ownership flag may be needed too.
4. Usually no: bit-field order and padding are implementation-defined. Serialize fields explicitly with chosen widths and byte order.
