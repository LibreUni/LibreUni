# C at the System Boundary

Portable C stops at several boundaries. The language defines object and function semantics; a hosted implementation supplies a library; an operating system defines system calls; a target ABI defines calling convention and binary layout; a device manual defines MMIO behavior. A correct systems lesson keeps those contracts separate.

## Library, system call, and kernel

`printf` is a C library interface that may format and buffer before invoking platform services. A POSIX `write` is an operating-system interface, not a C language primitive. The actual transition instruction, argument registers, privilege level, and error convention belong to the target ABI and OS. Treat a code sample using them as conditional on those documents.

## ABI obligations

An ABI may specify which registers carry arguments, who preserves which registers, stack alignment, return-value representation, symbol naming, and struct layout. C source that calls a function through a mismatched declaration can violate the ABI even when the types “look close”. Use headers supplied by the platform and compile with compatible options.

## MMIO and `volatile`

A hardware register may be exposed at an address, but the address, width, access mode, required ordering, and acknowledgement sequence come from the device manual. `volatile` prevents the compiler from treating an access as an ordinary discardable load/store; it does not supply atomicity, memory barriers, or a correct device protocol.

```c
volatile uint32_t *status = (volatile uint32_t *)DEVICE_STATUS_ADDRESS;
while ((*status & READY_BIT) == 0u) { }
```

The example is not portable C: the address and bit definitions are target facts. It also needs a timeout or failure policy in a real driver.

## Interrupts and callbacks

An interrupt handler runs under platform-specific constraints. Keep it bounded, acknowledge the device correctly, and communicate with normal code using the platform's atomic or synchronization primitives. Calling arbitrary application callbacks from interrupt context can block, allocate, or re-enter non-reentrant code; recording an event for later dispatch is often safer.

## Transfer exercises

1. Classify a `fopen` call, an x86 `syscall` instruction, and a memory-mapped register as language/library/OS/device contracts.
2. Explain why `inline` is not a portable promise that a function call disappears.
3. List the missing facts needed before using an MMIO address from a datasheet.
4. Design an ISR-to-main-loop handoff and state the shared-state ordering rule.

### Diagnostic solutions

1. `fopen` is a library interface; `syscall` is target ABI/OS machinery; the register address and protocol are device/target facts.
2. `inline` permits an implementation to inline or not; observable semantics and ABI remain the contract. Measure performance under the target build.
3. Address, width, read/write side effects, reset state, bit meanings, ordering, acknowledgment, timeout, and concurrency/interrupt rules.
4. Write a bounded event into a ring or set an atomic flag in the ISR, then consume it in normal context under the platform's synchronization and memory-order rules.
