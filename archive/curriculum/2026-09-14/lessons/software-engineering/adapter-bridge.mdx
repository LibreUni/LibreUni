# Adapter and Bridge: Two Kinds of Decoupling

An Adapter makes an existing component look like the interface a client already expects. A Bridge is an architectural split chosen so an abstraction and its implementation can vary independently. Both use composition often; their forces and timing differ.

## Adapter translation

An adapter must preserve or deliberately map semantics, not only rename methods. It needs a policy for units, missing values, timeouts, retries, ownership, and errors:

```python
class WeatherPort:
    def temperature_celsius(self, city):
        raise NotImplementedError

class FahrenheitAdapter(WeatherPort):
    def __init__(self, legacy): self.legacy = legacy
    def temperature_celsius(self, city):
        fahrenheit = self.legacy.read_temp_f(city)
        return (fahrenheit - 32) * 5 / 9
```

## Bridge dimensions

Suppose a notification abstraction (`Reminder`, `Alert`) can use email, SMS, or push implementations. Inheriting every product/transport combination creates a Cartesian product. A bridge keeps the abstraction and implementation hierarchies separate, but the implementation port must still state guarantees common to every transport.

### Diagnostic solutions

1. Units/time zones, error categories, nullability, retry/idempotency, and ownership are common examples.
2. It separates variation axes but every implementation must satisfy the abstraction's behavior; otherwise clients cannot substitute transports.
3. An unsupported currency, lossy precision conversion, or security guarantee the legacy API cannot provide should be rejected or surfaced explicitly.
4. Document whether the adapter borrows or owns the wrapped client and when it closes it; never double-close an externally owned resource.
