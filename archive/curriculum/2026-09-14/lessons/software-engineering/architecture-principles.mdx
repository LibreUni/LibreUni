# Architecture as Quality-Attribute Decisions

Architecture is the set of structures and decisions that are hard or expensive to change. It is not a diagram style and not a synonym for “microservices.” A useful architecture connects a quality scenario to boundaries, mechanisms, risks, and evidence.

## Structure and quality scenarios

Start with a small set of scenarios: a tenant boundary must prevent data leakage; a provider outage must not block core writes; a release must be reversible; a team must change pricing without changing fulfillment. Identify the owner of each invariant and the mechanism that enforces it. If a boundary cannot say where failure appears, it is not yet a useful boundary.

## Tactics and trade-offs

Tactics are mechanisms applied to a scenario: timeouts and bulkheads for dependency failure, queues for decoupling, immutable events for audit, caching for bounded freshness, replication for availability, and schema validation for compatibility. Each tactic introduces a counter-cost. A timeout prevents indefinite waiting but creates an ambiguous outcome; a cache lowers latency but weakens freshness; a queue absorbs bursts but adds lag and duplicate-processing obligations.

## Decision records and diagrams

An architecture decision record should name context, decision, alternatives, consequences, assumptions, and evidence. A component diagram shows ownership and dependencies; a deployment diagram shows runtime placement; a sequence diagram shows behavior over time. Keep diagrams selective and label the failure or trust boundary that matters. A diagram that omits the database transaction or external provider can make an unsafe design look complete.

## Transfer exercises

1. Write an ADR for adding a read cache to a user profile service.
2. Identify a hidden cost of splitting a monolith at a team boundary.
3. Choose one tactic for a provider outage and state its failure mode.
4. Explain why a deployment diagram cannot establish an authorization property by itself.

### Diagnostic solutions

1. State the freshness bound, invalidation/source of truth, cache failure behavior, cost, and tests/metrics. Do not claim consistency stronger than the policy.
2. Distributed transactions, network failure, observability, version compatibility, and local development complexity can all increase.
3. A timeout plus circuit breaker bounds waiting but may reject work; an outbox preserves intent but can accumulate lag. State the recovery path.
4. Authorization depends on identity, policy evaluation, and enforcement at a request/data boundary; placement alone does not prove that a call is denied.
