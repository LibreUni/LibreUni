# Behavior-Driven Development and Shared Examples

BDD is a collaboration and specification practice organized around examples of system behavior. “Given/When/Then” is a readable shape, not a substitute for domain conversation. A scenario earns its place when it helps stakeholders and engineers agree on a decision and creates evidence that can fail.

## Three Amigos and vocabulary

Product/domain, development, and testing perspectives should challenge the scenario before automation. Ask what “owner,” “balance,” “available,” and “withdraw” mean, then choose examples that distinguish competing interpretations. A scenario should not encode every UI click when the behavior is a domain rule.

## Scenario quality

Keep a scenario independent, focused, and observable. Use a small example table when the rule has a partition:

| Plan | Cancellation time | Access result |
| --- | --- | --- |
| monthly | before renewal | ends at policy boundary |
| annual | after payment | refund/credit policy is explicit |
| any | repeated request | idempotent result |

Automation may call APIs, domain objects, or a UI; the scenario should remain understandable if the implementation changes. A failing step is a prompt to inspect contract and test fixture, not proof that the business rule is wrong.

## Transfer exercises

1. Write two examples that distinguish inclusive from exclusive due dates.
2. Explain why a scenario that asserts a CSS selector is brittle.
3. Add an alternate flow for a notification timeout.
4. Identify which examples should become unit, integration, and acceptance tests.

### Diagnostic solutions

1. Use a timestamp exactly at the boundary and one unit before/after, with a declared time zone and precision.
2. It couples the behavior specification to presentation structure; assert user-visible or API behavior unless the selector itself is a supported accessibility contract.
3. State whether the operation commits, queues, retries, or reports ambiguity, and how duplicate delivery is prevented.
4. Pure rule examples can be unit tests; persistence/transaction examples integration tests; end-to-end user goals acceptance tests. Keep the source scenario readable across layers.
