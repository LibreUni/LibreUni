# Builder and Prototype: Controlled Construction

Builders and prototypes address different construction pressures. A builder makes a multi-step configuration readable and validates before publication. A prototype creates a new object from an existing example, but must define which state is copied, which state is shared, and whether identity is renewed.

## Staged construction

```python
class Request:
    def __init__(self, url, timeout, headers):
        self.url, self.timeout, self.headers = url, timeout, headers

class RequestBuilder:
    def __init__(self, url):
        self.url = url
        self.timeout = 5
        self.headers = {}

    def timeout_seconds(self, value):
        if value <= 0: raise ValueError("timeout must be positive")
        self.timeout = value
        return self

    def build(self):
        return Request(self.url, self.timeout, dict(self.headers))
```

`build` copies the headers so later builder mutation does not change the product. The request's own contract should still validate the URL and any security policy.

## Prototype copying

A prototype is useful when an object is expensive or complex to configure and a new variant should inherit most state. Deep versus shallow copy is a semantic choice: shared caches may be intentional; mutable permissions or lists usually are not. Assign a new identity when the copy represents a new domain entity, and preserve identity only when the object is a value snapshot with that meaning.

### Diagnostic solutions

1. URL has an allowed scheme/host policy; timeout is positive and bounded; headers do not contain forbidden secrets/logging data.
2. Sharing an immutable formatting table can be safe; sharing a mutable permission list is unsafe unless shared mutation is part of the contract.
3. Later mutation could bypass validation or alter an in-flight request; immutable products make the validated state stable.
4. Clone, mutate the clone's recipient list, and assert the template list is unchanged; also assert identity and owner rules.
