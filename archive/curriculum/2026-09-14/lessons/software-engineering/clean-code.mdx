# Readable Code and Local Reasoning

“Clean” is not a universal visual style. Code is readable when a maintainer can recover the relevant contract, state, failure modes, and change boundary without simulating unrelated machinery. Names, functions, modules, comments, and formatting are means to that end.

## Names and functions

A useful name answers a question the reader would otherwise have to infer: `retry_deadline` communicates a time boundary; `x` does not when several time values exist. Functions should have one coherent reason to change, but “one thing” means one level of abstraction and one contract, not one line of code.

Prefer guard clauses when they make invalid states exit early, but do not flatten a state machine into a maze of returns. Keep side effects visible and make units explicit in names or types.

## Duplication, comments, and errors

Duplication is not identical text; it is duplicated knowledge that must change together. Two similar parsers for different protocols may intentionally diverge. Copying a business rule into two services creates a consistency risk even if the code looks different. Remove duplication when the same reason to change is genuinely shared, and preserve it when coupling would be worse.

Comments should explain why a non-obvious constraint exists, the source of a workaround, or the invariant a reader must preserve. A comment that says “increment i” adds no evidence and can become false. Error handling should preserve context, distinguish expected rejection from an invariant violation, and avoid logging secrets.

## Refactoring as a controlled change

Before changing structure, capture behavior with examples or characterization tests. Make one transformation, run the relevant checks, and inspect the diff. A formatter can reduce noise, but it cannot tell whether a state transition changed. A clean-looking rewrite without a behavior oracle is a risk transfer.

## Transfer exercises

1. Give a case where duplication is safer than a shared abstraction.
2. Rewrite a comment that restates code into a contract comment.
3. Identify a hidden side effect in a function named `calculate_total`.
4. Propose a test before extracting a payment helper.

### Diagnostic solutions

1. Two algorithms share a shape but differ in policy or are expected to evolve independently; forcing one abstraction couples unrelated change.
2. Explain an invariant, external constraint, or reason for a surprising workaround, and link to the evidence or issue that would invalidate it.
3. It may write a database row, emit an event, or mutate a global cache. Either rename it to expose the effect or separate calculation from effects.
4. Test the current observable total for normal, rounding, missing, and failure cases; then preserve those tests while extracting the helper.
