# Dependency Inversion and Stable Boundaries

The dependency-inversion principle has two parts: high-level policy should not depend directly on low-level details, and both should depend on abstractions; abstractions should belong to the policy's language rather than being a thin copy of a vendor API. The goal is control of change and testability, not indirection for its own sake.

## Policy and detail

Suppose a reminder policy needs `send(recipient, message, idempotency_key)` and a provider SDK offers `post_message(template_id, payload, headers)`. Define the application port around the policy's guarantee, then adapt the SDK. The port should state retryability, duplicate effects, error categories, and data handling.

```python
class Notifier:
    def send(self, recipient, message, key):
        raise NotImplementedError

class ReminderService:
    def __init__(self, notifier):
        self.notifier = notifier

    def remind(self, reminder):
        return self.notifier.send(reminder.recipient,
                                  reminder.message,
                                  reminder.occurrence_id)
```

## Adapter and ownership

The adapter owns translation and provider-specific failure mapping. It should not silently strengthen guarantees: if the provider lacks idempotency, the application port must say so or add a durable deduplication boundary. An abstraction is useful only when its semantics are stable enough for policy clients to rely on.

### Diagnostic solutions

1. Include event identity, payload/visibility, append-only behavior, durability result, and failure categories; do not expose arbitrary SQL methods to policy.
2. Provider renames, pagination, retries, or error types force policy changes even when the application's behavior is unchanged.
3. Constructor injection makes the dependency explicit and stable for an object; parameter injection suits one operation; environment lookup hides the dependency and harms determinism.
4. A tiny stable pure calculation with no volatile dependency may be clearer as a direct function; an interface adds no test or change value.
