# Facade and Proxy: Simplifying and Controlling Access

A facade offers a task-oriented interface over a subsystem. A proxy stands in for another object and controls or changes access: it may be remote, lazy, cached, protected, or instrumented. They can be combined, but the reason for the boundary matters.

## Facade boundaries

A useful facade names a meaningful use case and owns coordination decisions appropriate to that boundary. It should not become a dumping ground for every subsystem rule. The facade's contract should describe partial failure, retry identity, authorization, and observability.

## Proxy semantics

A protection proxy checks identity/authorization; a virtual proxy defers expensive construction; a remote proxy maps calls across a network; a caching proxy changes freshness and invalidation. Each is an adapter-like boundary with stronger semantic obligations. A remote proxy cannot honestly promise local latency or atomic failure behavior.

4. Identify a case where a facade becomes a god object.

### Diagnostic solutions

1. Checkout must specify payment timeout/ambiguous result and inventory conflict; clients need a recovery/reconciliation path.
2. Network failure, retries, serialization, and remote side effects mean the proxy cannot behave exactly like a local call; document those differences.
3. A shared key can return one principal's data to another. Partition by authorized identity or prove the data is public.
4. When it accumulates unrelated use cases and policies from every subsystem, split by boundary or use-case ownership.
