# Integration Testing at Real Boundaries

Integration tests establish behavior that depends on a boundary: a database's transaction/isolation semantics, a serialization format, an HTTP provider contract, a filesystem, or a queue. They are not automatically better than unit tests; they answer a different question and should be placed where the real risk lives.

## Fidelity and scope

A test doubles the parts outside its boundary; the closer the environment is to production, the more realistic the evidence, but setup and diagnosis cost more. A fake database may be useful for a fast policy test and misleading for transaction semantics. A local container can test schema and protocol while still differing in scale, storage, credentials, or failover.

## Database and provider contracts

An integration test should declare fixture isolation, seed data, transaction scope, cleanup, clock/time zone, and failure injection. For a provider, test status mapping, timeout behavior, retries, idempotency, rate limits, and malformed responses. Do not assert only that “a request was made” when the contract is about the provider effect or data persisted.

## Diagnosis and test portfolio

Keep unit tests close to pure policy, integration tests at critical boundaries, and a small number of end-to-end tests for user goals and deployment wiring. A failing integration test should say whether schema, fixture, environment, or application contract failed. Make cleanup reliable; leaked state creates order-dependent evidence.

## Transfer exercises

1. Design an integration test for a migration that adds a non-null column.
2. Name a limitation of an in-memory fake for a database.
3. Explain why test data must include duplicate requests at an external boundary.
4. Choose a test layer for a user-visible authorization guarantee.

### Diagnostic solutions

1. Run old/new application compatibility, migrate representative rows, write/read the new field, test rollback/repair and null/default semantics, then verify constraints.
2. It may not model transactions, isolation, query parsing, constraints, indexes, or locking accurately.
3. Retries and timeouts make duplicate requests normal; the effect must be idempotent or explicitly compensated.
4. Include an API/integration test at the authorization/data boundary and an end-to-end scenario for the user goal; a unit policy test alone cannot prove wiring.
