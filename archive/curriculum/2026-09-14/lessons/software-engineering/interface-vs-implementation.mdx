# Interfaces, Representations, and Abstraction Functions

An interface is a promise about observable behavior. An implementation is a representation plus algorithms that satisfy that promise. If clients must know whether a queue uses a ring or a linked list, the abstraction boundary is leaking and future change becomes expensive.

## Contract, representation invariant, abstraction function

Suppose a queue is represented by `items`, `head`, `tail`, and `count`. A representation invariant might require `0 <= count <= capacity` and positions modulo capacity. The abstraction function maps the circular segment beginning at head to the logical FIFO sequence. A method proof has three parts: its precondition is checked, it preserves the representation invariant, and its result matches the abstract operation.

## Example: two set representations

A small set can use a sorted vector and binary search; a large mutable set can use hashing. Both can implement `add`, `contains`, and `remove` if they agree on equality, duplicate policy, and mutation semantics. The vector may give deterministic iteration order while the hash table does not; that difference is observable and must either be excluded from the interface or documented.

## Evolution and compatibility

Changing an interface can break source, binary, behavioral, or operational clients. Adding an optional field may be source-compatible but still break a strict parser. Replacing an exception with a sentinel can be behaviorally incompatible even if the method signature stays the same. Record compatibility assumptions and test old clients where the boundary matters.

### Diagnostic solutions

1. `0 <= top <= capacity`; the abstract sequence is `items[0..top)`, and pop returns the last element of that sequence.
2. Iteration order, hash timing, collision behavior, or the exact error type may leak. Decide which are part of the contract before optimizing.
3. It connects concrete fields to the abstract value, so reviewers can check whether each operation preserves meaning rather than only inspecting syntax.
4. Run old client behavior against both implementations for empty, singleton, and repeated drain cases; assert the documented status/value distinction.
