# Software Engineering as Evidence-Based Design

Software engineering is the discipline of making software systems dependable under real constraints: incomplete requirements, changing environments, finite budgets, human collaboration, and failure. Code is an important artifact, but a working build is not evidence that the right problem was solved or that the system will remain safe to change.

## Start with a system boundary

Consider “send a reminder when a report is ready.” The sentence leaves open who may request it, what counts as ready, whether duplicate reminders are acceptable, what happens when delivery fails, and which data may be visible. A professional team writes the boundary before choosing classes or cloud services:

- actors and trust boundaries;
- inputs, outputs, and observable side effects;
- invariants that must never be violated;
- quality objectives with a population and measurement window; and
- explicit non-goals and assumptions.

The boundary is a communication device and a test design. If two readers can implement incompatible behavior from the same request, the request is not yet a usable specification.

## Quality is multidimensional

“High quality” is not a synonym for “few defects.” A service can be functionally correct for a happy path yet unusable under load, impossible to operate, insecure, or too coupled to evolve. Quality attributes compete: stronger auditability can add latency and storage; lower latency can reduce consistency; a broad extension point can increase complexity.

State each important quality claim as an evidence obligation. “The service is reliable” becomes “99.9% of scheduled jobs complete within five minutes over a calendar month, excluding documented maintenance, with retries and an operator-visible failure state.” The target is not automatically good; its scope makes disagreement and testing possible.

## A small evidence loop

Use a short loop for each meaningful change: state the behavior, choose a design that makes it observable, implement the smallest slice, test normal and failure cases, review the evidence, and record what remains uncertain. A test is a probe, not a proof of all behavior. A review is an argument, not a substitute for execution.

## Professional responsibility

Engineers are responsible for honest claims about what they know, what they measured, and what they do not control. Escalate safety and security risks, protect confidential data, disclose uncertainty, and do not treat a deadline as permission to hide a known failure mode. Responsibility is distributed across a team, but a handoff does not erase a defect that was knowingly misrepresented.

## Transfer exercises

1. Rewrite “the API should be fast” as a measurable objective with workload and percentile.
2. Identify three different failure boundaries in a file-upload service.
3. Give one example where adding a feature can reduce a quality attribute.
4. List the evidence needed before claiming a retry mechanism is idempotent.

### Diagnostic solutions

1. For example: “For 95% of authenticated requests of 20 KB under 100 concurrent clients, p99 response time is below 200 ms over a 15-minute test.” State what is excluded.
2. Authentication/authorization, storage capacity and durability, and downstream virus-scanning or notification failure are distinct boundaries.
3. A synchronous audit trail can improve accountability while increasing write latency; a cache can improve latency while making freshness weaker.
4. Define an operation identity, replay it under timeouts and duplicate delivery, inspect persisted effects, and test concurrent retries. The evidence must include the provider or database boundary where duplication could occur.
