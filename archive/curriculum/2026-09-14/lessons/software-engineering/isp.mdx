# Interface Segregation and Client Needs

The interface-segregation principle protects clients from dependencies they do not need. A large interface creates change pressure: a read-only client must recompile, mock, or implement methods for writing, administration, or transport even when those capabilities are irrelevant.

## Capability boundaries

Instead of one `DocumentStore` with read, write, delete, search, and administrative methods, define the capabilities clients actually consume:

```python
class Reader:
    def read(self, document_id): raise NotImplementedError

class Writer:
    def write(self, document): raise NotImplementedError

def render_preview(reader, document_id):
    return reader.read(document_id).title
```

The concrete store may implement both capabilities. The preview client now depends only on read behavior, so write-policy changes do not alter its contract.

## Costs and counterexamples

Over-segregation can produce dozens of one-method interfaces that obscure a coherent concept and increase wiring. Split when clients or security boundaries differ, not whenever a method can be extracted. Keep a shared value type or protocol where the behavior truly belongs together, and preserve substitutability within each capability.

## Transfer exercises

2. Explain how interface segregation can reduce security risk.

4. Design a compatibility migration from a fat interface to two capabilities.

### Diagnostic solutions

1. Separate `Printer`, `Scanner`, `Fax`, and `StatusReader` based on actual clients and authorization; a multifunction device may implement several.
2. A client receives fewer methods/privileges and has fewer ways to misuse a component. Authorization still needs enforcement at the boundary.
3. Splitting can separate operations that must be atomic or coordinated, forcing clients to reconstruct an invariant incorrectly.
4. Add capability interfaces, adapt existing implementations, migrate clients gradually, and deprecate the old interface with tests for behavior and access policy.
