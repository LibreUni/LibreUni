# Liskov Substitution and Behavioral Contracts

Subtyping is a behavioral promise: code written against the base contract should continue to work when given an instance of the subtype. Shared fields, method names, or an “is-a” sentence are not enough.

## Contract rules

For a base operation, a substitutable subtype generally may weaken preconditions (accept more), strengthen postconditions (promise at least as much), and preserve invariants. It must not introduce surprising exceptions, mutate state the base promised not to mutate, or change equality/ordering assumptions clients rely on.

The classic rectangle/square example is useful only when the base rectangle contract permits independent width and height changes. If clients rely on that postcondition, a square cannot substitute. The defect is in the modeled contract, not in geometry.

## Alternatives to inheritance

Use capability interfaces (`Readable`, `Writable`), composition, or an explicit result type when behaviors differ. Adapters can translate a legacy component, but the adapter must not claim a stronger contract than it can implement. A type hierarchy should make invalid clients impossible or at least visible through the interface.

## Transfer exercises

1. Give an example of a weakened postcondition.
2. Identify a subtype that accepts more inputs but still violates substitutability through side effects.
3. Redesign `ReadOnlyFile` without lying about capabilities.
4. Write a contract test that every writer implementation must pass.

### Diagnostic solutions

1. A base `sort` promises ascending order; a subtype returns an arbitrary permutation. It accepts the same inputs but weakens the result.
2. A read-only query that unexpectedly deletes or logs sensitive data can violate observable side-effect expectations even if its return value matches.
3. Expose separate `Readable` and `Writable` interfaces or make the operation return a documented unsupported result through a capability-aware API.
4. Test accepted bytes, retryable/fatal errors, idempotency policy, and whether the promised postcondition holds after success.
