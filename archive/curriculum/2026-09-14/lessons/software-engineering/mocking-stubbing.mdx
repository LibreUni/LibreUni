# Test Doubles Without Lying to Yourself

Test doubles control or observe a dependency. A dummy fills an unused argument; a stub returns controlled answers; a fake provides a lightweight working implementation; a spy records calls; a mock verifies an interaction expectation. The labels matter less than the question: what behavior is the test establishing, and which boundary is being replaced?

## Behavior versus interaction

Interaction assertions are justified when the interaction is a contract: publishing a required event, releasing a resource, or using an idempotency key. They are brittle when they assert incidental call order or private helper structure. Prefer checking returned behavior, persisted state, and emitted boundary effects.

The fake is useful only if its behavior matches the relevant audit contract. If production relies on uniqueness or durability, add a real-boundary test; a list does not model those properties.

## Contract drift

A double can become a second implementation of the dependency and drift. Keep it small, derive it from an owned interface, and pair it with contract tests shared by fake and real adapters when practical. Do not return impossible values merely to make a branch easy to reach; represent failure modes the boundary can actually produce.

## Transfer exercises

4. Design a contract test shared by a provider adapter and its fake.

### Diagnostic solutions

1. It is a fake if it provides a lightweight behavior; it is also a spy if it records calls. Categories can overlap by purpose.
2. An outbox publisher must receive a stable event ID exactly once per committed event, or a resource must be closed before return; state the reason.
3. It may omit constraints, transactions, isolation, query semantics, durability, and contention.
4. Feed success, retryable, fatal, malformed, and timeout cases; assert mapped result categories, idempotency key propagation, and no secret leakage.
