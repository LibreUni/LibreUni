# Open-Closed Design and Stable Variation Points

The open-closed principle says a module should be open to required extension and closed to risky modification. It is not a command to never edit code. The design question is whether a change axis is stable enough, valuable enough, and constrained enough to earn an extension boundary.

## Variation and invariants

Suppose checkout supports shipping rules. Keep invariant parts—order identity, authorization, money units, and persistence—outside the variation, and give each shipping strategy a contract such as: nonnegative cost, supported destination, deterministic result for the same inputs, and no mutation of the order.

```python
class FreeShipping:
    def quote(self, order):
        return 0

class ThresholdShipping:
    def __init__(self, threshold, fee):
        self.threshold, self.fee = threshold, fee
    def quote(self, order):
        return 0 if order.subtotal >= self.threshold else self.fee

def shipping_total(order, policy):
    return policy.quote(order)
```

The caller is closed to adding a new policy, but the policy contract is open to implementations. The example still needs validation of threshold and currency in a real domain.

## Modification is sometimes the right design

If the rule is local, unstable, or used once, a direct edit may be clearer and safer than adding a hierarchy. Extension boundaries can also make illegal combinations possible, spread validation across implementations, or freeze a poor interface. Use tests and change history to decide where closure buys risk reduction.

### Diagnostic solutions

1. Format variation (CSV/JSON) with an output encoding/escaping and failure contract; do not let exporters silently change business totals.
2. A single stable branch with no expected variation may be easier to read and test; speculative abstraction adds surface without reducing change risk.
3. Clients must know whether retries, partial output, or unsupported inputs are safe; hiding these differences makes substitution unsound.
4. Nonnegative cost in the correct currency and same result for the same order/destination; add unsupported-destination behavior and rounding tests.
