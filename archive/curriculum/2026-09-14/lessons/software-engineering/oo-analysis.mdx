# Object-Oriented Analysis: From Needs to Models

Analysis asks what problem the system must solve and what concepts make the behavior intelligible. It is not a race to name classes from nouns. A useful model is selective: it preserves distinctions that affect behavior, ownership, constraints, or change.

## Actors, goals, and boundaries

An actor is a role external to the system boundary, not necessarily a human. A payment provider, scheduler, or administrator can be an actor. Write goals in observable terms: “a coordinator can approve a request” is stronger than “the system manages approvals.” Name preconditions and postconditions so acceptance tests can be derived.

## Domain concepts and vocabulary

Candidate concepts earn a place when they carry a rule, identity, relationship, or meaningful state. “Reservation” may be a domain entity; “blue button” is a presentation detail unless it encodes a workflow distinction. Create a glossary and resolve synonyms before they become inconsistent field names.

## Alternate flows and abuse cases

The happy path is a hypothesis. Ask what happens when a precondition is false, a dependency times out, a request is repeated, a clock boundary is crossed, or a user lacks permission. Abuse cases apply the same discipline to an adversary: what asset is targeted, through which boundary, with which capability, and what evidence detects the attempt?

## Transfer exercises

1. Write a scenario for changing a reservation's time and include one conflict alternative.
2. Identify a concept that should remain a value object rather than an entity.
3. Turn “secure login” into an abuse case.
4. List one question that a model cannot answer without stakeholder evidence.

### Diagnostic solutions

1. Include actor, identity, old/new interval, conflict rule, authorization, and commit/failure postconditions.
2. A currency amount with currency code can be a value if identity is irrelevant and equality is by value; document rounding and immutability.
3. Asset: account/session; attacker: credential holder or network observer; goal: authenticate or take over; boundary: login/token; evidence: rejection, rate limit, and audit record.
4. Whether cancellation refunds money, whether a late delivery is acceptable, or which records must be retained are product/policy facts, not class-diagram deductions.
