# Object-Oriented Design: Responsibilities and Collaborations

Design turns an analyzed behavior into executable structure. The central question is not “which pattern is this?” but “which object has the information and authority to enforce this rule, and what does it need from collaborators?”

## Information, authority, and cohesion

Keep local invariants near the state they govern. A `Money` value can enforce currency/scale rules; a `Reservation` can enforce its own lifecycle; a `BookingService` can coordinate availability and authorization. A service that owns no state and only forwards calls may be a useful boundary, but a “god service” that knows every table and policy is a coupling hotspot.

## Collaborations as traces

For a use case, write a normal trace and failure traces before selecting classes:

1. actor sends a request with identity and proposed interval;
2. boundary authenticates and loads relevant policy;
3. coordinator checks the invariant under the chosen concurrency boundary;
4. repository commits the reservation and an audit event;
5. notification is scheduled with a stable event identity.

Ask what is visible if step 4 succeeds and step 5 times out. The answer determines idempotency and recovery, not just method names.

## Design review questions

Review whether each dependency is necessary, whether a collaborator can be substituted, whether a failure is represented, and whether a mutable reference leaks an invariant. A sequence diagram should show meaningful messages and ownership boundaries, not every getter. A class diagram should show relationships that affect reasoning, not every field.

## Transfer exercises

1. Assign responsibilities for validating an interval, checking room conflicts, and sending a reminder.
2. Give a failure trace for “database commit succeeds, worker crashes before email.”
3. Explain why a controller that contains pricing rules is hard to test.
4. Identify a dependency that should be injected and one that should remain internal.

### Diagnostic solutions

1. Interval value/reservation for local validity; repository/coordinator for competing availability; worker/provider boundary for delivery with idempotency.
2. The durable event remains pending; a worker retries by event identity; an operator can inspect age and reconcile. No second reservation should be created.
3. It couples policy to transport and makes tests construct HTTP details; extract a pure policy or domain boundary with a focused contract.
4. Inject a clock/provider whose behavior is part of the test; keep a private helper internal when substituting it would not clarify a meaningful boundary.
