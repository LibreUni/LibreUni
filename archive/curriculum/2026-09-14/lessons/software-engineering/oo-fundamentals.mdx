# Objects, Encapsulation, and Composition

Object-oriented design is a way to organize state, behavior, and variation. An object is not valuable because it has getters and setters; it is valuable when a boundary protects an invariant or gives a change a controlled home.

## Identity, state, behavior

An object model should answer: what has identity, what state may change, which operations are legal, and which invariant must always hold? A `Reservation` may have an identity independent of its current status; a value object such as `Money` may be defined entirely by value and currency. Confusing the two creates equality and lifecycle bugs.

```python
class Reservation:
    def __init__(self, reservation_id, start, end):
        if end <= start:
            raise ValueError("end must be after start")
        self._id = reservation_id
        self._start = start
        self._end = end
        self._status = "active"

    def cancel(self):
        if self._status != "active":
            raise ValueError("only active reservations can be cancelled")
        self._status = "cancelled"
```

The constructor and transition enforce only local invariants. Conflict with another reservation belongs to a coordinator or repository that can observe the relevant set atomically.

## Encapsulation and collaboration

Expose operations that express intent, such as `cancel()` or `reserve()`, rather than making every caller manipulate status strings. Keep read-only views narrow and document whether returned collections are snapshots or live aliases. Encapsulation is broken when a “private” collection is returned for external mutation or when a public method allows an invalid transition indirectly.

## Inheritance and composition

Inheritance is appropriate when a subtype satisfies the base type's behavioral contract everywhere clients rely on it. Shared implementation is not enough. Composition is often safer when a component can be replaced, configured, or combined independently. A `Report` can compose a `Formatter`; it need not inherit from a formatter merely to reuse a method.

## Transfer exercises

1. State a local invariant and a cross-object invariant for a shopping cart.
2. Give a subtype that violates a base contract even though it shares method names.
3. Identify an aliasing hazard in a method that returns a mutable internal list.
4. Choose composition or inheritance for pluggable tax rules and defend it.

### Diagnostic solutions

1. Local: quantity is positive and item identity is valid. Cross-object: total equals the sum of line prices under one currency/rounding policy.
2. A `ReadOnlyFile` subtype of a writable `File` that throws on `write` violates clients that rely on the writable contract.
3. A caller can mutate the list and bypass validation; return an immutable view or copy when ownership is not transferred.
4. Composition: tax policies vary independently and can be injected/tested without claiming that every policy is a subtype with identical behavior.
