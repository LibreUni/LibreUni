# Refactoring Under a Behavioral Safety Net

Refactoring changes internal structure without intentionally changing externally observable behavior. It is not a cleanup excuse for unreviewed feature changes, and a passing test suite does not guarantee preservation if the suite omits important behavior.

## Smells as hypotheses

Long methods, duplicated knowledge, feature envy, primitive obsession, and divergent change are signals, not automatic defects. Ask what makes a change hard: unclear responsibility, hidden state, unstable dependency, duplicated policy, or a missing abstraction. A refactoring should reduce a named risk and leave the contract easier to inspect.

The equivalence is only as broad as the cases and language semantics tested. If `values` can be a generator, a database cursor, or a custom numeric type, the contract must say so.

## Safe sequence and legacy systems

1. Write the intent and current observable contract.
2. Add characterization tests for representative and boundary behavior.
3. Make one small transformation.
4. Run focused checks, then the broader suite and static analysis.
5. Inspect the diff and record any changed assumption.

For systems with weak tests, use logs, production traces, approval rules, and shadow comparisons as additional evidence. A strangler or adapter boundary can reduce risk when a complete rewrite would expand the unknown surface.

## Transfer exercises

1. Distinguish a refactor from a feature in a pull request.
2. Give a characterization test for an undocumented legacy parser.
3. Explain why a formatter-only diff can still hide risk.
4. Name a case where a new module is safer than an incremental refactor.

### Diagnostic solutions

1. A refactor preserves the stated external behavior; a feature changes or adds behavior. If both are needed, separate commits/acceptance criteria.
2. Capture accepted/rejected inputs, output normalization, error type, and side effects for representative boundary cases before changing code.
3. Formatting can obscure accidental edits, line-ending changes, or generated code changes; review tooling and keep mechanical changes separate.
4. A security or ownership boundary may be too tangled to change safely in place; add an adapter/parallel implementation and compare outputs before switching.
