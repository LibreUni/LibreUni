# Lifecycle Models and Feedback Loops

A lifecycle model allocates attention across discovery, specification, design, implementation, verification, release, operation, and retirement. It is not a guarantee of quality and not a personality type for a team. The choice should reduce a known uncertainty at an acceptable cost.

## Activities and risk

Every project needs some form of problem discovery, contract definition, design reasoning, implementation, verification, release control, operation, and learning. The sequence and granularity vary. A regulated device may require traceability and independent review before implementation; a consumer experiment may need rapid product feedback; a database migration may require a reversible rollout and restore drill.

Map each risk to a feedback loop:

| Risk | Feedback artifact | Decision it informs |
| --- | --- | --- |
| Users interpret a workflow differently | prototype and task observation | revise behavior contract |
| A dependency has unknown latency | integration spike and percentile measurement | choose timeout/bulkhead policy |
| A migration may lose data | rehearsal restore and invariant checks | approve or redesign migration |
| A security boundary is misunderstood | threat model and abuse tests | change authorization or scope |

The table is more useful than the name “agile” or “waterfall” because it names the uncertainty and the evidence.

## Incremental does not mean careless

An increment is valuable only if it is integrated, testable, and honest about what it does not yet guarantee. Vertical slices can expose cross-layer assumptions early; horizontal layers can be appropriate when an interface or platform boundary must be stabilized first. “Done” needs a definition that includes tests, review, documentation, observability, and migration behavior where relevant.

Continuous delivery reduces the batch size between change and feedback; it does not require deploying every change to every user. Feature flags, canaries, staged migrations, and explicit rollback or repair paths make release risk observable. A rollback may be impossible after an irreversible data migration, so “rollback” must not be a ritual word.

## Transfer exercises

1. Choose feedback for an unknown third-party API rate limit and explain why a unit test is insufficient.
2. Distinguish an increment, a release, and a deployment.
3. Give a case where a rollback cannot safely undo a release and state the repair strategy.
4. Design a definition of done for a schema change.

### Diagnostic solutions

1. Use a bounded integration test or sandbox probe that measures throttling and retry semantics; a unit test cannot establish the external provider's behavior.
2. An increment is an integrated product change; a release makes a version available under a rollout policy; a deployment places an artifact in an environment. They can be separated by flags or stages.
3. Destructive or externally visible data changes may be irreversible. Use expand/contract migrations, backups, forward repair, and reconciliation rather than claiming an unsafe rollback.
4. Include backward-compatible schema, application tests, migration rehearsal, observability, access review, and a rollback/repair decision with an owner.
