# Factories, Global State, and Lifetime

A factory hides construction choices; a singleton restricts or centralizes instance lifetime. They solve different problems. A factory can improve dependency inversion without creating global state. A singleton may be justified for a process-wide resource with one coherent owner, but “only one” is a requirement that must include tests, concurrency, shutdown, and configuration.

## Factory boundary

Use a factory when the concrete type depends on configuration, input, platform, or a policy that should not leak into callers:

```python
def make_parser(format_name):
    if format_name == "json": return JsonParser()
    if format_name == "csv": return CsvParser()
    raise ValueError("unsupported format")
```

The factory contract includes unsupported input and configuration errors. A factory that returns a common interface still needs the substitutability tests for each implementation.

## Singleton costs

Global access hides dependencies, makes test order matter, couples configuration to process lifetime, and creates contention or reentrancy risks. Lazy initialization also needs a thread-safety and failure policy. Prefer an application composition root that creates one instance and passes it to clients; the application can still have one database pool without every class reaching for a global.

## Transfer exercises

1. Give a valid singleton invariant and two tests it still requires.
2. Compare a factory with a service locator.
3. Design a shutdown policy for a process-wide resource.
4. Identify a scope where “one instance” is correct but global access is not.

### Diagnostic solutions

1. Exactly one registry per process with synchronized registration, deterministic initialization, and defined shutdown; test concurrent initialization and reset/isolation behavior.
2. A factory creates a requested dependency at a boundary; a service locator lets arbitrary code pull hidden dependencies, increasing coupling and making contracts less visible.
3. Stop new work, drain/close users, record failures, and define behavior for calls after shutdown. Do not rely on process exit ordering.
4. One repository per request or tenant can be correct while still being passed explicitly to handlers.
