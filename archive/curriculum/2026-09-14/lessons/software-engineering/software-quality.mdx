# Quality Attributes, Measurement, and Maintenance

Quality is the degree to which a system satisfies stated and implied needs under stated conditions. “No bugs” is neither measurable nor sufficient: a system may be secure but unusable, fast but inconsistent, maintainable but too expensive to run. Quality attributes are properties of a system in an environment, not decorative adjectives attached to a design.

## Quality scenarios

Write a scenario with:

- source and stimulus;
- operating environment and load;
- expected response;
- response measure; and
- evidence method and exclusions.

For availability, distinguish a user-visible error from a process being alive. For security, name an attacker capability and protected asset. For maintainability, define a change task, the affected module boundary, and the effort or defect risk to measure.

## Technical debt and maintenance

Technical debt is a present shortcut that creates future cost or risk; it is not equivalent to old code and not automatically bad. Record the principal (what was deferred), interest (how it harms future work or operations), trigger (when repayment becomes necessary), and owner. “Refactor later” without a trigger is an unowned risk.

Maintenance includes correcting defects, adapting to changed environments, improving behavior or performance, and preventing future failures. A dependency upgrade may be adaptive and security-critical; a readability refactor may be preventive or perfective; an incident fix is incomplete if it lacks a regression test or operational learning.

## Transfer exercises

1. Write a security scenario for a tenant-scoped API.
2. Explain why code coverage is evidence but not a quality attribute.
3. Classify a port from an deprecated operating system API to a new one.
4. Record one technical-debt item with principal, interest, trigger, and owner.

### Diagnostic solutions

1. For example: “Given an authenticated user from tenant A, a request containing tenant B's identifier is rejected and produces no tenant-B data; test with direct and indirect identifiers.”
2. Coverage measures which paths were executed by a test suite; it does not establish assertion quality, behavior correctness, usability, performance, or security.
3. Usually adaptive maintenance because the environment/API changed; the classification can include corrective work if the old API causes failures.
4. “Temporary duplicate parsing in two services; every rule change must be made twice and can diverge; trigger: next schema change; owner: service team.”
