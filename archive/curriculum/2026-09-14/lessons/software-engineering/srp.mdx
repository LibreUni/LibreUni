# Single Responsibility as Change Cohesion

The single-responsibility principle is about a module having one coherent reason to change, not about containing one method or one noun. A report component that calculates totals, formats HTML, writes files, and sends email has several change axes: business policy, presentation, persistence, and delivery.

## Separate policy from effects

Start from behavior, then separate decisions that can be tested from effects that require infrastructure:

```python
def invoice_total(lines, tax_rate):
    subtotal = sum(line.price * line.quantity for line in lines)
    return subtotal * (1 + tax_rate)

class InvoiceSender:
    def __init__(self, mailer):
        self.mailer = mailer

    def send(self, invoice, address):
        self.mailer.send(address, render_invoice(invoice))
```

The pure calculation and the delivery boundary can change for different reasons. Do not split merely to create more files; keep a boundary where a change can be reasoned about and tested independently.

## Counterexample: over-splitting

Splitting a module into `NameValidator`, `LengthValidator`, `CharacterValidator`, and `PasswordPolicy` can make a policy harder to read if every rule must coordinate through mutable state. Cohesion is lost when the new pieces cannot be understood without reconstructing a hidden workflow. Prefer a small policy object with a clear contract until independent change or reuse justifies finer seams.

## Transfer exercises

1. List the independent change axes in a CSV export function.
2. Give one reason not to split two helpers that always change together.
3. Propose a test boundary for a rate-limit policy.
4. Explain why a “God class” is a coupling problem, not just a size problem.

### Diagnostic solutions

1. Data selection, column mapping, escaping/format policy, file/stream delivery, and error reporting may differ; validate whether those are truly independent in the product.
2. The split can add coordination and duplicate knowledge without reducing change impact or improving testability.
3. A pure policy taking identity, time, and history and returning allow/deny plus retry time; persistence and clock adapters are tested separately.
4. A God class concentrates many change reasons and dependencies, so unrelated changes share a failure surface and tests require broad setup.
