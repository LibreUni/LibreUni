# Test-Driven Development as Design Feedback

TDD is a feedback loop: write a small failing example, implement enough to make it pass, then refactor while preserving behavior. Its value is not the color sequence itself; the test makes an interface and example concrete before implementation details harden.

## Red, green, refactor

Start with a meaningful example and a precise failure. Implement the smallest behavior that satisfies the current contract; avoid speculative generality. Then refactor names, boundaries, and duplication while keeping the test suite as a regression oracle. Add the next example only when it represents a distinct partition or a clarified requirement.

<CodeRunner client:load
  title="A small red-to-green step"
  language="python"
  code={`def clamp(value, low, high):
    if low > high:
        raise ValueError("low must not exceed high")
    return max(low, min(value, high))

cases = [(5, 0, 10), (-1, 0, 10), (11, 0, 10)]
for value, low, high in cases:
    print(clamp(value, low, high))`}
  output="5\n0\n10"

The code is not a complete specification: equality, numeric types, and error policy still need decisions. TDD exposes those decisions as examples; it does not invent them.

## Design pressure and limits

Hard-to-test code can signal hidden time, I/O, global state, or tangled responsibility. Splitting every dependency solely to make mocks easy can produce abstractions with no domain meaning. TDD also cannot by itself discover an unmet user need, prove a distributed guarantee, or measure production behavior. Pair it with exploration, review, integration tests, threat modeling, and operational rehearsal.

## Transfer exercises

1. Write the first failing example for a queue's empty pop.
2. Explain why “make it pass” can produce a false implementation.
3. Name one requirement best explored with a prototype rather than TDD alone.
4. Plan a refactoring step after a green test.

### Diagnostic solutions

1. Call pop on a new queue and assert the documented empty status/value without reading an element.
2. A test can encode a mistaken requirement or be too weak; review the contract and add counterexamples before trusting green.
3. User workflow, latency under real data, accessibility, or third-party integration feasibility may need an experiment.
4. Identify duplicated knowledge or an unclear boundary, make the smallest behavior-preserving change, then rerun focused and full tests.
