Performance engineering begins by defining what is being measured. A processor can be faster in cycles per instruction and slower in wall-clock time if its clock is lower, or faster on one input and slower on another because its memory behavior changes. A credible performance claim names the workload, correctness condition, measurement boundary, resource metric, and baseline. Only then do equations such as CPI, AMAT, Amdahl’s law, and throughput become useful rather than decorative.

## Time, instruction count, and CPI

For a program executing $IC$ instructions, average cycles per instruction $CPI$, and clock frequency $f$, idealized CPU time is

$$
T=\frac{IC\cdot CPI}{f}=IC\cdot CPI\cdot T_{cycle}.
$$

The formula is a decomposition, not a causal explanation. $IC$ depends on compiler, ISA, optimization, and input. CPI depends on pipeline width, hazards, cache behavior, branches, memory-level parallelism, and contention. Frequency depends on critical paths, voltage, temperature, and design point. Improving one term can worsen another.

If a processor retires 3 billion instructions in 1.5 seconds at 2 GHz, then $IC=3\cdot10^9$, cycles $=3\cdot10^9$, and $CPI=1$. If a second implementation retires 2.4 billion instructions in 1.4 seconds at 2.5 GHz, its cycles are $3.5\cdot10^9$ and CPI is about 1.458. It is faster in wall-clock time despite a worse CPI because it performs fewer instructions and runs at a higher frequency. Reporting CPI alone would reverse the conclusion.

$$
CPI=CPI_{base}+\alpha_{br}p_{br}+\alpha_{load}p_{load}+\alpha_{L1}p_{L1}+\cdots
$$

is useful only when $\alpha$ represents the relevant frequency and $p$ the conditional penalty. Double-counting a miss penalty that is already embedded in a measured CPI produces a false diagnosis.

> **Pause & Predict: Does lower CPI always imply faster execution?** Suppose an optimizing compiler eliminates 50% of the instructions in an inner loop. All eliminated instructions were simple 1-cycle integer additions; all long-latency memory loads remain.
> * What happens to the program's average $\text{CPI}$? Does it increase, decrease, or remain constant?
> * Does total execution time $T$ improve or degrade?
> Commit your reasoning before opening the analysis below.

**Analysis:**
The average $\text{CPI}$ actually **increases**!
Suppose the original program had 100 instructions: 50 ALU ops (1 cycle each) and 50 cache-miss loads (20 cycles each).
* Original cycles: $50(1) + 50(20) = 1050$ cycles. Original $\text{CPI} = 1050 / 100 = 10.5$.
* New program: The 50 ALU ops are eliminated. Remaining instructions: 50 loads.
* New cycles: $50(20) = 1000$ cycles. New $\text{CPI} = 1000 / 50 = 20.0$.
Average $\text{CPI}$ nearly doubled from $10.5$ to $20.0$, yet total execution time dropped from 1050 cycles to 1000 cycles. Optimizing for CPI alone is a classic pitfall: total wall-clock time ($T = IC \cdot \text{CPI} / f$) is the only true figure of merit.

## Latency, throughput, and queueing

Latency is the time for one operation from request to completion. Throughput is the sustainable completion rate. A pipelined multiplier may have latency four cycles and throughput one result per cycle; a nonpipelined multiplier may have latency and initiation interval both four cycles. A system can have low latency but poor throughput, or high latency with excellent throughput after filling.

Queueing adds waiting time. If a server’s utilization approaches one, small increases in offered load can produce large increases in response latency even when service time is unchanged. A network or memory benchmark that measures only peak bandwidth hides queueing effects and can overstate performance under contention. Tail latency—p95, p99, or higher—matters when a user request depends on many parallel subrequests.

**Worked pipeline example.** A four-stage unit has 2 ns latency per result after fill and accepts one input every 0.5 ns. For a single request, latency is approximately 2 ns; for 100 independent requests, completion time is $2+(99)(0.5)=51.5$ ns. A nonpipelined unit with 2 ns service time takes 200 ns. If the requests are dependent, however, the consumer may need to wait for each two-nanosecond result and receive little benefit from throughput.

## Amdahl’s law and bottlenecks

If fraction $p$ of the original execution time is improved by factor $s$, total speedup is

$$
S=\frac{1}{(1-p)+p/s}.
$$

The unimproved fraction limits the result. If memory accounts for 40% and is made twice as fast, $S=1/(0.6+0.2)=1.25$. If serialization accounts for 70% and becomes free, the maximum speedup is $1/0.3\approx3.33$, not infinite.

The fraction must be measured in the baseline execution, not inferred from the fraction of source code or hardware blocks. Improving cache hit rate can reduce memory time but also change overlap with computation; the simple law may need a more detailed model. Gustafson-style scaling asks a different question: as the problem grows with processor count, how much parallel work can be usefully added? Neither law replaces a workload definition.

## Roofline and resource ceilings

For data-intensive kernels, arithmetic intensity is operations per byte transferred from a bottleneck memory level. If peak compute throughput is $P_{peak}$ operations per second and sustainable bandwidth is $B$, attainable performance is bounded by

$$
P\le\min(P_{peak},B\cdot I),
$$

where $I$ is arithmetic intensity. A low-intensity kernel is bandwidth-bound; adding arithmetic units does little unless reuse or compression increases effective intensity. A high-intensity kernel is compute-bound until another resource—register capacity, cache bandwidth, instruction issue, or synchronization—becomes limiting.

**Worked roofline example.** A processor sustains 1 TB/s of relevant memory bandwidth and 4 TFLOP/s peak arithmetic. A kernel performs 2 floating operations per byte, so the bandwidth ceiling is 2 TFLOP/s and the kernel is bandwidth-bound under the model. Doubling peak compute to 8 TFLOP/s changes nothing; doubling reuse to 4 operations per byte raises the bandwidth ceiling to 4 TFLOP/s, at which point peak compute becomes the next ceiling.

## Measurement design

A benchmark is an experiment, not a stopwatch call. Define the hypothesis, independent variable, dependent metric, controlled variables, repetitions, warm-up policy, and stopping rule. The timing boundary must exclude setup when measuring steady-state execution and include it when measuring end-to-end user experience. Report distribution and uncertainty, not only the fastest run.

**Worked example: an experiment that could falsify a cache claim.** Suppose the claim is that 32×32 tiling makes a 1024×1024 double-precision transpose faster because it lowers L1 data-cache misses.

* **Hypothesis:** tiling reduces L1D miss rate relative to the naive traversal, and that reduction is the mechanism behind any wall-time gain.
* **Independent variable:** traversal order (naive, 16×16, 32×32, 64×64) with the same matrix and element type.
* **Dependent variables:** median wall time over repeated runs, L1D and LLC miss rates, and memory bandwidth, measured with hardware counters.
* **Controls:** identical compiler and flags, single thread pinned to one core, fixed frequency governor, same input values and alignment, warm-up before measurement, and interleaved A/B/B/A ordering to spread thermal and background drift.
* **Stopping rule and analysis:** report all runs or their median and confidence interval, not the fastest run; use enough repetitions that the interval for the tiled-versus-naive difference is narrower than the effect the claim asserts.

Under the stated hypothesis, either reduced misses without a time improvement or a time improvement without the predicted miss reduction fails to support the proposed mechanism. These observations can suggest another ceiling or cause, such as TLB behavior or code generation, but do not identify it by themselves. Reporting only a warm, best-of-three timing cannot distinguish these cases.

Warm-up may populate instruction/data caches, trigger JIT compilation, stabilize branch predictors, or move a frequency governor. Randomized input order can prevent an algorithm from receiving a pre-sorted favorable trace, but randomization itself must be reproducible and reported.

System-level confounders can dominate small architectural effects. CPU affinity, thread count, background OS load, thermal throttling, compiler optimization flags, and heap allocator behavior must all be tightly pinned and monitored.

Use counters to test mechanisms. If a cache hypothesis predicts that row-major traversal lowers L1 misses, measure misses and bandwidth as well as time. If a branch hypothesis predicts misprediction stalls, measure branch events and compare a branchless variant. Counters are not infallible—multiplexing, sampling, speculative counting, and privilege restrictions matter—but they are stronger evidence than a narrative about “cache friendliness.”

## Statistical interpretation

A mean is sensitive to outliers; a median describes a typical run; high percentiles describe tail behavior. Confidence intervals quantify uncertainty under assumptions about sampling, but repeated measurements from the same warmed system are not automatically independent. Effect size matters: a 1% improvement with 0.8% measurement variation is weak evidence unless the experiment is strengthened.

**Worked example: a 1% mean gain against run-to-run variation.** Five independent baseline runs give a mean of 100.0 ms with sample standard deviation 0.8 ms; five independent variant runs give 99.0 ms with the same standard deviation. The observed difference is 1.0 ms, or 1%.

Treating the runs as independent and approximately normal, the standard error of the difference is $0.8\sqrt{2/5} \approx 0.51$ ms. A Welch interval with about eight degrees of freedom and $t_{0.975} \approx 2.31$ gives a 95% interval of roughly $1.0 \pm 1.17$ ms, or $[-0.17, 2.17]$ ms. The interval includes zero, so the data do not establish the 1% gain even though the sample mean improved. If the same five input pairs are run in alternating order, the paired differences might be $[0.8, 1.2, 0.9, 1.1, 1.0]$ ms: mean 1.0 ms, sample standard deviation 0.16 ms, standard error 0.07 ms, and a 95% interval of about $[0.80, 1.20]$ ms, which excludes zero. Pairing removes between-run drift but does not make repeated runs on one warmed machine independent; the report must state which design was used and check for interference. Neither analysis protects against a sample that is too small to represent the workload, and neither says anything about the tail: a 1% mean gain can coexist with a worse p99.

Benchmark suites should include representative and adversarial workloads. A compiler optimization that wins on one synthetic loop may lose on a real application because instruction-cache pressure or code size changes. A cache design that wins on a small working set may lose when the active data exceeds L2. The strongest report explains where the model predicts failure and tests that boundary.

## Energy and performance per watt

Performance is not the only constraint. Dynamic energy is related to switching activity, capacitance, and voltage; leakage and static power matter at idle and high density. A higher frequency may require higher voltage and disproportionately increase power.

Memory traffic often consumes more energy than an arithmetic operation. Consequently, a cache optimization can improve both time and energy, or increase energy by fetching large unused lines.

Performance per watt is a ratio with a workload denominator. A design that finishes quickly but uses a high power burst may compare differently from one that runs longer at low power, depending on whether the system is energy-limited, thermally limited, or latency-limited. State the objective before optimizing.

**Worked example: voltage-frequency scaling and performance per watt.** Consider a simplified dynamic-power model $P_{dyn}=\alpha C V^{2} f$, with leakage and static power omitted. A core runs at 2.0 GHz and 1.0 V with $P_{dyn}=10$ W. To reach 3.0 GHz, the design raises the supply to 1.2 V. With IPC and instruction count unchanged, throughput rises by $3.0/2.0=1.5\times$, but power rises by $(1.2/1.0)^2 \times (3.0/2.0)=2.16\times$, to 21.6 W. Performance per watt therefore falls to $1.5/2.16 \approx 0.69$ of its original value, about 31% lower, and energy per instruction rises by $2.16/1.5=1.44$, or 44%. Including leakage and other static power can change the ratio in either direction: it must be measured or modeled at both operating points. The arithmetic does not prove that the higher frequency is wrong; it proves that the frequency choice must be evaluated against the stated objective, and that a 50% clock increase is not a 50% performance-per-watt increase.

### Worked Trace: Multi-Component CPI Stall Decomposition & Frequency Trade-off

Consider evaluating an architectural proposal to deepen a pipeline from 5 stages to 10 stages:
* **Baseline Processor (Arch-A)**: Clock frequency $f_A = 2.0\text{ GHz}$ ($T_{cycle} = 0.5\text{ ns}$). Base $CPI = 1.0$.
  * Branch instructions: 20% of workload, branch penalty is 2 cycles, misprediction rate $p_{br} = 5\%$.
  * Memory load instructions: 25% of workload, L1 D-cache miss rate $p_{miss} = 8\%$, miss penalty 40 cycles.
* **Proposed Processor (Arch-B)**: Deeper pipeline allows clock frequency to increase to $f_B = 3.0\text{ GHz}$ ($T_{cycle} = 0.333\text{ ns}$).
  * Deeper pipeline increases branch misprediction penalty to 6 cycles.
  * Higher frequency increases L1 D-cache miss penalty to 60 cycles (main memory latency in nanoseconds is constant at $20\text{ ns}$).

**Step 1: Compute Effective CPI for Arch-A**:
$$CPI_A = CPI_{base} + f_{br} \cdot p_{br} \cdot \text{Penalty}_{br, A} + f_{load} \cdot p_{miss} \cdot \text{Penalty}_{mem, A}$$
$$CPI_A = 1.0 + (0.20 \cdot 0.05 \cdot 2) + (0.25 \cdot 0.08 \cdot 40) = 1.0 + 0.02 + 0.80 = 1.82.$$

**Step 2: Compute Effective CPI for Arch-B**:
$$CPI_B = CPI_{base} + f_{br} \cdot p_{br} \cdot \text{Penalty}_{br, B} + f_{load} \cdot p_{miss} \cdot \text{Penalty}_{mem, B}$$
$$CPI_B = 1.0 + (0.20 \cdot 0.05 \cdot 6) + (0.25 \cdot 0.08 \cdot 60) = 1.0 + 0.06 + 1.20 = 2.26.$$

**Step 3: Compare Wall-Clock Execution Time**:
For an instruction trace of $IC = 10^9$ instructions:
$$T_A = \frac{IC \cdot CPI_A}{f_A} = \frac{10^9 \cdot 1.82}{2.0 \times 10^9\text{ Hz}} = 0.910\text{ seconds}.$$
$$T_B = \frac{IC \cdot CPI_B}{f_B} = \frac{10^9 \cdot 2.26}{3.0 \times 10^9\text{ Hz}} = 0.753\text{ seconds}.$$

**Conclusion**:
Even though Arch-B suffers a 24.2% penalty in CPI ($1.82 \to 2.26$) due to worse stall penalties in cycles, the 50% frequency increase ($2.0 \to 3.0\text{ GHz}$) dominates, producing an overall speedup of $\frac{0.910}{0.753} \approx 1.21\times$ (21% faster).


### Counterexample & Failure Mode: The MFLOPS / MIPS Mirage (The Algorithm vs Rate Trap)

Can a lower operation count or a higher execution rate mislead an optimization decision?
Consider multiplying two $N \times N$ dense matrices with $N = 1024$.

1. **Standard Triple-Loop $O(N^3)$**:
   * Operations: $2N^3 = 2(1024)^3 \approx 2.15 \times 10^9$ floating-point operations.
   * Execution on a SIMD machine: Highly optimized BLAS achieves 80% peak compute ($800\text{ GFLOP/s}$), finishing in $2.68\text{ ms}$.

2. **Strassen's Sub-Cubic Algorithm $O(N^{2.807})$**:
   * Strassen performs 7 recursive multiplications instead of 8, so the number of scalar multiplications is $7^{10} \approx 2.82 \times 10^8$ at $N=1024$—about $3.8\times$ fewer than the naive algorithm’s $N^3$ multiplications. Total floating-point operations also include the 18 matrix additions/subtractions per level; under the common 7-multiplication/18-addition count, Strassen needs about $1.97 \times 10^9$ floating-point operations at this size, only about 8% fewer than the naive algorithm’s $2N^3$.
   * Execution on the same SIMD machine: complex recursive memory layouts, matrix additions, and poor vector-register utilization lower compute efficiency to only 20% peak ($200\text{ GFLOP/s}$).
   * Wall time: $\frac{1.97 \times 10^9}{200 \times 10^9} \approx 9.9\text{ ms}$.

3. **The Mirage Breakdown**:
   * The standard algorithm sustains $800\text{ GFLOP/s}$ and finishes in $2.68\text{ ms}$.
   * Strassen sustains only $200\text{ GFLOP/s}$; at this size its operation-count advantage is too small to compensate, so it finishes in about $9.9\text{ ms}$.
   * The lesson is not that Strassen is always slower. It is that a rate or an asymptotic exponent does not determine wall time: the comparison must count the same operations, include additions and data movement, and use the same implementation efficiency. Reporting $2.82 \times 10^8$ as Strassen's total work silently drops the additions, and reporting $200\text{ GFLOP/s}$ as a performance verdict silently drops the algorithm's cost model.
   * **Rule**: Optimizing for MFLOPS, MIPS, or CPI without fixing the algorithmic work and the instruction count ($IC$) produces invalid engineering decisions.

### Exercise 5: Average throughput versus tail latency divergence

### Exercise 6: Pipeline latency, initiation interval, and throughput metrics

Distinguish latency, initiation interval, throughput, and utilization in a pipelined unit.

<ExerciseSolution hint="Differentiate between total end-to-end service delay (latency), minimum input issue separation (initiation interval), and completions per second (throughput).">

Latency is request-to-result delay; initiation interval is spacing between accepted inputs; throughput is completed results per unit time; utilization is occupied capacity relative to its maximum. A four-cycle pipeline can have four-cycle latency and one-cycle initiation interval.

</ExerciseSolution>

### Exercise 7: Benchmarking methodology critique: best-of-three reporting

</ExerciseSolution>
