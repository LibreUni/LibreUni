# Concurrency Control

Isolation names an allowed history; concurrency control is the mechanism that admits or rejects individual operations on the path to that history. A stock row can be protected with a lock, a version check, a timestamp rule, or serializable dependency tracking. Those mechanisms fail differently, so a system design must choose an error it can handle rather than merely demand “no races.”

{/* Source tracking: Locking, waits-for graphs, MVCC, and transaction-control trade-offs are synthesized from PostgreSQL's explicit-locking and transaction-isolation documentation and CMU 15-445/645 materials. Protocol traces and examples are original. */}

## Strict two-phase locking blocks unsafe orderings

> **Definition.** In two-phase locking, a transaction acquires locks during a growing phase and releases them only during a shrinking phase. A **strict** variant keeps write locks until commit or abort, preventing other transactions from reading or overwriting uncommitted writes.

| Requested lock | Existing shared | Existing exclusive |
| --- | --- | --- |
| shared | compatible | wait |
| exclusive | wait | wait |

participant "T2" as T2
T1 -> L : X(A) granted
T2 -> L : S(A) waits
T1 -> L : write A; COMMIT; release A
L -> T2 : S(A) granted

T2 cannot read T1's
uncommitted value.

Strictness is a recovery aid as well as a serializability tool: no committed transaction has observed a value that must later be undone. It can still reduce concurrency when a long transaction holds a hot row. A carefully bounded critical transaction is often more important than choosing an exotic lock mode.

### Application — lock the fact, not the screen

A reservation flow reads inventory, calls a remote payment service for 10 seconds, then decrements inventory. Should it hold an exclusive database lock during the call?

<ExerciseSolution hint="A database lock protects a local invariant; remote latency makes the protected interval unbounded.">
No. Holding the lock causes a slow external system to serialize unrelated reservations and can create deadlocks. First record an idempotent payment intent or outbox state, perform the remote call outside the inventory-critical transaction, then execute a short conditional reservation transaction. The repair is an explicit state machine, not a longer lock.

For one inventory row, the critical statement can be:

```sql
UPDATE inventory
SET available = available - :quantity
WHERE sku = :sku AND available >= :quantity;
```

The caller must inspect the affected-row count. `1` commits the reservation; `0` means the attempt lost the race or the request is no longer satisfiable and must not be treated as success. A serialization/deadlock error may be retried with the same idempotency key, bounded attempts, and backoff; a committed success must be returned from the idempotency record rather than applied twice. The predicate is necessary but not, by itself, evidence that an aggregate invariant spanning several stock rows is protected.
</ExerciseSolution>

## Deadlock is a graph, not “a slow query”

> **Invariant.** A waits-for graph has an edge $T_i \rightarrow T_j$ when $T_i$ waits for a lock held by $T_j$. A directed cycle means no member of that cycle can proceed without an abort or external intervention.

<PlantUML code={`@startuml
rectangle "T1\nholds X(order 7)\nwaits X(stock 9)" as T1
rectangle "T2\nholds X(stock 9)\nwaits X(order 7)" as T2
T1 --> T2 : waits for stock 9
T2 --> T1 : waits for order 7
note bottom of T2
Cycle: select a victim,
abort it, release its locks,
then retry safely.
end note
@enduml`} />

Detection periodically finds cycles and aborts a victim. Prevention imposes an ordering, such as always locking inventory before orders. Timeouts are simpler but can abort work that would have completed and may miss an operational root cause. Victim selection weighs age, work done, locks held, and rollback cost; it must never assume the transaction's external side effects can be undone by database rollback.

### Prediction — break the cycle

T1 holds **warehouse/5** and waits for **sku/9**; T2 holds **sku/9** and waits for **warehouse/5**. Give one prevention and one detection response.

<ExerciseSolution>
Prevention: define and enforce a global lock order, for example **(warehouse_id, sku)** sorted lexicographically, so both transactions request warehouse 5 before sku 9. Detection: record T1 → T2 and T2 → T1, abort a chosen victim, roll back its database work, then retry only if its operation uses an idempotency key or has no exposed external effect. Retrying without that boundary can duplicate messages or charges.
</ExerciseSolution>

## Protocols move the conflict check to different times

> **Worked example.** A flash-sale counter has frequent writes to one row; an analytics dashboard reads millions of rows and rarely writes. One protocol need not optimize both workloads.

| Protocol | When it rejects/confirms conflict | Strength | Cost / failure mode |
| --- | --- | --- | --- |
| strict 2PL | lock request | clear exclusion and recoverable writes | waits and deadlocks |
| timestamp ordering | operation violates timestamp order | no deadlocks | restarts under hot contention |
| optimistic control | commit-time read/write-set validation | readers run freely when conflicts are rare | expensive wasted work on conflict |
| MVCC | version visibility plus write/serializability validation | readers often avoid writer blocking | old-version retention; write skew unless stronger validation |

Timestamp ordering and optimistic control do not make conflicts disappear: they shift them into aborts. MVCC makes a snapshot readable, not necessarily serializable. A high-contention counter may prefer a single conditional update or a sharded/aggregated representation over a broad transaction that repeatedly aborts.

<details>
<summary>Why can “retry on serialization failure” still be unsafe?</summary>
The database transaction can be retried only if its inputs are still valid and it has not already produced an irreversible effect. Put an idempotency key in the committed database state, defer messages through an outbox, and make the consumer deduplicate. A retry loop without a limit, backoff, or idempotency boundary turns contention into duplication.
</details>

## Granularity must match the invariant

> **Warning.** A row lock is not a predicate lock. Locking the rows already returned by an on-call predicate may not prevent another transaction from inserting or changing a row that changes the predicate's truth.

| Invariant | Suitable shared boundary | Common false repair |
| --- | --- | --- |
| one seat never sold twice | one inventory/seat row plus conditional update | read value in application, then unconditional write |
| no duplicate username | unique constraint | rely on an application mutex |
| at least one doctor on call | serializable predicate protection or summary row | lock only the doctor being changed |
| total monthly credit ≤ limit | tenant-month summary row or serializable validation | lock each newly inserted invoice |

### Transfer — predict contention before implementing

A service records one million page views per minute and must display an approximate dashboard every minute; it also records money transfers requiring exact balances. Which path may tolerate commutative or delayed aggregation, and which cannot?

<ExerciseSolution hint="Separate the semantic requirement from the shared data shape.">
Page-view counters can be sharded, buffered, or eventually aggregated when a bounded delay/error is acceptable. Money transfers require an exact invariant at commit and need a transaction/constraint boundary that prevents overdraft. Applying exact locking to every page view wastes concurrency; applying approximate aggregation to balances changes the financial contract.
</ExerciseSolution>
