This comprehensive examination evaluates multi-tenant database systems engineering across four integrated domains: constrained relational schemas, query planning and access paths, transactional concurrency and write-ahead recovery, and distributed data replication and security.

Every material design assertion requires rigorous technical justification: an executable DDL constraint, a formal schedule trace, an `EXPLAIN` execution plan analysis, or an explicit failure contract.

## Examination Questions

<ExamQuestion id="q-db-exam-relational-ddl" points={25} title="Part A — Relational Contract, Composite Keys, and Exclusion DDL">

An equipment-lending network allows universities and research laboratories to share instruments across local facilities. An organization owns members, instruments, and sites; a booking reserves one instrument for a time interval $[starts\_at, ends\_at)$; an inspection makes an instrument unavailable over an inspection interval; and deposit payments are confirmed via external webhooks.

<PlantUML code={`@startuml
rectangle "tenant" as T
rectangle "site" as S
rectangle "equipment" as E
rectangle "booking\nstart, end, state" as B
rectangle "inspection\nblocks availability" as I
rectangle "deposit_event\nprovider event id" as D
T --> S : owns
T --> E : owns
T --> B : owns
S --> E : houses
E --> B : reserved by
E --> I : inspected
B --> D : deposit history
note right of B
Time interval and state
carry the booking contract.
end note
@enduml`} />

1. Produce complete PostgreSQL DDL for `tenant`, `equipment`, `booking`, `inspection`, and `deposit_event`.
2. Ensure that tenant IDs are scoped so that tenant 7 cannot reference equipment belonging to tenant 8.
3. Formulate the exact PostgreSQL exclusion constraint or transaction concurrency mechanism that mathematically prevents overlapping confirmed bookings for the same instrument.

<MarkingScheme points={25}>
- **Composite Key Scoping (8 pts):** All child tables (`equipment`, `booking`, `inspection`) must use composite candidate keys `(tenant_id, id)` and composite foreign keys `FOREIGN KEY (tenant_id, equipment_id) REFERENCES equipment(tenant_id, equipment_id)`. Foreign keys referencing only local `equipment_id` receive zero credit.
- **Interval Exclusion Constraint (10 pts):** Correct implementation using `btree_gist` extension:
  ```sql
  CREATE EXTENSION IF NOT EXISTS btree_gist;
  ALTER TABLE booking ADD CONSTRAINT no_overlapping_confirmed_bookings
    EXCLUDE USING gist (
      tenant_id WITH =,
      equipment_id WITH =,
      tstzrange(starts_at, ends_at) WITH &&
    ) WHERE (state = 'confirmed');
  ```
  Full credit requires noting that plain `CHECK` constraints cannot inspect sibling rows and are inadequate for interval mutual exclusion.
- **DDL Integrity and Domain Constraints (7 pts):** Valid timestamp ordering `CHECK (ends_at > starts_at)`, non-null state domains, and primary key identity declarations.
</MarkingScheme>

</ExamQuestion>

<ExamQuestion id="q-db-exam-query-portfolio" points={25} title="Part B — Query Portfolio, Zero-Safe Grouping, and Plan Cost Analysis">

An analytical reporting requirement demands tracking daily site utilization for an enterprise tenant, reporting every calendar day over the last 30 days regardless of whether any bookings occurred on that day.

1. Write a standard PostgreSQL query that outputs `(site_id, report_date, total_booked_hours, booking_count)`. The query must preserve zero-booking days with count 0 and 0.0 booked hours.
2. Formulate the predicate placement (`ON` vs. `WHERE`) required to avoid dropping calendar days when filtering for completed bookings.
3. Contrast an unclustered B-tree index scan against a sequential heap scan for a booking history query matching 1% versus 40% of table rows. Explain the cost crossover point.

<MarkingScheme points={25}>
- **Zero-Safe Date Dimension Generation (10 pts):** Uses `generate_series` for the calendar date dimension and `LEFT JOIN` onto aggregated bookings:
  ```sql
  WITH calendar AS (
    SELECT generate_series(CURRENT_DATE - INTERVAL '30 days', CURRENT_DATE, '1 day'::interval)::date AS report_date
  )
  SELECT s.site_id,
         c.report_date,
         COALESCE(SUM(EXTRACT(EPOCH FROM (LEAST(b.ends_at, c.report_date + 1) - GREATEST(b.starts_at, c.report_date))) / 3600.0), 0.0) AS total_booked_hours,
         COUNT(b.booking_id) AS booking_count
  FROM site s
  CROSS JOIN calendar c
  LEFT JOIN booking b
    ON b.site_id = s.site_id
   AND b.starts_at < c.report_date + 1
   AND b.ends_at > c.report_date
   AND b.state = 'confirmed'
  WHERE s.tenant_id = $1
  GROUP BY s.site_id, c.report_date
  ORDER BY s.site_id, c.report_date;
  ```
- **Predicate Placement Rationale (7 pts):** Explicitly identifies that placing `b.state = 'confirmed'` in `WHERE` eliminates null-extended rows, converting the outer join into an inner join. Keeping it in `ON` preserves all calendar days.
- **Physical Access Path Cost Crossover (8 pts):** At 1% selectivity, the B-tree index scan is optimal because random heap I/O touches few pages. At 40% selectivity, random heap page dereferencing exceeds the cost of a single sequential scan over all pages, causing the planner to select sequential scan.
</MarkingScheme>

</ExamQuestion>

<ExamQuestion id="q-db-exam-transactions-recovery" points={25} title="Part C — Concurrent Interleavings, Write Skew, and Outbox Idempotency">

Two laboratory administrators concurrently attempt to take instruments off-line for inspection while preserving the system invariant: *For each equipment category at a site, at least one instrument must remain available.*

1. Construct an interleaved transaction execution trace under Snapshot Isolation demonstrating how write skew occurs without lock conflicts.
2. Provide two distinct architectural solutions that guarantee preservation of the multi-row invariant under high write concurrency.
3. Detail an idempotent transactional outbox architecture that handles duplicate and delayed payment deposit webhooks from an external payment gateway.

<MarkingScheme points={25}>
- **Write Skew Execution Trace (8 pts):** Complete trace showing $T_1$ and $T_2$ reading the same snapshot with 2 available instruments, $T_1$ updating instrument $A$ to `'inspecting'` and $T_2$ updating instrument $B$ to `'inspecting'`. Because write sets $\{A\}$ and $\{B\}$ are disjoint, both commit, leaving 0 instruments available and violating the invariant.
- **Invariant Enforcement Repairs (9 pts):**
  - Option 1: True `SERIALIZABLE` isolation, tracking predicate dependencies and aborting the second committer with `40001` serialization failure.
  - Option 2: Explicit parent lock `SELECT * FROM equipment_category WHERE id = $1 FOR UPDATE;` or a dedicated category-availability counter row updated atomically.
- **Idempotent Webhook Outbox Design (8 pts):** Unique constraint on `deposit_events(provider_event_id)` to reject duplicate arrivals; local atomic transaction recording deposit state and appending an outbox message before returning HTTP 200; asynchronous worker processing outbox tasks idempotently.
</MarkingScheme>

</ExamQuestion>

<ExamQuestion id="q-db-exam-replication-security" points={25} title="Part D — Multi-Tenant Defense-in-Depth, RLS, and Failover Runbook">

An equipment network database runs with a write primary, an asynchronous streaming read replica, and daily physical WAL archives.

1. Design a defense-in-depth security architecture enforcing multi-tenant isolation across application queries, background workers, and direct reporting queries using PostgreSQL Row-Level Security (RLS).
2. Formulate the fencing and routing protocol required when promoting the read replica during primary network isolation, strictly preventing split-brain writes.
3. Write an incident response runbook for an accidental `DROP TABLE member;` executed on production, contrasting why promoting the replica fails and detailing point-in-time recovery (PITR) down to the second.

<MarkingScheme points={25}>
- **Row-Level Security Architecture (9 pts):** DDL enabling RLS on tables (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`), creating policies checking `tenant_id = current_setting('app.current_tenant_id', true)::bigint`, configuring a least-privilege non-superuser runtime role (`NOBYPASSRLS`), and testing that direct SQL queries without tenant filters return only authorized rows.
- **Failover Fencing and Split-Brain Prevention (8 pts):** Leader lease expiration or STONITH fencing revoking storage access from the isolated old primary; advancing the cluster epoch generation number upon promoting the replica; client connection pools re-pointing exclusively to the new epoch.
- **Point-in-Time Recovery Incident Runbook (8 pts):** Clarifies that streaming replication immediately duplicates the `DROP TABLE` command, making the replica useless for data recovery. Full recovery requires restoring the pre-incident physical base backup on an isolated host, setting `recovery_target_time` to 1 second before the command timestamp, replaying WAL up to the target boundary, and exporting recovered member data.
</MarkingScheme>

</ExamQuestion>
