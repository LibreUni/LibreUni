# Database Assessment

This assessment uses a different domain from the capstone: a multi-tenant equipment network. Universities and labs lend instruments through local sites. An organization owns members, equipment, and sites; a booking reserves one instrument for a time interval; an inspection can make equipment unavailable; deposits are processed by an external provider; and every tenant must remain isolated. A request may be retried, staff may work concurrently, a primary may fail, and reports may read from a delayed replica.

Do not submit disconnected diagrams, queries, or product claims. Every material assertion needs one of: an executable constraint, a trace, a plan/measurement, an explicit failure contract, or a test that could refute it.

## Assessment conditions and evidence rules

> **Definition.** A complete answer distinguishes what is **proved by a constraint**, **argued from a concurrency or failure model**, and **measured under a stated workload**. These evidence classes are not interchangeable.

| Condition | Requirement |
| --- | --- |
| time budget | 900 minutes including design, implementation/test evidence, and short defense |
| permitted tools | local DBMS documentation, SQL client, notes, and a reproducible fixture; no opaque generator as evidence |
| assumed deployment | one write primary, one asynchronous read replica, retained backups/WAL, external deposit provider |
| expected data scale | 10,000 tenants, 10 million bookings/year, skewed large tenants, 1% of equipment in inspection |
| answer format | schema/DDL, query portfolio, schedule/recovery dossier, operations/security plan, design rationale |
| grading principle | an explicit, tested limitation outranks an unsupported claim of universal correctness |

### Prediction — classify the evidence

A response says “the replica makes booking data durable” and supplies no failover test. Is the claim proved, measured, or merely asserted?

<ExerciseSolution>
It is merely asserted. An asynchronous replica can lag; a primary failure can lose acknowledged changes that have not reached the promoted replica. The response needs an explicit durability contract, replication position/failover reasoning, and a drill or documented implementation evidence. Availability architecture does not prove a durability objective by name.
</ExerciseSolution>

## Part A — relational contract and DDL

> **Invariant.** A booking belongs to exactly one tenant and one equipment item; the equipment and booking must have the same tenant. A completed booking retains the agreed deposit terms even if the current catalog policy changes.

Produce DDL for tenants, equipment, bookings, inspections, and deposit events. Use composite tenant-aware keys or an equivalent global-identity plus ownership design. Your booking line equivalent must use a composite foreign key when identifiers are tenant-local:

```sql
CREATE TABLE booking (
  tenant_id     bigint NOT NULL,
  booking_id    bigint GENERATED ALWAYS AS IDENTITY,
  equipment_id  bigint NOT NULL,
  starts_at     timestamptz NOT NULL,
  ends_at       timestamptz NOT NULL,
  state         text NOT NULL,
  PRIMARY KEY (tenant_id, booking_id),
  FOREIGN KEY (tenant_id, equipment_id)
    REFERENCES equipment (tenant_id, equipment_id),
  CHECK (ends_at > starts_at)
);

CREATE TABLE inspection (
  tenant_id     bigint NOT NULL,
  inspection_id bigint GENERATED ALWAYS AS IDENTITY,
  equipment_id  bigint NOT NULL,
  starts_at     timestamptz NOT NULL,
  ends_at       timestamptz NOT NULL,
  PRIMARY KEY (tenant_id, inspection_id),
  FOREIGN KEY (tenant_id, equipment_id)
    REFERENCES equipment (tenant_id, equipment_id),
  CHECK (ends_at > starts_at)
);
```

State what prevents overlapping confirmed bookings and an inspection/booking overlap. A CHECK constraint cannot safely query arbitrary sibling rows; use an exclusion constraint where supported, serializable/predicate protection, or a deliberately designed availability relation. Explain why the choice preserves the interval invariant.

### Application — cross-tenant counterexample

Tenant 7 and tenant 8 both use equipment ID 4. What must a booking foreign key contain to prevent tenant 7's booking from referencing tenant 8's equipment?

<ExerciseSolution hint="The key has to carry the ownership identity as well as the local ID.">
The foreign key must include **(tenant_id, equipment_id)** and reference a matching composite key on equipment, or the schema must use a globally unique equipment identifier plus a separately enforced tenant-ownership rule. A foreign key on equipment ID alone is insufficient when IDs are tenant-local; it admits an ambiguous or cross-tenant relation.
</ExerciseSolution>

## Part B — query portfolio and physical evidence

> **Example.** “Site utilization by day” has one row per tenant, site, and calendar day. To retain zero-booking days, generate the day relation and left join an aggregate at that exact grain; a WHERE predicate on the nullable right side can remove the zero rows.

Write and test these queries:

1. a tenant-scoped booking detail including equipment and current inspection status;
2. daily site utilization, including days with zero bookings;
3. the top three equipment types per tenant by booked hours over 30 days, with a stated tie policy;
4. equipment with an upcoming inspection and no confirmed conflicting booking;
5. members with no completed booking, with correct NULL behavior; and
6. duplicate, reordered, or rejected deposit-provider events.

For each query, state the input/output grain, joins that can multiply rows, NULL/empty-set behavior, and one hand-derived result fixture. For physical design, propose access paths for tenant booking history, interval conflict checks, and inspection lookups. Supply representative plan evidence and compare estimated with actual rows under a skewed tenant.

<details>
<summary>Minimum plan note</summary>
Record DBMS version, relevant settings, fixture distribution, query parameters, plan shape, estimated rows, actual rows, loops, and buffer/I/O behavior. Explain one rejected index or plan. A plan used once on an empty fixture is not evidence of scalability.
</details>

## Part C — schedule, retries, and recovery

> **Example.** Two staff members can each read “instrument free,” then create overlapping bookings for the same interval. Different booking rows do not make the interval invariant safe.

Draw a complete trace for concurrent requests A and B that overlap on one instrument. State the isolation level or explicit locking/exclusion mechanism, the conflict point, transaction outcomes, and whether either client can retry. Then extend the trace:

- A commits a booking and outbox event;
- the worker calls the deposit provider with an idempotency key;
- the process crashes after the provider receives the request but before local acknowledgement; and
- the provider later sends the same event twice and out of order.

Specify the durable state before and after each boundary. A correct answer uses a unique provider-event/idempotency constraint, legal monotonic state transitions, and a retry policy that does not create two deposits or two bookings.

### Prediction — the unsafe retry

A worker times out after calling the provider and creates a new provider request ID on retry. What invariant can fail even when every database transaction is serializable?

<ExerciseSolution>
The provider can process both request IDs and collect two deposits. Serializable database execution does not join an external provider's state into the transaction. Persist one idempotency key before the call, reuse it on retry, deduplicate incoming provider event IDs, and reconcile ambiguous outcomes by querying the provider/state record rather than inventing success or failure.
</ExerciseSolution>

## Part D — replication, security, and operations

> **Warning.** An asynchronous replica may serve stale utilization reports; it must not silently become the authoritative answer for a booking confirmation or a just-revoked tenant permission without a stated freshness contract.

Provide:

- a write/read routing rule for booking confirmation, reporting, and authorization;
- a primary-loss statement identifying acknowledged-write loss risk and the promotion/fencing behavior;
- RPO/RTO objectives plus a restore drill after a bad migration;
- least-privilege roles for runtime booking, reporting, migrations, and support;
- a tenant-isolation attack test against API input, direct runtime-role SQL, background exports, and composite references; and
- an audit-event design that records actor, tenant, target, action, outcome, time, and correlation ID without raw secrets.

### Transfer — defend one trade-off

Choose either asynchronous reporting or a cross-site deposit saga. State one user-visible intermediate state that is acceptable, one invariant that remains non-negotiable, and the reconciliation signal that detects lag or divergence.

<ExerciseSolution hint="Do not describe a trade-off as harmless; bound what can be stale and preserve the source of truth.">
For asynchronous reporting, a just-created booking may be absent from a report temporarily, while the primary booking state and tenant authorization remain authoritative. A replay position/watermark and lag alert detect delay; the reporting consumer replays idempotently. For a deposit saga, “deposit pending” may be visible, but duplicate charge prevention and legal state transitions remain non-negotiable; event IDs and reconciliation against provider status detect divergence.
</ExerciseSolution>

## Rubric and defense

> **Remark.** The rubric rewards evidence that can falsify a claim; it does not reward an unsupported list of database features.

| Criterion | Weight | Evidence expected |
| --- | ---: | --- |
| relational correctness | 25% | keys, constraints, interval/tenant counterexamples, tested DDL |
| query and physical reasoning | 20% | grain, edge-case outputs, plans, estimates, skew/write-cost argument |
| transaction and recovery reasoning | 20% | full traces, retry boundary, durable state, restore objective |
| distributed/security operations | 20% | stale/failover contract, roles/policies, attack and drill evidence |
| defense quality | 15% | one rejected alternative, one limitation, and precise response to challenge |

A short defense asks the learner to explain one plan estimate error, one schedule conflict, and one security/failure counterexample from their own artifacts. An answer that changes a guarantee after a counterexample receives credit only if it explicitly revises the client-visible contract and repair path.
