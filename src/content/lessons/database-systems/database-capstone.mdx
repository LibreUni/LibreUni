# Database Capstone

Build a database-backed marketplace for independent merchants. A merchant owns catalog items and warehouses; customers place orders; an order records immutable line prices; inventory is reserved before fulfillment; a provider sends duplicate and out-of-order payment webhooks. The target is not a collection of SQL snippets. It is an argument that the following facts survive normal operation and stated failures:

- a tenant cannot access another tenant's orders, products, inventory, or audit records;
- each order line retains the price accepted at checkout;
- inventory never becomes negative and one reservation is not counted twice;
- payment and fulfillment states advance only through legal, idempotent transitions; and
- an acknowledged order can be recovered, investigated, and measured.

## Establish the data contract before selecting tables

> **Invariant.** Every protected fact has one owner, one enforcement point, and one failure/reconciliation story. “The ORM handles it” does not identify any of those.

<PlantUML code={`@startuml
rectangle "tenant" as T
rectangle "store" as S
rectangle "product\ncurrent catalog state" as P
rectangle "warehouse_stock" as W
rectangle "orders" as O
rectangle "order_line\nimmutable unit_price" as L
rectangle "payment_event\nidempotency key + state" as E
T --> S : owns
S --> P : sells
S --> W : stocks
S --> O : receives
O --> L : contains
P --> L : price snapshot is copied
O --> E : payment history
note right of L
Order history must not change
when catalog price changes.
end note
@enduml`} />

Write a one-page domain contract before DDL. It must name entity identity, tenant ownership, deletion policy, money representation, time zone, legal state transitions, service-level targets, and values that can be stale. For example, use integer minor units or an exact numeric representation for money; state whether a product may be soft-deleted after being ordered; and distinguish a current catalog price from a historical purchase price.

### Prediction — find the missing fact

A draft schema stores order total and a foreign key to the current product price. A merchant changes a price after checkout. What report can now become false?

<ExerciseSolution>
Historical revenue and line-item invoices can change retroactively if they derive accepted price from the mutable product row. Store the accepted unit price and currency on each order line, or reference an immutable price version. If an order total is stored for performance, declare whether it is derived or atomically maintained and test it against the line sum.
</ExerciseSolution>

## Make invalid relationships unrepresentable

> **Example.** Tenant-scoped composite keys make it impossible to attach a tenant-12 order line to a tenant-13 order when the foreign key includes both tenant identity and order identity.

```sql
CREATE TABLE orders (
  tenant_id      bigint NOT NULL,
  order_id       bigint GENERATED ALWAYS AS IDENTITY,
  customer_id    bigint NOT NULL,
  status         text NOT NULL,
  created_at     timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, order_id),
  CHECK (status IN ('pending', 'paid', 'cancelled', 'fulfilled'))
);

CREATE TABLE order_line (
  tenant_id       bigint NOT NULL,
  order_id        bigint NOT NULL,
  line_no         integer NOT NULL,
  product_id      bigint NOT NULL,
  quantity        integer NOT NULL CHECK (quantity > 0),
  unit_price_minor bigint NOT NULL CHECK (unit_price_minor >= 0),
  PRIMARY KEY (tenant_id, order_id, line_no),
  FOREIGN KEY (tenant_id, order_id)
    REFERENCES orders (tenant_id, order_id)
);

CREATE TABLE warehouse_stock (
  tenant_id   bigint NOT NULL,
  warehouse_id bigint NOT NULL,
  product_id  bigint NOT NULL,
  on_hand     integer NOT NULL CHECK (on_hand >= 0),
  PRIMARY KEY (tenant_id, warehouse_id, product_id)
);
```

The code is a starting artifact, not the full schema. Add product/customer ownership foreign keys, a tenant-scoped SKU uniqueness rule, state-transition enforcement, webhook-event uniqueness, and deletion policy. A row-local CHECK cannot safely enforce an aggregate rule over arbitrary sibling rows; identify the transaction or summary relation that carries that responsibility.

### Application — prove one key choice

Give a counterexample that the composite order-line foreign key rejects but a foreign key on **order_id** alone could accept in a system where order identifiers are tenant-local.

<ExerciseSolution hint="Construct the same order number in two tenants.">
Let tenant 12 and tenant 13 both have order ID 9. A line with tenant 12 and order ID 9 must reference tenant 12's order, not whichever row an unconstrained ID lookup finds. The composite foreign key enforces that pair. A global surrogate ID can also work, but it does not remove the need to enforce tenant ownership on every related object and access path.
</ExerciseSolution>

## Design a short, recoverable order transaction

> **Definition.** The order transaction is the point where the system turns a customer request into durable local facts: order identity, immutable prices, inventory reservation, idempotency key, and an outbox event. It must not hold database locks while calling a payment provider.

<PlantUML code={`@startuml
participant "checkout client" as C
participant "order transaction" as T
database "orders + stock + outbox" as D
participant "payment worker" as W
participant "provider" as P
C -> T : request with idempotency key
T -> D : validate tenant; reserve stock; insert order/outbox
T -> D : COMMIT
W -> D : claim committed outbox record
W -> P : authorize with same key
P -> W : webhook may repeat or reorder
W -> D : legal monotonic state transition
@enduml`} />

The reservation must protect its own invariant. A conditional update of one stock row can reject a request whose quantity exceeds available stock; an aggregate reservation across warehouses needs a defined lock/serialization boundary. Store the client idempotency key under a uniqueness rule so retries converge on one order. The provider call is external: use the durable outbox and a webhook event ID to deduplicate it.

### Worked trace — competing last-unit requests

1. T1 conditionally reserves the last unit and commits.
2. T2 executes the same conditional update after T1; its affected-row count is zero.
3. T2 records or returns a rejection without creating a successful order state.
4. A committed outbox worker can retry provider communication with the same idempotency key.

<details>
<summary>What evidence must the concurrency test retain?</summary>
Keep initial fixture state, transaction timestamps/order, statement outcomes, isolation setting, locks or serialization errors, final rows, and emitted outbox IDs. A final stock value alone cannot distinguish a correct rejection from a lost update.
</details>

## Measure the workload and physical design

> **Warning.** An index, partition, or replica is a workload claim. Do not add one because it is familiar; name the query, cardinality, write cost, and changed-workload counterexample.

| Workload | Candidate evidence | Required counterexample |
| --- | --- | --- |
| tenant order history | plan for tenant/time range; index on tenant then time | tenant with 90% of all orders |
| stock lookup/reservation | primary key or narrow tenant/warehouse/product path | concurrent requests for same SKU |
| daily revenue | grain-first aggregate and calendar left join | day with zero sales, duplicate lines |
| webhook processing | uniqueness lookup on provider event ID | duplicate and out-of-order event |
| retention | time partition/pruning plan and drop policy | tenant-only query that cannot prune |

Seed enough data to expose selectivity, skew, and cache behavior. Record database version, schema/index definition, data generator distribution, concurrency level, warm-up, query text, plan, estimated and actual rows, and latency distribution. A single low elapsed time is not a benchmark and a single plan screenshot is not a physical-design argument.

### Transfer — reject a seductive index

A proposal adds a wide covering index on every order column to speed a nightly export. The table receives continuous inserts and status updates. What evidence would justify or reject it?

<ExerciseSolution>
Compare the export plan and buffer/I/O behavior with and without the index, then measure insert/update throughput, index size, vacuum/replication cost, and cache pressure under representative concurrency. If the export reads most rows once nightly, a sequential or partition-aware plan may dominate. The index earns its cost only when measured read benefit exceeds the continuing maintenance cost for the stated workload.
</ExerciseSolution>

## Rehearse recovery, replication, and security

> **Definition.** A production guarantee is incomplete without an operational test: a backup must restore, a failover must fence stale writers, and a least-privilege policy must reject a real adversarial request.

| Drill | Pass evidence |
| --- | --- |
| bad migration | isolated point-in-time restore, invariant checks, measured RPO/RTO |
| primary loss | promotion path, client fencing/epoch behavior, acknowledged-write loss statement |
| replica lag | read-after-write behavior and stale-result contract |
| leaked runtime credential | revocation/rotation time, narrowed replacement role, audit review |
| tenant attack | altered tenant ID, direct runtime-role query, composite-FK and policy rejection |
| negative inventory alert | freeze affected workflow, trace first invariant break, reconcile from order/audit facts |

Write an incident runbook for each drill: detection, containment, evidence preservation, integrity check, recovery action, client communication boundary, and regression test. A replica is not a backup after a bad delete; a backup is not security control if its archive role is broadly shared.

### Capstone defense prompt

Choose one intentional relaxation: asynchronous search indexing, a delayed analytics aggregate, time partitioning, a cross-service saga, or a readable replica. State the invariant it does **not** preserve immediately, the visible state it permits, the repair/reconciliation process, and the test that detects a broken implementation.

<ExerciseSolution hint="A strong answer names one bounded fact that may lag and a separate fact that still cannot be violated.">
A satisfactory defense distinguishes the relaxed projection from the authoritative transaction. For example, search may lag after an order commit, but the order row and tenant authorization remain authoritative; an idempotent event consumer replays missed work and a watermark/lag alert detects delay. Do not call the relaxation safe without an observable bound, source of truth, and repair path.
</ExerciseSolution>

## Deliverables and review rubric

> **Remark.** The deliverables are evidence containers: a diagram alone, a fast query alone, or a backup policy alone cannot establish the system contract.

Submit a repository or archive that runs from an empty database and includes:

1. domain contract, ER/domain diagram, DDL, migration plan, and seed fixture;
2. query portfolio with declared result grain, expected outputs, adversarial NULL/duplicate/tenant tests, and representative plans;
3. transaction/schedule dossier for inventory, idempotency, webhook order, and one aggregate invariant;
4. physical-design and benchmark report with workload assumptions and a rejected alternative;
5. recovery, replication, security, and incident-runbook evidence; and
6. a concise design defense that identifies one limit the system intentionally accepts.

| Criterion | Weight | Full-credit evidence |
| --- | ---: | --- |
| semantic and tenant correctness | 25% | executable constraints, counterexamples, and tested ownership |
| query/physical reasoning | 20% | measured plans plus write-cost and skew evidence |
| concurrency and recovery | 20% | traces, failure injection, safe retries, restore drill |
| security and operations | 20% | least privilege, attack tests, audit/rotation/runbooks |
| clarity of trade-offs | 15% | rejected alternatives and explicit assumptions |
