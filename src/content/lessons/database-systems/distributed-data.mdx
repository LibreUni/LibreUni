A client sends “transfer $100” and times out. The service cannot infer failure: the request may have reached a leader, committed on a quorum, committed locally but not replicated, or never left the client. Distribution adds uncertain communication to already difficult transaction boundaries. Start with the fact that must remain true and the failures the system promises to handle.

## A consistency claim must name its observer and failure

> **Definition.** A consistency contract states what operation may observe relative to which completed operations, under an explicit failure and communication model. “Eventually consistent” without a convergence target, stale-read bound, or conflict rule is not a useful contract.

| Product fact | Unsafe observation | Plausible contract | Availability consequence |
| --- | --- | --- | --- |
| transfer never spends money twice | client sees two accepted debits | one ordered, durable decision plus idempotency | may reject/wait during leader loss |
| product search catches up | new item missing briefly | asynchronous indexed projection | stale result is visible and repairable |
| tenant authorization revocation | revoked user still reads data | strongly ordered or bounded-stale authorization path | read may wait/fail during partition |
| analytics counter | dashboard lags by a minute | convergent aggregate with stated window | value may be temporarily approximate |

A network partition does not prove which side contains the newest value. A timeout is an ambiguous outcome, so a client needs an operation ID and a status lookup or idempotent retry rather than a second independent request.

### Prediction — client action after timeout

A payment request with idempotency key K times out. Which reply is safer: “failed,” “succeeded,” or “unknown; check K”?

<ExerciseSolution>
“Unknown; check K” is the honest reply until the durable system of record resolves it. Retrying with the same key can be safe if the server persists and deduplicates K; retrying with a new key can create a second charge. A false success misleads the client, while a false failure can trigger duplicate work.
</ExerciseSolution>

## Quorum arithmetic proves only intersection

<MathStatement id="quorum-intersection" kind="proposition" title="Read/write quorum intersection">
For N replicas, a read quorum R and write quorum W intersect when $R + W > N$. Two write quorums intersect when $2W > N$. These inequalities establish shared replica membership; they do not alone establish leader fencing, version ordering, durability of a particular implementation, or linearizability.
</MathStatement>

### Worked example — choose R and W

With N = 3 and W = 2, choose the smallest R that intersects every write quorum. Then state one thing the result still does not prove.

<ExerciseSolution hint="Use R + W > N, then list a protocol property outside set arithmetic.">
R = 2, because 2 + 2 > 3. A read of two replicas intersects a completed two-replica write, but it still needs version/term rules to distinguish a newest value from a stale or divergent response. It also says nothing about whether a client received an acknowledgement before the intended data-loss boundary.
</ExerciseSolution>

## Coordination has a blocking and repair cost

> **Example.** An order service and a warehouse service each own a database. “Create order and reserve stock” can be treated as one distributed atomic decision, or as local durable steps with a compensating cancellation path. The observable failure behavior differs.

| Design | Success rule | Partition / participant failure | Repair obligation |
| --- | --- | --- | --- |
| single database transaction | one local commit | one local failure domain | normal recovery |
| two-phase commit | coordinator collects prepare votes then decides | prepared participants can block awaiting decision | durable decision log and recovery protocol |
| saga / outbox | local commits advance an explicit state machine | temporary partial business state is visible | compensations, retries, and reconciliation |
| asynchronous projection | source event commits first | read model can lag | replay, watermark, and idempotent consumer |

Two-phase commit is not “a transaction across anything”: participants must durably prepare, a coordinator records a decision, and failure can leave prepared participants unable to decide alone. A saga makes partial progress explicit. It is suitable only when domain-level compensation can restore an acceptable business state; reversing a shipment after delivery is not the same as undoing a row update.

### Transfer — avoid a fake atomicity claim

A system writes a financial ledger in region X and sends a warehouse reservation request to region Y. Region Y is unreachable after the ledger commit. Choose a design and state what the customer can see.

<ExerciseSolution>
Use a durable outbox/state machine: record a pending reservation with the ledger transaction, retry the Y request idempotently, and expose “payment authorized, fulfillment pending” until the reservation succeeds or a defined compensation/refund occurs. Claiming an atomic cross-region success after X commits is false without a coordinating protocol and its availability cost. The visible intermediate state is a product decision, not a technical accident.
</ExerciseSolution>

## Distributed commit needs a durable decision, not a wish

{/* Source tracking: Commit coordination and its failure modes are synthesized from Gray and Lamport (2006); TrueTime and external consistency are synthesized from Corbett et al. (2012). */}

Two-phase commit (2PC) makes a set of participants agree on one outcome. In the **prepare** phase the coordinator asks each participant to durably record its vote and the resources it will need to commit. If every participant votes yes, the coordinator durably records **commit** and then tells them to commit; if any votes no, it records **abort**. A participant that has prepared must retain its locks and its ability to commit until it learns the decision.

| Failure | What remains true | What the system cannot do alone |
| --- | --- | --- |
| participant crashes after voting yes | its prepared state is durable | decide whether the coordinator chose commit or abort |
| coordinator crashes after recording commit | the decision is durable | notify unreachable participants until it recovers |
| coordinator crashes before recording a decision | no decision exists | force prepared participants to commit |
| network partition isolates a prepared participant | it cannot safely release locks | make progress without the decision |

The blocking case is fundamental to 2PC: prepared participants may hold locks while they wait for the coordinator. Three-phase commit removes some blocking under stronger assumptions, but adds rounds and still assumes bounded or predictable failures. A saga avoids prepared locks by making intermediate state visible, at the cost of requiring domain compensation.

Consensus protocols such as Paxos and Raft replicate a **log**, not a collection of independent row copies. A write is committed when a leader has replicated it to a quorum and the entry is ordered in the log; a new leader must contain every committed entry. Leader terms or epochs fence stale leaders so an old leader cannot acknowledge a write after a new one has been elected.

> **Invariant.** A quorum acknowledgement is evidence of replication, not of external consistency. The value a client reads may still depend on which replica answers and what ordering rule the client requires.

Spanner adds a physical ordering assumption: TrueTime exposes a bounded uncertainty interval for the local clock. A transaction waits out that uncertainty before committing, so timestamps assigned to committed transactions respect real-time order across regions. The result is **external consistency**, stronger than snapshot isolation, paid for with commit-wait latency and dependable clock infrastructure. Naming the assumption is part of the contract; a system without bounded clock uncertainty cannot copy the proof.

### Transfer — choose the commit boundary

A cross-region transfer must never be visible as two independent halves, and the service cannot tolerate blocking during a coordinator failure. Which property must it give up, and what should it tell the client while a decision is pending?

<ExerciseSolution hint="A non-blocking design cannot also promise a single instantaneous cross-region commit without a stronger coordination substrate.">
It must give up either non-blocking atomic commit or the claim of an instantaneous single decision. A durable outbox plus idempotent steps can keep serving, but the client sees an intermediate state such as “authorized, pending settlement.” A consensus-backed ledger can provide an ordered decision, but it may wait for a quorum and must expose a truthful pending status on timeout. Claiming both non-blocking operation and atomic cross-region success without naming the coordination mechanism is false.
</ExerciseSolution>
