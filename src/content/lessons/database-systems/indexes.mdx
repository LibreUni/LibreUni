# Indexes

A support query asks for the newest 50 failed deliveries for tenant 12. A table scan is correct, yet reading millions of unrelated rows is not a design. An index can make the request selective, but every new delivery and status update must also maintain its entries. The central question is not “should this column be indexed?” but “which ordered search space does this workload need, and what update work buys it?”

## B+ tree navigation is an ordering proof

> **Definition.** A B+ tree keeps keys sorted in page-sized nodes. An internal separator partitions key ranges; leaves contain search keys and tuple references and are linked for ordered scans. Balance means every leaf has the same depth.

<PlantUML code={`@startuml
rectangle "root\n< (12, 2025-01-01) | ≥ (12, 2025-01-01)" as R
rectangle "leaf A\n(11, …)\n(12, 2024-12-31)" as A
rectangle "leaf B\n(12, 2025-01-01)\n(12, 2025-01-02)\n(13, …)" as B
R --> A : lower range
R --> B : target range
A --> B : leaf-next
note right of B
Range scan follows leaves
without returning to root.
end note
@enduml`} />

To find `(12, 2025-01-02)`, compare it with the root separator, choose leaf B, then search that leaf. If B is full on insertion, split it into two sorted leaves and propagate a separator upward. The split changes navigation, not query meaning. A correct implementation ensures every key remains in exactly one leaf and every separator directs search to a child whose range contains the key.

### Prediction — separator choice

Leaves after an insert must be `[4, 7]` and `[9, 13]`. Which value can be a separator if the parent routes keys less than the separator left and all other keys right?

<ExerciseSolution hint="Use the smallest key on the right leaf under this comparison convention.">
`9` works: 4 and 7 route left; 9 and 13 route right. `7` would route 7 right even though it remains left, unless the comparator convention were changed consistently. Separator values are routing contracts, not decorative summaries.
</ExerciseSolution>

## Composite keys have a left-to-right geometry

> **Invariant.** An index on `(tenant_id, created_at, id)` is ordered first by tenant, then by time *within an equal tenant*, then by `id` within an equal tenant and time.

| Query shape | Can `(tenant_id, created_at, id)` navigate directly? | Why |
| --- | --- | --- |
| `tenant_id = 12 ORDER BY created_at, id` | Yes | equality fixes the leading group; suffix order is already present |
| `tenant_id = 12 AND created_at >= t` | Yes | starts at one tenant/time boundary and scans forward |
| `created_at >= t` for all tenants | Usually no | matching times are scattered across tenant groups |
| `tenant_id = 12 ORDER BY id` | Not generally | `created_at` intervenes before `id` order |

This is lexicographic order, not a slogan about “leading columns.” It also explains why a query returning most of a table can prefer a sequential scan: an index may locate every tuple but require many scattered heap reads. Clustering, cache state, visibility, and selectivity decide the trade.

### Worked application — an access path proposal

For:

```sql
SELECT id, created_at, error_code
FROM delivery
WHERE tenant_id = $1 AND status = 'failed'
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

an index such as `(tenant_id, status, created_at DESC, id DESC) INCLUDE (error_code)` can align equality predicates with output order and may avoid a sort. It is useful only if failed rows per tenant are selective enough and the added write/space cost is justified. If `status` changes often, the same index can amplify a hot write path.

<details>
<summary>What makes this “covering” claim conditional?</summary>
All selected values may be present in the index, but an MVCC engine can still need a heap or visibility-map check before returning a tuple. An index-only scan is a plan opportunity, not a guarantee that heap I/O is zero.
</details>

## Derived structures must preserve query semantics

> **Warning.** An index is not the logical source of truth. It is correct only if visible rows required by its predicate have entries and each entry resolves to a row that still satisfies its indexed condition.

A partial index stores only rows satisfying a fixed predicate, for example `WHERE status = 'failed'`. The optimizer may use it only when it can establish that the query condition implies the partial predicate. An expression index on `lower(email)` similarly requires matching normalization, collation, and expression semantics. A raw `email` index does not automatically answer a transformed predicate.

Hash indexes target equality lookups; they do not yield the ordered leaf traversal required by a range. A Bloom filter answers a narrower question: it may safely say “definitely absent,” but “possibly present” still requires another access path. Treating a filter's positive result as a row location is a logical bug.

### Transfer — a subtle uniqueness requirement

Each tenant may register an email once, case-insensitively. Tenants may share the same spelling. Propose the key and state two details that could invalidate a naive implementation.

<ExerciseSolution hint="The uniqueness domain contains both tenant identity and the agreed normalization rule.">
Use a unique index or constraint over `(tenant_id, lower(email))` only after specifying the normalization/collation contract. The naive `UNIQUE(email)` wrongly forbids different tenants; `UNIQUE(tenant_id, email)` can allow case variants when the product treats them as equal. Unicode normalization and whether NULL emails are allowed must be specified as well, because DBMS NULL uniqueness behavior varies.
</ExerciseSolution>

## Maintenance cost belongs in the design

> **Example.** Inserting one delivery row may insert one heap record plus entries in the primary key, foreign-key support, status/time, and audit indexes. Updating an indexed status can remove and add an entry even when the business update looks small.

| Proposal | Read benefit | Write and recovery cost | Decision evidence |
| --- | --- | --- | --- |
| key index on `delivery(id)` | direct point lookup | one entry per insert; split/vacuum work | point lookup frequency and uniqueness need |
| wide covering support index | fewer heap visits for support query | larger entries, cache pressure, status-update work | `EXPLAIN (ANALYZE)` plus write benchmark |
| partial failed-delivery index | small hot subset | predicate transitions maintain membership | failed-row fraction and query implication |

Measure representative reads and writes, including warm and cold-cache assumptions. A plan estimate is evidence about a model, not proof: compare estimated and actual cardinalities, then inspect skew or stale statistics before adding an index merely to silence a slow example.

### Prediction — reject an index

A monthly archive table is append-only, queried once nightly by `WHERE created_at >= current_date - interval '30 days'`, and 95% of rows match. Should a B-tree on `created_at` be the default answer?

<ExerciseSolution>
Not automatically. The predicate returns almost the entire relation, so a sequential scan can be cheaper than index navigation plus widespread tuple access. Time partitioning, zone maps/segment metadata, or a sequential aggregate may fit the actual workload better. The decisive evidence is selectivity and physical locality, not the existence of a date predicate.
</ExerciseSolution>
