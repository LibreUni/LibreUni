# Query Execution and Optimization

`SELECT` says what rows are required, not how to obtain them. For a tenant's failed deliveries, a database may scan a table, probe an index, hash a small relation, sort before aggregation, or stream groups in order. All correct plans return the same logical bag under the same SQL semantics; their intermediate cardinalities, memory pressure, and I/O differ radically.

<details>
  <summary>Readiness refresh: selectivity and simple estimates</summary>

  Selectivity is the fraction of rows that survive a predicate: a 5% predicate on 10,000 rows first estimates 500 rows. For two predicates, multiplying selectivities is an **independence assumption**, not a fact about correlated data. Tree height, hash access, and page I/O use the same bounded models introduced in storage; every estimate below names what it ignores.
</details>

## An operator tree carries relations upward

> **Definition.** A physical plan is an operator tree: each node consumes one or more streams of rows, produces a stream with a defined schema and multiplicity, and pays a resource cost under stated assumptions.

Read the tree bottom-up. The `orders` access produces rows; the filter reduces them; the join attaches customer attributes; the aggregate changes the grain to one row per customer. “Hash join” alone does not establish quality. Building a hash table on 10,000 filtered orders can fit memory; building one on 500 million customers may spill or fail the cost budget.

### Prediction — join result grain

`orders` has one row per order and `order_line` has one row per line. A join on `order_id` followed by `SUM(line.amount)` has what grain immediately before the aggregate?

<ExerciseSolution hint="A one-to-many join repeats the order fields once per matching line.">
The joined stream has one row per matching order line, not one per order. Grouping by customer then sums line amounts at customer grain. If an order-level amount is joined and summed after this join, it is duplicated once per line; aggregate it at order grain first or use a different construction.
</ExerciseSolution>

## Cost begins with cardinality, not a magic constant

<MathStatement id="plan-cardinality" kind="proposition" title="A first selectivity estimate">
For a relation $R$ with $|R|$ rows and a predicate with selectivity $s$, a simple estimate is $|\sigma_p(R)| \approx s|R|$. For an equijoin, an independence-based first estimate is often $|R \bowtie S| \approx |R||S|/\max(V(R,a), V(S,a))$, where $V(R,a)$ is the distinct-count estimate. These are models to test, not laws of the data.
</MathStatement>

Suppose `orders` contains 10,000,000 rows and 1% are failed. The filter estimate is 100,000 rows. If 80% of failures belong to one enterprise tenant, treating `tenant_id` and `status` as independent can underestimate that tenant's result by nearly two orders of magnitude. That error can turn a nested loop chosen for a tiny outer input into repeated expensive probes.

Vary selectivity and page count, then predict before revealing a plan. The model exposes a bounded scan/index/join trade-off; it does not claim a real DBMS uses its exact coefficients. Its value is making the hidden assumption visible: a selective access path becomes worse when the matching set approaches a scan.

### Worked calculation — two plans

Assume a 1,000-page `orders` table, a 20-page `customer` table, and a predicate that returns 2 orders. A nested-loop plan that probes an index for two customers may be excellent. If stale statistics estimate 2 but actual rows are 200,000, the same plan can perform 200,000 probes; a hash join with a 20-page customer build may dominate. The logical query did not change. The cardinality claim did.

<details>
<summary>What evidence distinguishes a bad estimate from a bad algorithm?</summary>
Compare `EXPLAIN` estimates with `EXPLAIN ANALYZE` actual rows at the first divergent node. If the estimate is wrong, inspect stale statistics, skew, correlation, parameter-sensitive values, and predicate semantics. If estimates are sound but the cost model still chooses poorly, measure its I/O, memory, and cache assumptions before forcing a plan.
</details>

## Physical algorithms expose different failure modes

> **Example.** A merge join needs both inputs ordered on the join key; it can exploit matching indexes or pay to sort. A hash join needs a build side that fits its memory budget or partition/spill logic. A nested loop needs a small outer input or a cheap indexed inner probe.

| Operator choice | Strong case | Dangerous assumption | Observable warning |
| --- | --- | --- | --- |
| Sequential scan | high selectivity loss / most pages needed | index navigation is always faster | index plan visits most heap pages randomly |
| Index scan | few qualifying rows, useful order | predicate matches an index range | actual rows approach table cardinality |
| Hash join | modest build input, equality join | build fits memory | batches/spills or unexpectedly huge build |
| Merge join | inputs ordered or cheap to sort | order cost is recovered later | both inputs sort only for one join |
| Nested loop | tiny outer plus indexed inner | outer cardinality is truly tiny | probes explode after a misestimate |

### Application — predicate placement changes both semantics and cost

An outer join must retain every customer, even those with no failed order. Where does `order.status = 'failed'` belong: in `WHERE` after a left join or in the join condition / filtered right input?

<ExerciseSolution>
Place it in the right input or `ON` condition. A `WHERE order.status = 'failed'` filter after the left join removes null-extended rows and turns the result into an inner-join-like result. The optimizer may push a semantically valid filter down, but only after preserving outer-join null behavior. Correct cardinality starts with correct semantics.
</ExerciseSolution>

## Plans must be read as conditional evidence

> **Warning.** A low estimated cost is not elapsed time and a plan is not a proof that the query is correct. Cost units compare alternatives under a DBMS model; actual timing depends on cache state, concurrency, hardware, and configuration.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, count(*)
FROM orders
WHERE tenant_id = 12 AND status = 'failed'
GROUP BY customer_id;
```

For each node, record estimated rows, actual rows, loops, buffer reads/hits, and whether the node changed the expected grain. Test an empty tenant, a tenant with skewed failed rows, and a fresh-cached versus warm-cached run. A forced index plan is a diagnostic experiment, not a general remedy.

### Transfer — an estimate that lies politely

A table has independent-looking global statistics: 1% `status='failed'`, 1% `region='north'`. In north, however, 90% of rows have failed. A query filters both predicates. What should the optimizer or designer learn from a large estimate error?

<ExerciseSolution hint="The missing fact is correlation, not arithmetic competence.">
Global independence predicts about $0.01\%$ of rows, while the north subset predicts about $0.9\%$ if north is 1% of the table. The response can include richer/multivariate statistics, a partition-aware estimate, a targeted index only if the workload supports it, and a regression query against the skew. Hard-coding one plan hides the data-distribution cause.
</ExerciseSolution>
