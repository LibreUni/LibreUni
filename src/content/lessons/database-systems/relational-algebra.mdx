# Relational algebra: derive a query before SQL

Relational algebra gives a compact way to answer “what rows?” before a SQL dialect, a query plan, or a UI obscures the question. Its greatest practical use is not memorizing symbols. It is exposing a missing condition, an incompatible difference, or a changed result grain early.

> **Definition.** An algebra expression takes one or more relations as input and produces another relation. Name the output schema and grain after every nontrivial operator; this is how you notice an accidental duplication or lost attribute.

{/* Source tracking: The operator-based relational query model is synthesized from Codd’s 1970 relational model paper and the relational-algebra treatment in Ramakrishnan and Gehrke’s *Database Management Systems*. */}

## The operators we will use

<MathStatement id="ra-operators" kind="definition" title="Set-relational operators">

For a relation $R$ and predicate $\theta$:

$$
\sigma_{\theta}(R) = \{t \in R \mid \theta(t)\}
$$

- **Selection** $\sigma_{\theta}(R)$ keeps tuples satisfying $\theta$.
- **Projection** $\pi_{A,B}(R)$ keeps named attributes and removes duplicate tuples under set semantics.
- **Rename** $\rho_{new\_name \leftarrow old\_name}(R)$ changes a relation or attribute name so an expression is well-formed.
- **Product** $R \times S$ pairs every tuple of $R$ with every tuple of $S$.
- **Join** $R \bowtie_{R.a = S.a} S$ is a selected product with compatible joined attributes.
- **Difference** $R - S$ keeps tuples in $R$ that are not in $S$; $R$ and $S$ must have compatible schemas.
</MathStatement>

## Trace a query, not just its notation

Use these fixed relations for term `2026S`.

| `Student` |  |  | `Required` |  | `Enrollment` |  |  |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `sid` | `cohort` |  | `cid` |  | `sid` | `cid` | `term` |
| Ada | first_year |  | C101 |  | Ada | C101 | 2026S |
| Bo | second_year |  | C201 |  | Ada | C201 | 2026S |
| Cy | first_year |  |  |  | Bo | C101 | 2026S |
|  |  |  |  |  | Bo | C201 | 2025F |
|  |  |  |  |  | Cy | C101 | 2026S |

> **Worked example.** “Which students are enrolled in C101 in 2026S?” starts with selection, then projection:

$$
\pi_{sid}\bigl(\sigma_{cid = \text{'C101'} \land term = \text{'2026S'}}(Enrollment)\bigr)
= \{\text{Ada}, \text{Bo}, \text{Cy}\}.
$$

The selected relation still has grain “one enrollment.” The projected result has grain “one student who meets the condition.” That change is intentional.

### Predict the intermediate result

What is the schema and tuple set of

$$
\pi_{sid,cid}\bigl(\sigma_{term = \text{'2026S'}}(Enrollment)\bigr)?
$$

<ExerciseSolution hint="Selection leaves all attributes in place; projection then drops only `term`.">

Its schema is `(sid, cid)` and its tuples are `(Ada, C101)`, `(Ada, C201)`, `(Bo, C101)`, and `(Cy, C101)`. The result says that a student is enrolled in a course during the chosen term; it no longer states the term, so do not reuse it for a multi-term question without rebuilding the scope.
</ExerciseSolution>

## “All required courses” is a missing-pair problem

The word **all** often tempts people into a vague division operator. Derive it by enumerating what should exist and subtracting what is absent.

> **Example.** Find students who are enrolled in every required course in `2026S`. First make every expected student/course pair. Then remove pairs that have no matching enrollment.

$$
\begin{aligned}
Enrolled &= \pi_{sid,cid}\bigl(\sigma_{term = \text{'2026S'}}(Enrollment)\bigr) \\
Expected &= \pi_{sid}(Student) \times Required \\
Missing &= Expected - Enrolled \\
Answer &= \pi_{sid}(Student) - \pi_{sid}(Missing)
\end{aligned}
$$

`Expected` and `Enrolled` both have schema `(sid, cid)`, so the difference is defined. For the data above, `Missing` contains `(Bo, C201)`, `(Cy, C201)`; `Answer` is `{Ada}`.

> **Invariant.** Before taking a union, intersection, or difference, verify compatible schemas and attribute meanings. Two columns both named `id` are not automatically compatible if one is a student identifier and the other is an offering identifier.

### Apply the derivation

The dean asks for students who are enrolled in every required course **and** are in the `first_year` cohort. Where should the cohort condition go: in `Enrolled`, `Expected`, or the final answer?

<ExerciseSolution hint="The cohort condition restricts who is required to satisfy all pairs, not what counts as a matching enrollment.">

Restrict the candidate students before forming expected pairs:

$$
Eligible = \sigma_{cohort = \text{first\_year}}(Student), \qquad
Expected = \pi_{sid}(Eligible) \times Required.
$$

Then use the same `Missing` and final subtraction pattern with `Eligible`. Filtering only the final answer can be correct for a simple output filter, but it unnecessarily constructs missing pairs for students who were never candidates and obscures the requirement.
</ExerciseSolution>

## A rewrite needs stated assumptions

Algebra helps explain why an optimizer can sometimes move work earlier.

<MathStatement id="ra-pushdown" kind="proposition" title="Safe inner-join selection pushdown">

For set relations, an inner join, and a two-valued predicate $\theta_R$ that mentions only attributes of $R$:

$$
\sigma_{\theta_R}(R \bowtie_{R.a = S.a} S)
= \sigma_{\theta_R}(R) \bowtie_{R.a = S.a} S.
$$
</MathStatement>

<MathProof id="ra-pushdown-proof" for="ra-pushdown" collapsible>

A joined tuple survives the left expression exactly when its `R` component satisfies $\theta_R$. Because the predicate reads no `S` attribute, filtering `R` first removes exactly those same joined tuples. The statement does not claim the two expressions have equal cost, nor does it cover outer joins or SQL's three-valued predicate behavior.
</MathProof>

> **Counterexample.** With a left outer join, moving a predicate about the right relation from `WHERE` into a pre-join filter can preserve unmatched left rows that the original `WHERE` condition removes. For example, if `R` has one row and `S` has none, `WHERE S.flag = 'Y'` removes the null-extended row after the join. The same condition inside the right input still lets the left outer join emit it. The expressions are not interchangeable.

> **Warning.** SQL normally uses bag semantics and three-valued logic. An algebra law stated for sets and two-valued predicates is a reasoning aid, not permission to apply it blindly to a SQL query.

### Check a proposed rewrite

An engineer changes

$$
\sigma_{R.term = \text{'2026S'}}(R \bowtie_{R.sid = S.sid} S)
$$

to

$$
\sigma_{R.term = \text{'2026S'}}(R) \bowtie_{R.sid = S.sid} S.
$$

List the three facts you would check before accepting the rewrite.

<ExerciseSolution hint="Match the proposition's assumptions one by one.">

Check that the join is inner, the predicate reads only `R` attributes, and the intended semantics support the stated selection law (including how duplicate rows and `NULL` values are handled in the actual SQL dialect). Also confirm that `term` means the same thing at this point in the expression; an alias or prior rename can change that fact.
</ExerciseSolution>

## Transfer task: derive, then validate

> **Remark.** A universal requirement becomes an ordinary difference once you make the expected pairs explicit. Keep the candidate population, required set, and time scope visible in the expression.

Define `Student(sid)`, `Course(cid)`, `Taken(sid, cid, term)`, and `Core(cid)`. Derive an expression for students who took every core course in `2026S` but no non-core course in that term. State the schema of each difference operand. Then test your expression against a three-student, two-course dataset of your own.

<ExerciseSolution hint="Reuse expected-minus-completed for the “every core” part. Build a second set of students with a non-core enrollment, then subtract it.">

First project the current-term rows to the exact pair used by the expected relation: $Completed = \pi_{sid,cid}(\sigma_{term=\text{'2026S'}}(Taken))$. The projection is essential: `term` is a filter attribute, not part of the `(sid,cid)` difference schema. Then let $Expected = \pi_{sid}(Student) \times Core$, and $AllCore = \pi_{sid}(Student) - \pi_{sid}(Expected - Completed)$. For non-core courses, first make a course relation compatible with `Core`, such as $NonCore = \pi_{cid}(Course) - Core$, then compute $HasNonCore = \pi_{sid}(Completed \bowtie NonCore)$. The answer is $AllCore - HasNonCore$. In the two key differences, `(sid, cid)` is compatible with `(sid, cid)` and `(cid)` is compatible with `(cid)`.
</ExerciseSolution>
