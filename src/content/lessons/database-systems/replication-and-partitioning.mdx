# Replication and Partitioning

A replica that is one minute behind can be an excellent reporting target and a dangerous authorization target. A partitioned table can make retention cheap and still leave a tenant-hotspot unsolved. Replication and partitioning change where data lives and when it becomes visible; neither silently preserves every single-node guarantee.

{/* Source tracking: Replication behavior and partitioning concepts are synthesized from PostgreSQL documentation; leadership/fencing terminology is cross-checked against the Raft paper. Workload matrices and migration traces are original. */}

## Replication changes the meaning of acknowledgement

> **Definition.** Replication copies committed state or log records to other nodes. A write's durability claim depends on which copies must acknowledge before the client is told success and which failures are in scope.

| Mode | Client acknowledgement | Read behavior | Primary risk |
| --- | --- | --- | --- |
| asynchronous | local durable primary commit | replicas can lag | acknowledged tail can be lost on failover |
| synchronous to one or more standbys | required standby acknowledgement as configured | some reads may still be stale | higher latency / reduced write availability |
| logical/event projection | source commit before consumer applies event | explicit lag and replay boundary | duplicate or delayed consumer work |

A replica should report both replication position and lag relative to a named source. “Healthy” cannot mean only that its process is running. A read-after-write API must either route to a sufficiently caught-up replica, route to the writer, wait with a bound, or return a clearly stale contract.

### Prediction — a false zero-loss claim

A primary acknowledges a write locally, then crashes before its asynchronous replica receives it. The replica is promoted. What happened to the client-observed write?

<ExerciseSolution>
It can be lost despite the former primary's acknowledgement. The deployment promised local durable commit, not durable replication to the promoted node. Calling this “zero data loss” confuses storage durability with a failover durability contract. Synchronous acknowledgement, durable client retry records, or a revised product guarantee changes the claim and its latency/availability cost.
</ExerciseSolution>

## Promotion needs fencing against stale writers

> **Invariant.** At most one authority may accept writes for a replication epoch. A promoted leader must reject requests carrying an old lease, term, or fencing token, and clients must stop reaching the former leader.

<PlantUML code={`@startuml
participant "client" as C
participant "old primary, epoch 17" as O
participant "new primary, epoch 18" as N
participant "routing control" as R
R -> N : promote with epoch 18
R -> C : route writes to epoch 18
C -> O : delayed write with epoch 17
O -> O : reject / fenced
C -> N : retry with epoch 18
note right of N
Promotion without fencing can
permit two write authorities.
end note
@enduml`} />

Failover is not finished when a process starts accepting traffic. Fencing prevents an isolated former primary from continuing to accept writes that later conflict with the new authority. The precise technique may be leases, terms, a strongly consistent configuration store, or a database-specific mechanism; the required property is refusal of stale authority.

### Application — read your own write

A client creates an order, then reads it from an asynchronous replica. Give two correct API behaviors.

<ExerciseSolution>
Route the immediate read to the primary/source of truth, or attach a required log position/version and wait until the chosen replica confirms it has replayed that position within a timeout. Returning “not found” from a lagging replica as if the order never existed violates read-your-writes. The API can instead return an explicitly stale result if the product contract permits it.
</ExerciseSolution>

## A partition key is a workload and operations decision

> **Worked example.** Time partitions make dropping expired events cheap and can prune a query with a time predicate. They do not make a tenant-only query prune partitions, and they can concentrate today's write hotspot in one partition.

| Candidate key | Serves | Breaks or complicates | Evidence to collect |
| --- | --- | --- | --- |
| time range | retention, time-bounded scans | current-write hotspot; tenant-only query | date filters, retention cadence, ingest skew |
| tenant hash | tenant isolation and balanced ownership | cross-tenant reporting; tenant moves | tenant-size distribution, joins, reporting scope |
| geography | residency / latency boundary | global users and moving customers | legal domain, traffic origin, disaster plan |
| product/category | localized catalog access | uneven popularity and changing classification | hot-key distribution, reclassification rate |

A partition is not automatically a shard. Local table partitions can remain on one database node; a shard adds independent placement, failure, and coordination boundaries. Global uniqueness and foreign keys become harder when the key omits the partition owner. Put tenant identity into keys where tenant isolation is a requirement, rather than assuming an application filter is always present.

### Prediction — pruning counterexample

A table is partitioned monthly. A query filters only **tenant_id = 42** and lacks a time predicate. How many partitions can the planner discard from partition bounds alone?

<ExerciseSolution>
None merely from month bounds: tenant identity gives no constraint on the partition key. An index can still help each partition, but the query may need to inspect all of them. Add an appropriate time predicate, choose a tenant-aligned partition/shard design when the workload warrants it, or maintain a separate routing structure with a documented correctness boundary.
</ExerciseSolution>

## Migration is a state transition, not a copy command

> **Warning.** Copying a tenant to a new shard and immediately switching traffic risks missing writes, duplicate events, and split reads. A migration needs a source of truth, an ordered cutover boundary, and reconciliation before deleting the old copy.

| Phase | Required evidence |
| --- | --- |
| prepare | destination schema/version accepts the tenant; ownership routing is versioned |
| copy | snapshot position and checksum/count evidence are recorded |
| catch up | ordered changes after the snapshot replay idempotently |
| cut over | writes are fenced or redirected at one durable ownership epoch |
| verify | key counts, sampled hashes, invariants, and lag converge |
| retire | old copy is retained until rollback window and audit evidence expire |

### Transfer — choose the cutover test

Tenant 42 is moving to a new shard while orders continue to arrive. What single test is insufficient, and what must replace it?

<ExerciseSolution hint="A matching row count cannot prove every key/version and in-flight write moved exactly once.">
A final row count alone is insufficient: it misses mismatched values, duplicate outbox events, and writes after the snapshot. Record a migration epoch, fence or route writes through that epoch, replay changes after a known position idempotently, then verify key sets, checksums or sampled hashes, and domain invariants before retirement. Keep a rollback decision rule rather than deleting the old copy on optimism.
</ExerciseSolution>
