# Schema review: turn requirements into constraints

A schema review is a testable argument, not a naming review. For every relation, ask: what is one row? What identifies it? Which other row must exist? Which value is a historical fact rather than a lookup? Then write the smallest constraint or test that would catch a violation.

> **Definition.** A schema review maps domain rules to database-enforceable constraints, documents rules that cannot be enforced locally, and supplies adversarial examples for both. It reviews facts and failure modes before it reviews syntax.

## Review one multi-tenant order design

An online marketplace gives every seller a tenant. Product and order identifiers are tenant-scoped, so a foreign key must carry the tenant identity too.

<PlantUML
  code={String.raw`
class Tenant {
  tenant_id : UUID <<PK>>
}
class Product {
  tenant_id : UUID <<PK>>
  product_id : UUID <<PK>>
  sku : text
  list_price : money
}
class PurchaseOrder {
  tenant_id : UUID <<PK>>
  order_id : UUID <<PK>>
  customer_id : UUID
  placed_at : timestamp
}
class OrderLine {
  tenant_id : UUID <<PK>>
  order_id : UUID <<PK>>
  line_no : integer <<PK>>
  product_id : UUID <<FK>>
  quantity : integer
  unit_price : money
}
Tenant "1" -- "0..*" Product
Tenant "1" -- "0..*" PurchaseOrder
PurchaseOrder "1" -- "1..*" OrderLine
Product "1" -- "0..*" OrderLine : selected product
`}
/>

| Relation | Grain | Key | Core reference or rule |
| --- | --- | --- | --- |
| `Product(tenant_id, product_id, sku, list_price)` | One catalog product for one tenant | `(tenant_id, product_id)` | `sku` may need `UNIQUE(tenant_id, sku)` if the business calls it a tenant-local identifier |
| `PurchaseOrder(tenant_id, order_id, customer_id, placed_at)` | One placed order for one tenant | `(tenant_id, order_id)` | Tenant-scoped customer reference, if customers are tenant-scoped |
| `OrderLine(tenant_id, order_id, line_no, product_id, quantity, unit_price)` | One product line in one order | `(tenant_id, order_id, line_no)` | Composite reference to its order and selected product; `quantity > 0` |

> **Worked example.** `unit_price` belongs on `OrderLine` when it records the price actually agreed at purchase time. `Product.list_price` is a current catalog fact and may change tomorrow. Replacing `unit_price` with a lookup from `Product` changes historical orders retroactively; it is not a harmless normalization.

{/* Source tracking: The use of keys, composite foreign keys, check constraints, and their enforcement boundaries is synthesized from PostgreSQL’s current constraints documentation. */}

### Predict the tenant leak

Tenant A has `product_id = p9`; tenant B also has `product_id = p9`. An order line for tenant A references only `product_id = p9`. What incorrect fact can the database accept if the foreign key is only `OrderLine.product_id → Product.product_id`?

<ExerciseSolution hint="The identifier is scoped by tenant, so the product ID alone is ambiguous.">

The order line can be associated with tenant B's product even though the order belongs to tenant A. The database sees a matching product ID but cannot prove tenant consistency. Make `(tenant_id, product_id)` a referenced key of `Product` and reference both columns from `OrderLine`.
</ExerciseSolution>

<CodeExercise
  client:load
  title="Keep the tenant in the product reference"
  code={String.raw`FOREIGN KEY (tenant_id, product_id)
  REFERENCES Product ([!blank!], [!blank!])`}
  answers={["tenant_id", "product_id"]}
  explanation="A composite foreign key must name a candidate key with the same tenant-scoped meaning in Product."
/>

> **Invariant.** If identifiers are tenant-scoped, every relationship that uses one must establish tenant equality as part of its key or foreign key. Filtering by tenant in application code is not an equivalent integrity constraint.

## Walk the review questions in order

| Review question | Evidence to request | A failure it catches |
| --- | --- | --- |
| What is one row? | A grain sentence for each relation | A line item table that also stores order-wide shipping state |
| What identifies it? | Candidate keys and whether they are stable | A display label silently used as a primary key |
| What must exist first? | Foreign keys and deletion/update policy | An order line with no order or wrong-tenant product |
| Which values are derived or historical? | Source of truth and update rule | Repricing past orders by joining current catalog price |
| Which rules span rows? | Transaction/procedure/test design | Two writes that independently pass an aggregate capacity rule |
| How will it change? | Backfill, compatibility, rollback, and verification plan | A non-null column added before legacy rows are populated |

> **Warning.** A `CHECK` constraint validates the row being written; it is not a general substitute for a rule involving arbitrary other rows. “An order total equals the sum of its lines” or “stock never drops below zero” needs a design that coordinates reads and writes, not a wish written as a local check.

### Review a mixed-grain proposal

A teammate proposes this shortcut:

```text
OrderLine(tenant_id, order_id, line_no, product_id, quantity,
          order_status, placed_at, customer_email)
```

Name two facts with the wrong grain. Where should each live instead?

<ExerciseSolution hint="A line is one product occurrence; ask whether each value is the same for every line of an order.">

`order_status` and `placed_at` are facts about the whole order, so they belong in `PurchaseOrder`. `customer_email` is normally a customer fact, so it belongs in a tenant-scoped customer relation or an explicitly justified immutable order-contact snapshot. Repeating order-level values on every line causes update anomalies and makes a changed line capable of contradicting its own order.
</ExerciseSolution>

## Turn dependencies into constraints and tests

> **Definition.** A dependency hypothesis is useful in a review only when it names a business rule that can be enforced by a key, tested by adversarial rows, or explicitly owned by an application procedure.

For this design, the following dependencies express useful review hypotheses:

$$
(tenant\_id, product\_id) \to (sku, list\_price)
$$

$$
(tenant\_id, order\_id, line\_no) \to (product\_id, quantity, unit\_price).
$$

They justify the relation keys only if the product and line identifiers really are stable in the business domain. A natural key such as SKU may also be unique per tenant, but only after spelling out capitalization, reuse, and retirement policy.

> **Counterexample.** Adding `UNIQUE(sku)` globally because the current export has no duplicates can reject two independent sellers' legitimate use of the same SKU. The requirement is usually tenant-local uniqueness, which has a different key and different error behavior.

### Make an adversarial test set

Write four insert attempts that should not all succeed:

1. a duplicate line number in one order;
2. a zero or negative quantity;
3. a line that names a missing order;
4. a line for tenant A that names tenant B's product ID.

<ExerciseSolution hint="Map each attempt to a distinct constraint; the last one needs the composite key.">

The duplicate is rejected by `PRIMARY KEY (tenant_id, order_id, line_no)`. The invalid quantity is rejected by `CHECK (quantity > 0)`. The missing order is rejected by `FOREIGN KEY (tenant_id, order_id) REFERENCES PurchaseOrder`. The cross-tenant product is rejected only when the product foreign key is `(tenant_id, product_id) REFERENCES Product(tenant_id, product_id)`. These tests establish different invariants; one successful happy-path order proves none of them.
</ExerciseSolution>

## Review a change before the migration is written

The product team wants to allow a line to have no catalog product after a product is retired, while preserving the original line description and price.

> **Worked example.** This is not just “make `product_id` nullable.” Decide first whether a line must retain a historical product snapshot, whether product deletion is forbidden, or whether retirement is represented by a status rather than deletion. If the relationship becomes optional, update the foreign-key nullability, the reporting contract, and tests for null product references together.

<details>
  <summary>Questions that are intentionally deferred to a migration plan</summary>

  A schema review should identify, but not guess, the rollout method: how existing lines are backfilled, whether reads tolerate a temporary dual representation, what rollback preserves, and how a large index or constraint build affects live traffic. Those are operational choices requiring the actual database and workload.
</details>

### Transfer task

Review a proposed `OrderDiscount(tenant_id, order_id, code, amount)` relation. Decide whether its grain is one applied discount, one discount code definition, or both. State a key, one foreign key, and one rule that cannot be justified until the business answers a question.

<ExerciseSolution hint="A discount code definition and an applied discount are different facts. Ask whether a code may be applied twice to the same order.">

Use `OrderDiscount` for one applied discount on one order, with a key such as `(tenant_id, order_id, code)` if a code may be applied at most once per order, and a foreign key from `(tenant_id, order_id)` to `PurchaseOrder`. Keep code definition/eligibility in a separate tenant-scoped `Discount` relation. You cannot choose the key until the business says whether the same code can be applied more than once, whether stacked codes are allowed, and whether `amount` is a snapshot or recomputed from a changing rule.
</ExerciseSolution>
