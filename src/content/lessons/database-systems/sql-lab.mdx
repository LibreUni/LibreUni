Every task uses the same fixed fixture and expected edge cases. The embedded runner executes read-only SQLite in the browser, so a wrong join or a misplaced predicate produces a real result rather than a plausible hand trace. SQLite and PostgreSQL both support aggregate `FILTER`, but a SQLite result is not evidence of PostgreSQL-specific behavior. Use a disposable local PostgreSQL database for constraint error text and PostgreSQL plans.

| Evidence path | What it establishes | What it does not establish |
| --- | --- | --- |
| In-browser SQLite runner | executable join, grouping, and `NOT EXISTS` result semantics for this fixture | PostgreSQL-specific planner, MVCC, constraint error text, or isolation behavior |

## Create the fixed fixture

The browser runner below loads this fixture into SQLite automatically. To test PostgreSQL-specific behavior, load these statements into a disposable PostgreSQL database; the tables also support hand tracing.

```sql
CREATE TABLE client (
  client_id    integer PRIMARY KEY,
  display_name text NOT NULL
);

CREATE TABLE offering (
  offering_id integer PRIMARY KEY,
  code        text NOT NULL,
  region      text NOT NULL,
  capacity    integer NOT NULL CHECK (capacity >= 0)
);

CREATE TABLE allocation (
  client_id   integer NOT NULL REFERENCES client(client_id),
  offering_id integer NOT NULL REFERENCES offering(offering_id),
  status      text NOT NULL CHECK (status IN ('active', 'queued', 'suspended')),
  memory_gb   integer CHECK (memory_gb IS NULL OR memory_gb BETWEEN 0 AND 100),
  PRIMARY KEY (client_id, offering_id)
);

INSERT INTO client (client_id, display_name) VALUES
  (1, 'Ada'), (2, 'Bo'), (3, 'Cy'), (4, 'Dee');

INSERT INTO offering (offering_id, code, region, capacity) VALUES
  (10, 'DB101', 'us-east-1', 2),
  (11, 'DB201', 'us-east-1', 1),
  (12, 'DB301', 'us-east-1', 2),
  (13, 'DB101', 'us-west-2', 2);

INSERT INTO allocation (client_id, offering_id, status, memory_gb) VALUES
  (1, 10, 'active', 87),
  (2, 10, 'suspended', 40),
  (3, 11, 'queued', NULL),
  (4, 13, 'active', 93);
```

| Relation | Fixture facts |
| --- | --- |
| `client` | Ada, Bo, Cy, and Dee exist |
| `offering` | DB101, DB201, DB301 are in us-east-1; DB101 also has an older us-west-2 offering |
| `allocation` | Ada has active allocation in DB101; Bo is suspended; Cy is queued; Dee has active allocation only in us-west-2 |

## Task 1: keep offerings with zero active allocations

**Result contract:** one row per offering in `us-east-1`, including offerings with no active allocations; columns are `offering_id`, `code`, `active_allocations`, and `is_full`; ordered by code then offering ID.

Start with this skeleton. Decide where the status condition belongs before running it.

<CodeExercise
  client:load
  title="Complete the matching and grouping contract"
  code={String.raw`SELECT o.offering_id,
       o.code,
       [!blank!] AS active_allocations,
       [!blank!] AS is_full
FROM offering AS o
LEFT JOIN allocation AS a
  [!blank!] a.offering_id = o.offering_id
 AND a.status = 'active'
WHERE o.region = 'us-east-1'
[!blank!] o.offering_id, o.code, o.capacity
ORDER BY o.code, o.offering_id`}
  answers={["COUNT(a.client_id)", "COUNT(a.client_id) >= o.capacity", "ON", "GROUP BY"]}
  explanation="`COUNT(a.client_id)` counts only real matches, so a null-extended offering reports zero; compare that count with capacity for `is_full`. The status predicate belongs in `ON`: moving it to `WHERE` removes the offerings this report must include. `GROUP BY` states the one-row-per-offering grain."
/>

```sql
SELECT o.offering_id,
       o.code,
       COUNT(a.client_id) AS active_allocations,
       COUNT(a.client_id) >= o.capacity AS is_full
FROM offering AS o
LEFT JOIN allocation AS a
  ON a.offering_id = o.offering_id
 AND a.status = 'active'
WHERE o.region = 'us-east-1'
GROUP BY o.offering_id, o.code, o.capacity
ORDER BY o.code, o.offering_id;
```

> **Worked example.** The left join emits each us-east-1 offering even when no active right row exists. `COUNT(a.client_id)` ignores the null-extended value, so it produces zero for DB201 and DB301; `COUNT(*)` would instead count the left row and be wrong for this contract.

**Expected `Task 1` result** (SQLite evaluates boolean comparisons such as `>=` as `0` / `1`, whereas PostgreSQL returns `false` / `true`):

| `offering_id` | `code` | `active_allocations` | `is_full` |
| --- | --- | --- | --- |
| 10 | DB101 | 1 | 0 |
| 11 | DB201 | 0 | 0 |
| 12 | DB301 | 0 | 0 |

### Break it on purpose

Move `a.status = 'active'` into `WHERE`, then predict the result. Why is DB201 absent even though it has an allocation row?

<ExerciseSolution hint="`WHERE` filters after NULL extension and after the right-side status is visible.">

Only DB101 remains. DB201's only match has status `queued`, so the `WHERE` predicate is false; DB301 has a null-extended status, so the predicate is `UNKNOWN`. Both are removed. The query has changed from “all offerings, count active matches” to “offerings with at least one active match.”
</ExerciseSolution>

> **Counterexample.** A query can be syntactically valid, return a count, and still fail the report contract. A test dataset containing only offerings with active allocations would not expose this `ON`/`WHERE` bug; zero and nonqualifying cases must be seeded deliberately.

## Task 2: find clients with no active allocation in region us-east-1

**Result contract:** one row per client who has no `active` allocation in a us-east-1 offering; ordered by client ID.

Complete the absence test, then compare your result with the fixture.

<CodeExercise
  client:load
  title="Reconstruct the correlated absence test"
  code={String.raw`SELECT c.client_id, c.display_name
FROM client AS c
WHERE [!blank!] (
  SELECT 1
  FROM allocation AS a
  JOIN offering AS o ON o.offering_id = a.offering_id
  WHERE [!blank!]
    AND a.status = 'active'
    AND o.region = 'us-east-1'
);`}
  answers={["NOT EXISTS", "a.client_id = c.client_id"]}
  explanation="`NOT EXISTS` states the required absence directly and is NULL-safe. The correlated equality is what binds the subquery to one outer client; without it the subquery answers a global question instead of a per-client one."
/>

```sql
SELECT c.client_id, c.display_name
FROM client AS c
WHERE NOT EXISTS (
  SELECT 1
  FROM allocation AS a
  JOIN offering AS o ON o.offering_id = a.offering_id
  WHERE a.client_id = c.client_id
    AND a.status = 'active'
    AND o.region = 'us-east-1'
)
ORDER BY c.client_id;
```

> **Worked example.** Bo is included because suspended is not active. Cy is included because queued is not active. Dee is included because the only active row is in us-west-2. Ada is excluded because the correlated subquery finds the active us-east-1 DB101 allocation.

**Expected `Task 2` result:**

| `client_id` | `display_name` |
| --- | --- |
| 2 | Bo |
| 3 | Cy |
| 4 | Dee |

> **Warning.** Do not replace this query with `NOT IN (SELECT client_id FROM allocation)` without a precise proof about NULL and the omitted region/status conditions. `NOT EXISTS` states the required correlated absence directly.

### Change the requirement

The platform policy changes “no active allocation” to “no active **or queued** allocation.” Which predicate changes, and which expected row disappears?

<ExerciseSolution hint="The region boundary is unchanged. Only the accepted allocation states change.">

Change the correlated condition to `a.status IN ('active', 'queued')`. Cy disappears because Cy is queued in DB201 for us-east-1. Bo remains because suspended is still excluded; Dee remains because the only row is in us-west-2.
</ExerciseSolution>

## Task 3: test the schema, not just the queries

For each proposed write, predict the intended rejection. In a local PostgreSQL lab, issue each in its own transaction and roll it back after the expected error.

| Proposed fact | Constraint that should reject it |
| --- | --- |
| Add a second `(1, 10, 'active', 91)` row | Composite primary key on `(client_id, offering_id)` |
| Add `(1, 999, 'active', 91)` | Foreign key to `offering` |
| Add `(1, 11, 'active', -4)` | Memory allocation range check |
| Add `(1, 11, 'active', 101)` | Memory allocation range check |

```sql
BEGIN;
INSERT INTO allocation (client_id, offering_id, status, memory_gb)
VALUES (1, 999, 'active', 91);
-- PostgreSQL reports a foreign-key violation here.
ROLLBACK;
```

> **Invariant.** Constraint tests are part of the schema's behavior specification. A successful `SELECT` cannot prove that invalid state is impossible; each rule needs at least one adversarial write that targets it.

### Diagnose a missing rule

The infrastructure team now says “a full offering may not gain another active allocation.” Can you express that correctly with the existing row-local `CHECK` constraints? State what is missing from the lab design.

<ExerciseSolution hint="Capacity depends on multiple allocation rows, but a CHECK sees its own row's values.">

No. `capacity` and the count of active allocation rows live in different rows/relations, so an ordinary row-local check cannot safely compare them. The design needs a transaction-aware allocation operation or another coordinated integrity mechanism, plus concurrency tests. This lab intentionally stops before transaction isolation and does not pretend a check constraint solves it.
</ExerciseSolution>

## Task 4: make a cautious plan observation (optional)

Run the zero-safe report with PostgreSQL's read-only plan command:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.offering_id,
       o.code,
       COUNT(a.client_id) AS active_allocations
FROM offering AS o
LEFT JOIN allocation AS a
  ON a.offering_id = o.offering_id
 AND a.status = 'active'
WHERE o.region = 'us-east-1'
GROUP BY o.offering_id, o.code
ORDER BY o.code, o.offering_id;
```

Record exactly one observation that the output supports, such as “on this four-offering fixture, PostgreSQL chose a sequential scan.” Do **not** conclude that a sequential scan is always best or that the plan proves semantic correctness.

> **Remark (Optional extension on testing an index hypothesis).** In a disposable lab only, add an index after recording the baseline, rerun the same `EXPLAIN`, and compare the actual rows as well as the plan. For a tiny fixture PostgreSQL may rationally keep a sequential scan. The experiment teaches that a physical change is a cost hypothesis, while the report contract is a correctness obligation.

<Exercise id="ex-lab-conditional-aggregation" type="construct" level="application" title="Conditional Aggregation with Status Filtering">

Write a PostgreSQL query against `offering(offering_id, code, region)` and `allocation(client_id, offering_id, status)` that reports `(code, active_count, queued_count)` for all us-east-1 offerings, preserving offerings with zero allocations. Use standard SQL aggregate `FILTER` clauses.

<ExerciseSolution hint="Use a LEFT JOIN from offering to allocation and aggregate using FILTER (WHERE ...).">

```sql
SELECT o.code,
       COUNT(*) FILTER (WHERE a.status = 'active') AS active_count,
       COUNT(*) FILTER (WHERE a.status = 'queued') AS queued_count
FROM offering AS o
LEFT JOIN allocation AS a
  ON a.offering_id = o.offering_id
WHERE o.region = 'us-east-1'
GROUP BY o.offering_id, o.code
ORDER BY o.code;
```
`COUNT(*) FILTER (WHERE ...)` evaluates conditions over right-side matches while preserving empty offerings with count 0.

</ExerciseSolution>

<Exercise id="ex-lab-multi-row-check-invariant" type="verify" level="application" title="Capacity Check Constraint Scope Limitation">

A developer attempts to enforce an offering capacity limit by writing `CHECK ((SELECT COUNT(*) FROM allocation a WHERE a.offering_id = offering_id) <= capacity)` inside a table definition. Verify why standard SQL rejects or fails to guarantee this constraint under concurrent transactions.

<ExerciseSolution hint="Check constraints are evaluated strictly on the single modified row and cannot safely query dynamic foreign tables.">

Standard SQL table check constraints evaluate predicates over the immediate columns of the mutated row; subqueries in `CHECK` constraints are either explicitly disallowed by RDBMS engines or susceptible to race conditions under non-serializable isolation levels, where concurrent commits can exceed capacity without seeing each other's inserts.

</ExerciseSolution>

</Exercise>

<Exercise id="ex-lab-explain-plan-interpretation" type="describe" level="recall" title="Query Plan Execution vs. Correctness Semantics">

Explain why observing a sequential scan in `EXPLAIN ANALYZE` on a four-row fixture does not indicate an optimization defect or justify adding an index.

<ExerciseSolution hint="Compare disk page fetch overhead with sequential cache hits on small tables.">

For small relations occupying a single disk page, a sequential scan reads the single page directly into cache without paying the additional overhead of traversing an index B-tree. The optimizer correctly minimizes cost based on catalog statistics. Physical plans reflect cost models, not relational correctness contracts.

</ExerciseSolution>

</Exercise>

Design test cases for the multi-status allocation query. Identify two adversarial seed rows that expose bugs in: (1) moving status checks to `WHERE`, and (2) using unfiltered `COUNT(*)`.

<ExerciseSolution hint="Provide an offering with only suspended allocations, and an offering with zero allocations.">

2. Seed an offering with zero allocations: using unfiltered `COUNT(*)` reports count 1 due to the null-extended joined row, whereas `COUNT(*) FILTER (...)` or `COUNT(a.client_id)` correctly yields 0.
