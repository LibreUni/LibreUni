# SQL lab: build and verify a registration report

This is a paper-first lab with an optional PostgreSQL 18 run. Every task has a fixed fixture and expected edge cases, so you can complete the semantic work without a database server. If you do run it, use a disposable local database: the SQL below creates and inserts lab data.

| Evidence path | What it establishes | What it does not establish |
| --- | --- | --- |
| PostgreSQL 18 fixture | PostgreSQL syntax, constraints, `FILTER`, and an observed `EXPLAIN` plan | behavior of other engines or every workload |
| SQLite or hand trace | portable join, grouping, and `NOT EXISTS` result semantics for this fixture | PostgreSQL planner, MVCC, error text, or isolation behavior |

Record the engine and version with every observed result. Do not submit SQLite output as evidence that a PostgreSQL-specific statement or plan executed.

> **Definition.** A lab result contract states the output grain, inclusion rules, ordering, and test rows before execution. A query is not complete because it returns plausible rows on a happy-path dataset.

## Lab brief and evidence checklist

| Deliverable | What to include | Evidence of success |
| --- | --- | --- |
| Zero-safe enrollment report | Contract, query, predicted table | Offerings with zero enrolled students remain |
| Anti-join | Contract, query, predicted table | A student with only an old enrollment is correctly included |
| Constraint probes | Four deliberately invalid writes | Each is rejected by the intended key, foreign key, or check |
| Plan observation (optional) | `EXPLAIN` output and one cautious claim | A measured plan fact, not a promise that all data will use that plan |

> **Warning.** Do not run these statements against a shared or production schema. The lesson has no arbitrary SQL executor; a local PostgreSQL instance is optional, and the supplied tables are enough to hand-trace each task.

## Create the fixed fixture

If you have a disposable PostgreSQL database, load the schema and rows. Otherwise, use the tables as the authoritative fixture for hand tracing.

```sql
CREATE TABLE student (
  student_id   integer PRIMARY KEY,
  display_name text NOT NULL
);

CREATE TABLE offering (
  offering_id integer PRIMARY KEY,
  code        text NOT NULL,
  term        text NOT NULL,
  capacity    integer NOT NULL CHECK (capacity >= 0)
);

CREATE TABLE enrollment (
  student_id  integer NOT NULL REFERENCES student(student_id),
  offering_id integer NOT NULL REFERENCES offering(offering_id),
  status      text NOT NULL CHECK (status IN ('enrolled', 'waitlisted', 'dropped')),
  grade       integer CHECK (grade IS NULL OR grade BETWEEN 0 AND 100),
  PRIMARY KEY (student_id, offering_id)
);

INSERT INTO student (student_id, display_name) VALUES
  (1, 'Ada'), (2, 'Bo'), (3, 'Cy'), (4, 'Dee');

INSERT INTO offering (offering_id, code, term, capacity) VALUES
  (10, 'DB101', '2026S', 2),
  (11, 'DB201', '2026S', 1),
  (12, 'DB301', '2026S', 2),
  (13, 'DB101', '2025F', 2);

INSERT INTO enrollment (student_id, offering_id, status, grade) VALUES
  (1, 10, 'enrolled', 87),
  (2, 10, 'dropped', 40),
  (3, 11, 'waitlisted', NULL),
  (4, 13, 'enrolled', 93);
```

| Relation | Fixture facts |
| --- | --- |
| `student` | Ada, Bo, Cy, and Dee exist |
| `offering` | DB101, DB201, DB301 are in 2026S; DB101 also has an older 2025F offering |
| `enrollment` | Ada is enrolled in current DB101; Bo is dropped; Cy is waitlisted; Dee is enrolled only in the old term |

> **Invariant.** `enrollment` has grain “one student's status in one offering.” Its composite primary key forbids two simultaneous rows for the same student/offering pair. The foreign keys forbid an enrollment for an unknown student or offering.

### Warm-up prediction

Before writing SQL, list the 2026S offerings and the count of rows whose status is `enrolled`. Do not count `dropped` or `waitlisted` rows.

<ExerciseSolution hint="Filter the enrollment rows by status first, then keep every current-term offering.">

The desired report has DB101 with count 1, DB201 with count 0, and DB301 with count 0. The fixed fixture has no enrolled row for DB201 or DB301. This table is the oracle for the first task, not an optional afterthought.
</ExerciseSolution>

## Task 1: keep offerings with zero enrolled students

**Result contract:** one row per offering in `2026S`, including offerings with no enrolled students; columns are `code`, `enrolled_count`, and `is_full`; ordered by code then offering ID.

Start with this skeleton. Decide where the status condition belongs before running it.

<CodeExercise
  client:load
  title="Match enrolled rows without deleting empty offerings"
  code={String.raw`FROM offering AS o
LEFT JOIN enrollment AS e
  [!blank!] e.offering_id = o.offering_id
 AND e.status = 'enrolled'`}
  answers={["ON"]}
  explanation="The status controls which right-side rows match. The report still requires every current-term offering from the left side."
/>

```sql
SELECT o.offering_id,
       o.code,
       COUNT(e.student_id) AS enrolled_count,
       COUNT(e.student_id) >= o.capacity AS is_full
FROM offering AS o
LEFT JOIN enrollment AS e
  ON e.offering_id = o.offering_id
 AND e.status = 'enrolled'
WHERE o.term = '2026S'
GROUP BY o.offering_id, o.code, o.capacity
ORDER BY o.code, o.offering_id;
```

> **Worked example.** The left join emits each 2026S offering even when no enrolled right row exists. `COUNT(e.student_id)` ignores the null-extended value, so it produces zero for DB201 and DB301; `COUNT(*)` would instead count the left row and be wrong for this contract.

| Expected `Task 1` result |  |  |  |
| --- | --- | --- | --- |
| `offering_id` | `code` | `enrolled_count` | `is_full` |
| 10 | DB101 | 1 | false |
| 11 | DB201 | 0 | false |
| 12 | DB301 | 0 | false |

### Break it on purpose

Move `e.status = 'enrolled'` into `WHERE`, then predict the result. Why is DB201 absent even though it has an enrollment row?

<ExerciseSolution hint="`WHERE` filters after NULL extension and after the right-side status is visible.">

Only DB101 remains. DB201's only match has status `waitlisted`, so the `WHERE` predicate is false; DB301 has a null-extended status, so the predicate is `UNKNOWN`. Both are removed. The query has changed from “all offerings, count enrolled matches” to “offerings with at least one enrolled match.”
</ExerciseSolution>

> **Counterexample.** A query can be syntactically valid, return a count, and still fail the report contract. A test dataset containing only offerings with enrolled students would not expose this `ON`/`WHERE` bug; zero and nonqualifying cases must be seeded deliberately.

## Task 2: find students with no current enrollment

**Result contract:** one row per student who has no `enrolled` registration in a 2026S offering; ordered by student ID.

Complete the absence test, then compare your result with the fixture.

<CodeExercise
  client:load
  title="Ask whether a matching row exists"
  code={String.raw`SELECT s.student_id, s.display_name
FROM student AS s
WHERE [!blank!] (
  SELECT 1
  FROM enrollment AS e
  JOIN offering AS o ON o.offering_id = e.offering_id
  WHERE e.student_id = s.student_id
    AND e.status = 'enrolled'
    AND o.term = '2026S'
);`}
  answers={["NOT EXISTS"]}
  explanation="The subquery is correlated to one student. The outer row survives exactly when it has no enrolled current-term row."
/>

```sql
SELECT s.student_id, s.display_name
FROM student AS s
WHERE NOT EXISTS (
  SELECT 1
  FROM enrollment AS e
  JOIN offering AS o ON o.offering_id = e.offering_id
  WHERE e.student_id = s.student_id
    AND e.status = 'enrolled'
    AND o.term = '2026S'
)
ORDER BY s.student_id;
```

> **Worked example.** Bo is included because dropped is not enrolled. Cy is included because waitlisted is not enrolled. Dee is included because the only enrolled row is in 2025F. Ada is excluded because the correlated subquery finds current DB101.

| Expected `Task 2` result |  |
| --- | --- |
| `student_id` | `display_name` |
| 2 | Bo |
| 3 | Cy |
| 4 | Dee |

> **Warning.** Do not replace this query with `NOT IN (SELECT student_id FROM enrollment)` without a precise proof about NULL and the omitted term/status conditions. `NOT EXISTS` states the required correlated absence directly.

### Change the requirement

The registrar changes “no current enrollment” to “no current **or waitlisted** registration.” Which predicate changes, and which expected row disappears?

<ExerciseSolution hint="The term boundary is unchanged. Only the accepted enrollment states change.">

Change the correlated condition to `e.status IN ('enrolled', 'waitlisted')`. Cy disappears because Cy is waitlisted in DB201 for 2026S. Bo remains because dropped is still excluded; Dee remains because the only row is in 2025F.
</ExerciseSolution>

## Task 3: test the schema, not just the queries

For each proposed write, predict the intended rejection. In a local PostgreSQL lab, issue each in its own transaction and roll it back after the expected error.

| Proposed fact | Constraint that should reject it |
| --- | --- |
| Add a second `(1, 10, 'enrolled', 91)` row | Composite primary key on `(student_id, offering_id)` |
| Add `(1, 999, 'enrolled', 91)` | Foreign key to `offering` |
| Add `(1, 11, 'enrolled', -4)` | Grade check |
| Add `(1, 11, 'enrolled', 101)` | Grade check |

```sql
BEGIN;
INSERT INTO enrollment (student_id, offering_id, status, grade)
VALUES (1, 999, 'enrolled', 91);
-- PostgreSQL reports a foreign-key violation here.
ROLLBACK;
```

> **Invariant.** Constraint tests are part of the schema's behavior specification. A successful `SELECT` cannot prove that invalid state is impossible; each rule needs at least one adversarial write that targets it.

### Diagnose a missing rule

The school now says “a full offering may not gain another enrolled student.” Can you express that correctly with the existing row-local `CHECK` constraints? State what is missing from the lab design.

<ExerciseSolution hint="Capacity depends on multiple enrollment rows, but a CHECK sees its own row's values.">

No. `capacity` and the count of enrolled rows live in different rows/relations, so an ordinary row-local check cannot safely compare them. The design needs a transaction-aware enrollment operation or another coordinated integrity mechanism, plus concurrency tests. This lab intentionally stops before transaction isolation and does not pretend a check constraint solves it.
</ExerciseSolution>

## Task 4: make a cautious plan observation (optional)

Run the zero-safe report with PostgreSQL's read-only plan command:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.offering_id,
       o.code,
       COUNT(e.student_id) AS enrolled_count
FROM offering AS o
LEFT JOIN enrollment AS e
  ON e.offering_id = o.offering_id
 AND e.status = 'enrolled'
WHERE o.term = '2026S'
GROUP BY o.offering_id, o.code
ORDER BY o.code, o.offering_id;
```

Record exactly one observation that the output supports, such as “on this four-offering fixture, PostgreSQL chose a sequential scan.” Do **not** conclude that a sequential scan is always best or that the plan proves semantic correctness.

<details>
  <summary>Optional extension: test an index hypothesis</summary>

For a tiny fixture PostgreSQL may rationally keep a sequential scan. The experiment teaches that a physical change is a cost hypothesis, while the report contract is a correctness obligation.
</details>

## Portfolio transfer task

Write and test a query for: “For every 2026S offering, show the code, the number of enrolled students, and the number of waitlisted students; include offerings with neither; order by code.” Submit:

1. a one-sentence result contract;
2. the SQL with a sentence for each `ON`, `WHERE`, and aggregate choice;
3. a predicted result table for the fixed fixture;
4. two extra seed rows that would catch a wrong answer.

<ExerciseSolution hint="Keep the current-term condition on Offering. Preserve all offerings with a left join, then use conditional aggregation for the two status counts.">

One correct core is:

```sql
SELECT o.code,
       COUNT(*) FILTER (WHERE e.status = 'enrolled') AS enrolled_count,
       COUNT(*) FILTER (WHERE e.status = 'waitlisted') AS waitlisted_count
FROM offering AS o
LEFT JOIN enrollment AS e
  ON e.offering_id = o.offering_id
WHERE o.term = '2026S'
GROUP BY o.offering_id, o.code
ORDER BY o.code, o.offering_id;
```

For the fixture, DB101 is `(1, 0)`, DB201 is `(0, 1)`, and DB301 is `(0, 0)`. Seed one offering with both an enrolled and waitlisted row, plus one offering with only a dropped row. Those cases catch accidental status filtering in `WHERE` and incorrect use of `COUNT(*)` without a filter.
</ExerciseSolution>
