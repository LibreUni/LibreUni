# SQL querying: specify rows, then test edge cases

SQL is concise enough to hide a wrong question. Before typing, say the output grain: “one row per offering in 2026S, including offerings with zero enrolled students.” That single sentence determines whether a filter belongs in `ON`, `WHERE`, or `HAVING`.

> **Definition.** This lesson uses PostgreSQL `SELECT` semantics. A query's clauses define a logical result; the optimizer may use a different physical execution order to compute it.

{/* Source tracking: The logical `SELECT` processing model and join/aggregate clauses are synthesized from PostgreSQL’s current `SELECT` documentation. */}

## Follow the logical pipeline

For a common grouped query, reason in this order.

| Stage | Question answered | Typical clause |
| --- | --- | --- |
| Build candidate rows | Which source rows and matches are available? | `FROM ... JOIN ... ON ...` |
| Remove individual rows | Which candidate rows satisfy a condition? | `WHERE` |
| Form groups | Which remaining rows belong together? | `GROUP BY` |
| Remove groups | Which computed groups qualify? | `HAVING` |
| Shape output | Which expressions become columns? | `SELECT` |
| Present a sequence | What order is promised to the client? | `ORDER BY` |

> **Warning.** This is a semantic trace, not an execution-plan trace. A database may push a filter into a scan or rearrange inner joins when it can preserve the same result. Never infer a result order without `ORDER BY`.

## Build a zero-safe enrollment report

Use this registration fixture.

| `Offering` |  |  | `Enrollment` |  |  |
| --- | --- | --- | --- | --- | --- |
| `offering_id` | `code` | `term` | `student_id` | `offering_id` | `status` |
| 10 | DB101 | 2026S | Ada | 10 | enrolled |
| 11 | DB201 | 2026S | Bo | 11 | dropped |
| 12 | DB301 | 2026S |  |  |  |
| 13 | DB101 | 2025F |  |  |  |

The report must include offering 11 and 12 with count zero. Its grain is **one offering in 2026S**, not one joined enrollment row.

```sql
SELECT o.code,
       COUNT(e.student_id) AS enrolled_count
FROM Offering AS o
LEFT JOIN Enrollment AS e
  ON e.offering_id = o.offering_id
 AND e.status = 'enrolled'
WHERE o.term = '2026S'
GROUP BY o.offering_id, o.code
ORDER BY o.code;
```

> **Worked example.** `ON` decides which enrollment rows match each offering. The status condition keeps only enrolled matches, while the left join still emits null-extended rows for offerings with no such match. `WHERE` then removes the old-term offering 13. `COUNT(e.student_id)` counts only non-null matching IDs, yielding `DB101 → 1`, `DB201 → 0`, and `DB301 → 0`.

### Predict the bug

Move `AND e.status = 'enrolled'` from `ON` to `WHERE`. Which offering rows disappear, and why?

<ExerciseSolution hint="A left join creates NULLs for rows with no qualifying right-side match; `WHERE` runs afterward.">

Offerings 11 and 12 disappear. Offering 11's only matching enrollment is `dropped`; offering 12 is null-extended because it has no enrollment. Neither makes `e.status = 'enrolled'` true in `WHERE`. The condition turns this part of the left join into inner-join-like behavior for that predicate.
</ExerciseSolution>

## See predicate placement change the result

The visual model fixes Ada at grade 87, Bo at grade 40, and Cy with no enrollment. Set the threshold to 50. Predict whether Cy survives before trying both placements.

<JoinPredicatePlayground client:load />

> **Invariant.** In a `LEFT JOIN`, a predicate in `ON` limits right-side matches while retaining every left-side row. A predicate in `WHERE` filters the post-join rows, including null-extended rows. Put it where the report's inclusion rule says it belongs.

> **Counterexample.** “Put every filter in `WHERE`” fails for the zero-safe report. “Put every filter in `ON`” also fails when the condition should remove left rows, such as `o.term = '2026S'`. Clause placement follows row survival, not a style rule.

### Apply the row-survival test

The product team wants **all** 2026S offerings, but only grades of 70 or more should be shown when a grade exists. Where do `o.term = '2026S'` and `e.grade >= 70` belong?

<ExerciseSolution hint="Ask whether each condition describes a left row that may survive and a right row that may match.">

`o.term = '2026S'` belongs in `WHERE` because an old-term offering should disappear. `e.grade >= 70` belongs in `ON` if a 2026S offering must still appear when it has no passing grade. This preserves the left relation's required rows while changing which right rows qualify as matches.
</ExerciseSolution>

## Groups answer a different question from rows

`WHERE` filters rows before aggregation; `HAVING` filters a group after an aggregate has been computed.

```sql
SELECT o.code,
       COUNT(e.student_id) AS enrolled_count
FROM Offering AS o
LEFT JOIN Enrollment AS e
  ON e.offering_id = o.offering_id
 AND e.status = 'enrolled'
WHERE o.term = '2026S'
GROUP BY o.offering_id, o.code
HAVING COUNT(e.student_id) >= 1;
```

> **Worked example.** This version has the same group grain as the zero-safe report but removes groups with zero enrolled students at `HAVING`. Moving `COUNT(e.student_id) >= 1` to `WHERE` is invalid because `WHERE` is evaluated before the count exists.

### Trace a result

For the fixture above, what rows survive the `HAVING` version? Then state what one output row means.

<ExerciseSolution hint="Reuse the three group counts from the earlier report.">

Only `DB101, 1` survives. Each output row means “one offering in 2026S whose enrolled-student count is at least one.” It does not mean one student, because the grouping collapsed student rows.
</ExerciseSolution>

## Anti-joins: prefer a NULL-safe question

To ask for students with no current enrollment, write the absence condition directly.

```sql
SELECT s.student_id
FROM Student AS s
WHERE NOT EXISTS (
  SELECT 1
  FROM Enrollment AS e
  WHERE e.student_id = s.student_id
    AND e.status = 'enrolled'
);
```

> **Worked example.** The correlated condition asks whether an enrolled row exists for this student. If none exists, `NOT EXISTS` is true. The query does not depend on a subquery list having no `NULL` values.

> **Warning.** `NOT IN (subquery)` can behave unexpectedly if the subquery returns `NULL`: comparisons can become `UNKNOWN`, so no outer row is retained. Use `NOT EXISTS` for an anti-join unless you have proved the list is non-null and understand the intended semantics.

### Prediction with a NULL

Suppose a data-quality bug produces an enrollment row with `student_id = NULL`. Why can `WHERE s.student_id NOT IN (SELECT student_id FROM Enrollment)` return no students, while the `NOT EXISTS` query above can still answer the intended question?

<ExerciseSolution hint="Evaluate `s.student_id <> NULL` using SQL three-valued logic.">

The `NOT IN` condition is equivalent to a chain of inequalities. One comparison to `NULL` becomes `UNKNOWN`, so the whole predicate may fail to become true for every student. `NOT EXISTS` tests only whether a correlated row with equal non-null ID and enrolled status exists; an unrelated null ID does not make that condition true.
</ExerciseSolution>

## Transfer task: make the contract executable

> **Remark.** Preserve the left relation's required rows first; then make each count's membership rule explicit. A report with two status counts is not a reason to let an unqualified join choose the result grain.

Write a PostgreSQL query for: “For each 2026S offering, return its code, the number of enrolled students, and a Boolean `is_full`; include empty offerings; return only offerings whose capacity is at least 1; order by code.” Before writing SQL, state:

1. the output grain;
2. which predicate belongs in `ON`, `WHERE`, and `HAVING` (if any);
3. two seed rows that would expose a misplaced predicate.

<ExerciseSolution hint="The capacity condition is about an Offering row. Enrollment status decides a right-side match. `is_full` is computed after the group count.">

The grain is one 2026S offering with positive capacity. Put `e.status = 'enrolled'` in `ON`; put `o.term = '2026S'` and `o.capacity >= 1` in `WHERE`; no `HAVING` is required unless the report later filters counts. Compute `COUNT(e.student_id) >= o.capacity` as `is_full` after grouping. Seed an offering with capacity 5 and no enrollments, plus one with only a dropped enrollment: both must remain with count zero. Those rows reveal the error of moving the status predicate to `WHERE`.
</ExerciseSolution>
