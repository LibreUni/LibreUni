SQL is concise enough to hide a wrong question. Before typing, say the output grain: “one row per offering in us-east-1, including offerings with zero active allocations.” That single sentence determines whether a filter belongs in `ON`, `WHERE`, or `HAVING`.

> **Definition.** This lesson uses PostgreSQL `SELECT` semantics. A query's clauses define a logical result; the optimizer may use a different physical execution order to compute it.

## Follow the logical pipeline

For a common grouped query, reason in this order.

| Stage | Question answered | Typical clause |
| --- | --- | --- |
| Build candidate rows | Which source rows and matches are available? | `FROM ... JOIN ... ON ...` |
| Remove individual rows | Which candidate rows satisfy a condition? | `WHERE` |
| Form groups | Which remaining rows belong together? | `GROUP BY` |
| Remove groups | Which computed groups qualify? | `HAVING` |
| Shape output | Which expressions become columns? | `SELECT` |
| Present a sequence | What order is promised to the client? | `ORDER BY` |

> **Warning.** This is a semantic trace, not an execution-plan trace. A database may push a filter into a scan or rearrange inner joins when it can preserve the same result. Never infer a result order without `ORDER BY`.

The analogous PostgreSQL statement is:

```sql
SELECT o.code,
       COUNT(a.client_id) AS active_count
FROM Offering AS o
LEFT JOIN Allocation AS a
  ON a.offering_id = o.offering_id
 AND a.status = 'active'
WHERE o.region = 'us-east-1'
GROUP BY o.offering_id, o.code
ORDER BY o.code;
```

> **Worked example.** `ON` decides which allocation rows match each offering. The status condition keeps only active matches, while the left join still emits null-extended rows for offerings with no such match. `WHERE` then removes the other-region offering 13. `COUNT(a.client_id)` counts only non-null matching IDs, yielding `DB101 → 1`, `DB201 → 0`, and `DB301 → 0`.

### Predict the bug

Move `AND a.status = 'active'` from `ON` to `WHERE`. Which offering rows disappear, and why?

<ExerciseSolution hint="A left join creates NULLs for rows with no qualifying right-side match; `WHERE` runs afterward.">

Offerings 11 and 12 disappear. Offering 11's only matching allocation is `suspended`; offering 12 is null-extended because it has no allocation. Neither makes `a.status = 'active'` true in `WHERE`. The condition turns this part of the left join into inner-join-like behavior for that predicate.
</ExerciseSolution>

## See predicate placement change the result

The visual model fixes `worker-01` at 87 GB, `worker-02` at 40 GB, and `worker-03` with no allocations. Set the threshold to 50 GB. Predict whether `worker-03` survives before trying both placements.

<JoinPredicatePlayground client:load />

> **Invariant.** In a `LEFT JOIN`, a predicate in `ON` limits right-side matches while retaining every left-side row. A predicate in `WHERE` filters the post-join rows, including null-extended rows. Put it where the report's inclusion rule says it belongs.

> **Counterexample.** “Put every filter in `WHERE`” fails for the zero-safe report. “Put every filter in `ON`” also fails when the condition should remove left rows, such as `o.region = 'us-east-1'`. Clause placement follows row survival, not a style rule.

### Apply the row-survival test

The infrastructure team wants **all** us-east-1 offerings, but only allocations of 70 GB or more should be shown when an allocation exists. Where do `o.region = 'us-east-1'` and `a.memory_gb >= 70` belong?

<ExerciseSolution hint="Ask whether each condition describes a left row that may survive and a right row that may match.">

`o.region = 'us-east-1'` belongs in `WHERE` because an other-region offering should disappear. `a.memory_gb >= 70` belongs in `ON` if a us-east-1 offering must still appear when it has no qualifying allocation. This preserves the left relation's required rows while changing which right rows qualify as matches.
</ExerciseSolution>

## Groups answer a different question from rows

`WHERE` filters rows before aggregation; `HAVING` filters a group after an aggregate has been computed.

```sql
SELECT o.code,
       COUNT(a.client_id) AS active_count
FROM Offering AS o
LEFT JOIN Allocation AS a
  ON a.offering_id = o.offering_id
 AND a.status = 'active'
WHERE o.region = 'us-east-1'
GROUP BY o.offering_id, o.code
HAVING COUNT(a.client_id) >= 1;
```

> **Worked example.** This version has the same group grain as the zero-safe report but removes groups with zero active allocations at `HAVING`. Moving `COUNT(a.client_id) >= 1` to `WHERE` is invalid because `WHERE` is evaluated before the count exists.

### Trace a result

For the fixture above, what rows survive the `HAVING` version? Then state what one output row means.

<ExerciseSolution hint="Reuse the three group counts from the earlier report.">

Only `DB101, 1` survives. Each output row means “one offering in us-east-1 whose active allocation count is at least one.” It does not mean one client, because the grouping collapsed allocation rows.
</ExerciseSolution>

## Anti-joins: prefer a NULL-safe question

To ask for clients with no active allocation in region us-east-1, write the absence condition directly.

```sql
SELECT c.client_id
FROM Client AS c
WHERE NOT EXISTS (
  SELECT 1
  FROM Allocation AS a
  JOIN Offering AS o ON o.offering_id = a.offering_id
  WHERE a.client_id = c.client_id
    AND a.status = 'active'
    AND o.region = 'us-east-1'
);
```

> **Worked example.** The correlated condition asks whether an active allocation row exists for this client. If none exists, `NOT EXISTS` is true. The query does not depend on a subquery list having no `NULL` values.

> **Warning.** `NOT IN (subquery)` can behave unexpectedly if the subquery returns `NULL`: comparisons can become `UNKNOWN`, so no outer row is retained. Use `NOT EXISTS` for an anti-join unless you have proved the list is non-null and understand the intended semantics.

### Prediction with a NULL

Suppose a data-quality bug produces an allocation row with `client_id = NULL`. Why can `WHERE c.client_id NOT IN (SELECT client_id FROM Allocation)` return no clients, while the `NOT EXISTS` query above can still answer the intended question?

<ExerciseSolution hint="Evaluate `c.client_id <> NULL` using SQL three-valued logic.">

The `NOT IN` condition is equivalent to a chain of inequalities. One comparison to `NULL` becomes `UNKNOWN`, so the whole predicate may fail to become true for every client. `NOT EXISTS` tests only whether a correlated row with equal non-null ID and active status exists; an unrelated null ID does not make that condition true.
</ExerciseSolution>

<Exercise id="ex-sql-predicate-placement" type="describe" level="recall" title="ON versus WHERE Predicate Placement Semantics">

Explain how moving an outer join filter predicate from the `ON` clause to the `WHERE` clause changes query semantics for null-extended rows. Give a concrete example where an offering with zero allocations is erroneously discarded.

<ExerciseSolution hint="A LEFT JOIN produces NULL values for right attributes when no match occurs. WHERE filters after that generation.">

In a `LEFT JOIN`, conditions in the `ON` clause decide whether right-side rows match, preserving all left rows. If the filter condition is moved to `WHERE`, it is evaluated on the joined result where right attributes are `NULL`. Comparisons against `NULL` evaluate to `UNKNOWN` in SQL's three-valued logic, which `WHERE` treats as false, eliminating unmatched left-side rows and inadvertently converting the outer join into an inner join.

</ExerciseSolution>

<Exercise id="ex-sql-anti-join-null-hazard" type="verify" level="application" title="Anti-Join NULL Semantics: NOT EXISTS vs. NOT IN">

Suppose an `Allocation` table contains a single row with `client_id = NULL`. Verify why `WHERE c.client_id NOT IN (SELECT client_id FROM Allocation)` returns zero clients, while a correlated `NOT EXISTS` query correctly identifies clients without allocations.

<ExerciseSolution hint="Evaluate the logical expansion of NOT IN with a NULL in the candidate set.">

`c.client_id NOT IN (a1, a2, ..., NULL)` expands to `(c.id <> a1) AND (c.id <> a2) AND ... AND (c.id <> NULL)`. In SQL, `c.id <> NULL` yields `UNKNOWN`. Because `TRUE AND UNKNOWN` is `UNKNOWN`, the entire predicate evaluates to `UNKNOWN` for every client, discarding all rows. In contrast, `NOT EXISTS` checks whether the subquery returns any row; a row with `NULL` matching condition `a.client_id = c.client_id` evaluates to `UNKNOWN` and is not returned, leaving `NOT EXISTS` true.

</ExerciseSolution>

</Exercise>

<Exercise id="ex-sql-aggregation-grain" type="construct" level="application" title="Grouped Aggregation with Post-Filter Specification">

Write a PostgreSQL query against `Offering(offering_id, code, region)` and `Allocation(client_id, offering_id, status)` that returns the service code and active allocation count for all us-east-1 offerings having strictly more than 10 active allocations.

<ExerciseSolution hint="Use WHERE to filter offerings by region, ON for allocation status, and HAVING for aggregate thresholds.">

```sql
SELECT o.code,
       COUNT(a.client_id) AS active_count
FROM Offering AS o
JOIN Allocation AS a
  ON a.offering_id = o.offering_id
 AND a.status = 'active'
WHERE o.region = 'us-east-1'
GROUP BY o.offering_id, o.code
HAVING COUNT(a.client_id) > 10
ORDER BY o.code;
```
Because the threshold requires `> 10` allocations, an inner join is sufficient. `GROUP BY` includes `offering_id` to guarantee uniqueness per offering section.

</ExerciseSolution>

</Exercise>

<Exercise id="ex-sql-zero-safe-report-transfer" type="generalise" level="transfer" title="Zero-Safe Offering Report with Computed Boolean Status">

Construct a query returning `(code, active_count, is_full)` for all offerings in region `us-east-1` with `capacity >= 1`. Offerings with zero allocations must appear with count 0 and `is_full = false`. Explain how the grain is preserved.

<ExerciseSolution hint="Preserve unmatched offerings with LEFT JOIN and count non-null client IDs.">

```sql
SELECT o.code,
       COUNT(a.client_id) AS active_count,
       COUNT(a.client_id) >= o.capacity AS is_full
FROM Offering AS o
LEFT JOIN Allocation AS a
  ON a.offering_id = o.offering_id
 AND a.status = 'active'
WHERE o.region = 'us-east-1'
  AND o.capacity >= 1
GROUP BY o.offering_id, o.code, o.capacity
ORDER BY o.code;
```
The grain is one positive-capacity offering in us-east-1. Placing `a.status = 'active'` in `ON` allows offerings without active allocations to survive as null-extended rows, which `COUNT(a.client_id)` aggregates to 0.

</ExerciseSolution>
