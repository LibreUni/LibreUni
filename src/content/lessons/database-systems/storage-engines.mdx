# Storage Engines

An order update changes `paid_at` from `NULL` to a timestamp. The SQL-level fact is tiny; the physical system must find a page, keep it resident while a worker changes it, preserve a stable reference from indexes, and survive a power loss between the write and the acknowledgement. A storage engine is the machinery that makes those obligations compatible.

<details>
  <summary>Readiness refresh: cost tools for page I/O</summary>

  A page I/O is one page read or write; it is the model's unit of work. A scan over $N$ pages is $O(N)$ I/Os. A balanced tree with fan-out $B$ reaches a key in about $O(\log_B N)$ page reads. A hash table is useful for equality lookup under its distribution assumptions, not for ordered range traversal. Treat these as named approximations: each comparison states its page, cache, and workload assumptions.

## Pages preserve location while records move

> **Definition.** A **page** is the unit the engine reads, caches, writes, and recovers. A **record identifier** is usually `(page_id, slot_id)`, not an application key such as an order number.

A slotted page grows its slot directory from one end and tuple payloads from the other. A slot points to a tuple's current offset. Moving a variable-length tuple *within the page* changes the slot, so an index entry that names the slot remains valid. Moving it to another page requires a forwarding record or index maintenance. The distinction explains why a physical identifier is unsuitable as a public business identifier.

The header records structural facts such as free-space boundaries and, in a WAL-based engine, the most recent log sequence number reflected by the page. PostgreSQL's current format is a concrete example: it has a fixed page header, line pointers, free space, items, and special space. Other engines choose different fields; the indirection principle is the transferable idea.

### Prediction — a tuple grows

Page 42 has 40 bytes of free space. Slot 1 points to a 24-byte tuple. Updating the tuple makes it 56 bytes. Which action preserves an index entry `(42, 1)`: overwrite in place, change only the slot, or copy to page 43 without further work?

<ExerciseSolution hint="Ask whether the record identifier names bytes or an indirection entry.">
Overwriting is impossible: the tuple needs 32 more bytes. If another 56-byte region exists within page 42 after compaction, the engine can copy the tuple there and change slot 1's offset; `(42, 1)` still resolves. Copying it to page 43 without a forwarding record or index update leaves the old identifier dangling. The missing idea is stable indirection, not a larger page.
</ExerciseSolution>

## A buffer frame has three different protections

> **Invariant.** A worker may use a page only while its frame is pinned; a frame may be evicted only when its pin count is zero; a dirty update must have a recovery-safe path before the frame is reused.

The buffer pool maps page identifiers to memory frames. Fetching a page pins a frame, possibly waits for I/O, and returns a frame that is initialized. A short latch protects the in-memory page structure while the worker examines or changes slots. A transaction lock or MVCC rule governs which *logical* rows a transaction may observe or modify across statements. These scopes differ deliberately.

| Mechanism | Protects | Typical lifetime | Failure if omitted |
| --- | --- | --- | --- |
| Pin | frame residency | until caller releases the page | eviction turns a live pointer into a stale reference |
| Latch | bytes and metadata in one frame | a short critical section | concurrent slot edits corrupt page structure |
| Transaction lock / version rule | logical row or predicate | until commit, abort, or validation | a correct page can still contain a lost update |

### Worked trace — two fetches and one eviction

1. Worker A fetches page 42; the page table installs frame 3 and A pins it.
2. Worker B asks for page 42 while the read is in flight; B joins that in-flight fetch rather than issuing a second read.
3. A latches frame 3, changes slot 1, marks it dirty, releases the latch, and later unpins it.
4. Eviction may choose frame 3 only after **all** pins are gone. It first satisfies the log condition below, writes the dirty page if necessary, then removes the page-table mapping.

<details>
<summary>Why not hold one global latch during step 2?</summary>
I/O can take orders of magnitude longer than metadata updates. A global latch held during I/O serializes unrelated page lookups. A correct design protects the page table briefly, represents the in-flight state, and lets other fetches wait on that page rather than on the entire pool.
</details>

### Application — scan pollution

A pool holds 100 pages. A hot OLTP working set uses pages 1–80 repeatedly. An analyst sequentially scans 10,000 distinct pages using naive LRU. Predict the result for the next OLTP burst.

<ExerciseSolution hint="A page referenced once by the scan looks recent to LRU.">
The scan continually inserts one-time pages at the most-recent end and eventually evicts much of pages 1–80. The next OLTP burst faults those hot pages again. A scan-resistant policy can give sequential pages low retention priority or use a separate ring, but it cannot ignore the need to pin pages while a scan consumes them.
</ExerciseSolution>

## Layout is a workload hypothesis

> **Example.** A fraud screen fetches one order and its 25 attributes; a finance report sums two numeric columns over 200 million orders. The first benefits from row locality; the second from reading and compressing only the needed columns.

| Layout | Favors | Pays for | Boundary case |
| --- | --- | --- | --- |
| Row store | point reads, full-row writes, transactional updates | unnecessary bytes during narrow analytics | wide rows can waste cache and I/O |
| Column store | scans of few attributes, aggregation, compression | rewriting or locating one full mutable row | late materialization must still reconstruct rows when needed |
| Log-structured / LSM | sustained append-heavy writes and immutable segments | compaction, read amplification, tombstone retention | a point read needs an index/filter across levels |

Compression changes the I/O/CPU balance. Dictionary, run-length, delta, and bit-packed encodings exploit repeated or ordered values; they are not free. A column segment that compresses well may be expensive to update one row at a time. An LSM engine writes new versions sequentially, then compacts segments; it must retain a delete tombstone until every relevant snapshot and replica can no longer interpret an older value.

### Transfer — a changed workload

An event table receives 50,000 inserts/s, later serves a 90-day aggregate, and also supports one support-agent lookup by event ID. Choose a primary layout and name the auxiliary structure that prevents the lookup from becoming a full scan.

<ExerciseSolution hint="Separate the write path, analytical path, and point-lookup path instead of seeking one universally best layout.">
An append-friendly log/LSM or time-partitioned row store fits the ingest path; columnar segments or a columnar replica can serve the aggregate after data becomes stable. A B-tree or hash-like key directory on `event_id` supplies the support lookup. The decision is conditional: if support lookups become dominant and updates are frequent, a row-oriented primary store may become the simpler choice.
</ExerciseSolution>

## A log makes a dirty page recoverable

> **Theorem.** Under write-ahead logging, the log record describing a page change must be durable before the changed data page can be written to durable storage. A commit acknowledgement requires the commit record's durability under the stated failure model.

For the `paid_at` update, write a log record with LSN 911, change the in-memory page, mark its page LSN 911, then flush the log through 911 before flushing page 42. After a crash, recovery compares the durable log with page LSNs: a page missing a logged update can be redone; an uncommitted update can be undone or made invisible according to the system's recovery design. Writing the page first risks a durable change with no durable explanation.

> **Warning.** A checksum detects accidental corruption probabilistically; it does not authenticate a page against a malicious writer. Backups and replicas help only when their integrity is independently verified.

### Prediction — crash boundary

The log is durable through LSN 910. Page 42 has been changed in memory to page LSN 911, but neither the log record 911 nor the page is flushed. The machine loses power. What may recovery expose?

<ExerciseSolution>
Nothing from LSN 911 may be exposed, because neither its log record nor its page image was durable. If the page had reached storage before the log record, recovery could find an unexplained update and could not rely on WAL redo/undo reasoning. The safe result follows from the ordering condition, not from hoping the device flushes in a convenient order.
</ExerciseSolution>
