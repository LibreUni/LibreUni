# Transaction Trace Lab

A trace is a proof artifact. A final table can look plausible after a lost update, a write skew, a deadlock victim, or a crash replay; the trace retains the operations, visibility rules, and failure boundary that distinguish them. Use the notation below before proposing a lock level or an ORM setting.

{/* Source tracking: Schedule notation, serializability, strict locking, WAL commit boundaries, and retry reasoning are synthesized from CMU 15-445/645 materials and PostgreSQL transaction/recovery documentation. The lab traces and prompts are original. */}

## Record enough state to replay the decision

> **Definition.** A useful transaction trace records each transaction's ordered reads and writes, lock/version state, commit or abort outcome, durable-log boundary, and any effect sent outside the database.

| Notation | Meaning | Question it answers |
| --- | --- | --- |
| **r1(x=20)** | T1 read 20 from x | which version did T1 base its decision on? |
| **w2(x=13)** | T2 wrote 13 | which operations conflict? |
| **X1(x)** | T1 holds an exclusive lock on x | why is T2 waiting or allowed through? |
| **C1** / **A1** | T1 commits / aborts | may its writes become visible? |
| **L=911 durable** | log through LSN 911 is stable | what can recovery rely on after a crash? |

<PlantUML code={`@startuml
participant "buyer request" as B
participant "T1" as T1
database "inventory" as I
participant "outbox worker" as W
participant "payment provider" as P
B -> T1 : reserve 7 units
T1 -> I : conditional update; insert outbox
T1 -> I : COMMIT
W -> I : claim committed outbox event
W -> P : charge with idempotency key
note right of P
The external call follows a
known commit, but may be retried.
end note
@enduml`} />

The first question is always semantic: what must remain true? The second is operational: at what read, write, commit, or recovery point is that truth enforced? A trace missing either cannot diagnose the system.

### Prediction — insufficient evidence

A support log says “stock became 13 after two requests for 7.” It contains only final row values. Name two distinct explanations that remain possible.

<ExerciseSolution hint="Final values discard order and visibility.">
A lost update can produce 13 from initial stock 20 when both transactions read 20 and overwrite each other. A correctly serialized system could also produce 13 after one request succeeds and a compensating restock changes the value. The missing data are the read versions, statement outcomes, commit order, and any intervening events; final state alone is not a concurrency proof.
</ExerciseSolution>

## Trace a lost update without smuggling in oversell

> **Example.** Start with **stock = 20**. Two buyers each request 7. The intended serial outcome after two accepted requests is 6; using 20 keeps lost update distinct from a separate insufficient-stock rule.

| Step | T1 | T2 | Stored stock | Consequence |
| --- | --- | --- | ---: | --- |
| 1 | read 20 |  | 20 | T1 plans 13 |
| 2 |  | read 20 | 20 | T2 also plans 13 |
| 3 | write 13; commit |  | 13 | one decrement recorded |
| 4 |  | write 13; commit | 13 | second decrement lost |

A weak implementation reads stock in the application and executes an unconditional write. A row-local repair puts the condition and decrement in one SQL statement: **update stock only when stock is at least the requested amount**. The affected-row count distinguishes reservation from rejection. A lock or serializable protocol can also serialize the read-modify-write, but the conditional statement expresses the invariant directly.

### Application — complete the repair trace

Assume T1 performs the conditional decrement first and commits. T2 performs the same conditional decrement after T1. Fill in T2's affected-row outcome and final stock.

<ExerciseSolution>
T1 changes 20 to 13. T2 sees 13, and its condition **stock >= 7** remains true, so it changes 13 to 6 and affects one row. If the initial stock were 10, T1 would leave 3 and T2 would affect zero rows. Conflating the 10-unit case with a lost update hides whether the design lost a write or correctly rejected an oversell.
</ExerciseSolution>

## Trace write skew as a predicate failure

> **Counterexample.** The invariant “at least one doctor remains on call” spans a set of rows. T1 changes doctor A; T2 changes doctor B. No row is written twice, yet both can jointly violate the predicate.

<PlantUML code={`@startuml
participant "T1" as T1
participant "T2" as T2
database "on_call(A,B)" as D
T1 -> D : read A=true, B=true
T2 -> D : read A=true, B=true
T1 -> D : set A=false; COMMIT
T2 -> D : set B=false; COMMIT
note right of D
Final predicate:
exists on_call = false
end note
@enduml`} />

A row-level optimistic version check can accept both writes because their write sets are disjoint. Repairs include serializable validation, predicate/range protection, or a single summary row updated as part of the rule. The trade-off is expected aborts or contention at the shared boundary.

### Prediction — identify the false repair

Which repair is insufficient by itself: lock A only, lock both currently on-call rows, serializable transaction, or update a protected on-call-count row?

<ExerciseSolution>
Locking A only is insufficient because T2 changes B. Locking both rows can work only if every transaction that could change membership follows the same discipline and range changes are also controlled; it is brittle. Serializable validation or a protected count/summary row gives a shared conflict boundary. The key gap is the predicate, not the absence of a row lock.
</ExerciseSolution>

## Trace waiting, deadlock, and a chosen abort

> **Definition.** A waits-for edge T1 → T2 means T1 waits for a lock held by T2. A cycle is a deadlock; deadlock detection breaks it by aborting at least one transaction.

| Step | T1 | T2 | Waits-for graph |
| --- | --- | --- | --- |
| 1 | holds X(order 7) |  | none |
| 2 |  | holds X(stock 9) | none |
| 3 | waits for X(stock 9) |  | T1 → T2 |
| 4 |  | waits for X(order 7) | T1 ↔ T2 |

<details>
<summary>Victim selection is not a correctness proof.</summary>
Aborting T2 releases stock 9 and lets T1 proceed, but the policy should consider rollback work and age. More importantly, the aborted transaction may need a retry protocol that avoids repeating a notification or payment that already escaped the database boundary.
</details>

### Transfer — order, crash, and webhook retry

Design the event order for: reserve stock, write an order, charge a provider, and send a confirmation. A crash can happen after any step; the provider can send the same webhook twice and out of order.

<ExerciseSolution hint="Make the database state transition and the retry key durable before depending on external delivery.">
In one transaction, insert the order in a pending state, reserve stock conditionally, store a unique provider-event/idempotency key, and insert an outbox record; then commit. A worker invokes the provider with that key and records only legal monotonic payment transitions in later transactions. Deduplicate webhook IDs with a unique constraint, and send confirmation from a committed outbox. Recovery can replay unclaimed outbox records; it must not infer a payment from a network timeout.
</ExerciseSolution>
