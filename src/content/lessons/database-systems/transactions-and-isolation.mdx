# Transactions and Isolation

Two buyers press “reserve” for the last seat. The application cannot treat two individually successful reads as proof that both reservations fit. It needs one unit of work whose committed outcome preserves `available_seats >= 0`, and it must say what a crash, competing transaction, or retry may observe.

{/* Source tracking: Isolation-level caveats, snapshot behavior, and serialization failures are synthesized from PostgreSQL's transaction-isolation documentation. Conflict serializability and schedule analysis are synthesized from CMU 15-445/645 materials. Examples and phrasing are original. */}

## ACID separates obligations that are often conflated

> **Definition.** A transaction is a unit with an all-or-nothing commit outcome. **Isolation** constrains concurrent observations; it does not infer every business rule from a schema.

| Claim | Concrete question | What it does not promise |
| --- | --- | --- |
| Atomicity | Can a crash expose only the debit, not the credit? | that the completed transfer was authorized |
| Consistency | Do commits preserve declared and encoded business invariants? | that an unexpressed rule is magically checked |
| Isolation | Which concurrent writes/read effects can this transaction see? | an absence of aborts or retries |
| Durability | After acknowledgement, which failures retain the commit? | survival of every regional or adversarial event |

For a reservation, a row-local invariant can often be enforced by one conditional statement:

```sql
UPDATE seat_inventory
SET available = available - :requested
WHERE event_id = :event_id
  AND available >= :requested;
```

An affected-row count of zero means the predicate was false *at the protected update boundary*; it is not a successful reservation. This is stronger than `SELECT available`, computing in the application, then issuing an unconditional update.

### Prediction — retry scope

A transaction inserts an order, reserves inventory, commits, then calls a payment provider. The network times out after the call. Should the client blindly repeat the whole sequence?

<ExerciseSolution hint="Separate a database rollback-safe action from an externally visible action that may already have occurred.">
No. Retrying the database transaction before knowing the previous commit can duplicate inventory or orders; retrying the provider call can double-charge. Commit an outbox or an idempotency key with the database work, then make the provider operation retryable against that stable key. Isolation protects database histories; it does not make an external API atomic with them.
</ExerciseSolution>

## Histories can be tested with a precedence graph

<MathStatement id="conflict-serializable" kind="theorem" title="Conflict-serializability test">
Build a graph with one node per transaction. Add $T_i \rightarrow T_j$ when an operation of $T_i$ precedes and conflicts with an operation of $T_j$ on the same item; a conflict has the same item and at least one write. The history is conflict-serializable exactly when this graph is acyclic.
</MathStatement>

<PlantUML code={`@startuml
rectangle "T1\nread A\nwrite A" as T1
rectangle "T2\nread A\nwrite B" as T2
rectangle "T3\nread B" as T3
T1 --> T2 : A write → read
T2 --> T3 : B write → read
note right of T3
No edge returns to T1,
so T1, T2, T3 is
one serial order.
end note
@enduml`} />

Reads of the same item do not conflict. A write followed by a read, a read followed by a write, or two ordered writes does. An acyclic graph yields a topological order that preserves every conflict order. A cycle is stronger evidence than a suspicious final balance: it proves no serial ordering can retain all observed conflicts.

### Worked trace — a lost update

Start with `available = 20`. T1 reads 20 and plans to subtract 7. T2 reads 20 and plans to subtract 7. T1 writes 13; T2 then writes 13. The intended serial result is 6, but the final result is 13: one subtraction disappeared. The writes create a cycle when each transaction's read/write dependencies are represented, so a serializable protocol must block, abort, or otherwise reject one path.

## Snapshot visibility has a known boundary

> **Counterexample.** “At least one doctor remains on call” can fail even when each transaction reads a consistent snapshot. T1 reads doctors A and B and turns A off; T2 reads the same snapshot and turns B off. The writes are disjoint, both commit, and no doctor remains.

<PlantUML code={`@startuml
participant "T1" as T1
participant "T2" as T2
database "on_call" as D
T1 -> D : read A=true, B=true
T2 -> D : read A=true, B=true
T1 -> D : write A=false
T2 -> D : write B=false
note right of D
Each row update succeeds;
the predicate invariant fails.
end note
@enduml`} />

Snapshot isolation often prevents dirty reads and many read anomalies while allowing readers and writers to proceed concurrently. It does **not** automatically serialize predicates over several rows. A serializable level may detect a dangerous dependency and abort one transaction; another repair is to lock/update a summary row that represents the invariant, or to encode a viable declarative constraint where possible.

| Requirement | Reliable repair shape | Why a weaker shortcut fails |
| --- | --- | --- |
| no duplicate email | unique constraint | `SELECT` then `INSERT` races |
| nonnegative stock in one row | conditional `UPDATE ... WHERE stock >= n` | a prior read becomes stale |
| at least one on-call doctor | serializable validation or protected summary/predicate | row-local updates are disjoint |
| price + order snapshot agree | same transaction and foreign-key/version rules | application-side sequencing can expose a prefix |

### Application — pick the conflict boundary

A tenant has a monthly credit limit across many invoices. Two requests each read remaining credit and add a different invoice. Name a repair and state the price it pays.

<ExerciseSolution>
Maintain a tenant-month summary row and update it conditionally in the same transaction, or use serializable isolation with a retry on serialization failure. The summary row makes the aggregate invariant a shared write boundary but can become hot; serializable validation preserves flexibility but can abort more often under contention. A normal row lock on each new invoice does not protect the aggregate predicate.
</ExerciseSolution>

## Isolation labels require an implementation contract

> **Warning.** “Read committed,” “repeatable read,” and “serializable” are names, not a portable proof. Check the target DBMS's documented semantics, error behavior, and replica/DDL caveats.

PostgreSQL, for example, documents Read Committed, Repeatable Read, and Serializable behavior, treats Read Uncommitted as Read Committed, and may report a serialization failure that the application must retry. That is an implementation example, not a license to generalize its exact snapshot boundary to another engine.

### Transfer — design a test rather than trust the label

You are told a service uses “repeatable read.” Give the smallest experiment that reveals whether it protects the on-call invariant.

<ExerciseSolution hint="Run the two disjoint writes concurrently and retain outcome evidence, not just the final rows.">
Create two on-call rows, begin two transactions at the claimed level, have both read the predicate, have each disable a different doctor, then commit. Record blocking, errors, commits, and the final predicate. If both commit with no doctor on call, the level does not protect this invariant; add a serializable/summary/predicate-based repair and rerun the same schedule.
</ExerciseSolution>
