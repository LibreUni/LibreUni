# Filesystem Lab: Recoverable Rename

The naive implementation is four lines: locate `old`, add `new`, remove `old`, return success. It loses data when target insertion runs out of space, leaks the replaced inode when its link count is not decremented, deadlocks when opposite cross-directory renames acquire parents in argument order, and exposes a mixed namespace after a crash when either directory write bypasses the log.

The project is complete only when tests distinguish those implementations from a correct one. A successful happy-path shell transcript is not evidence for atomicity or recovery.

This brief is original to LibreUni. It uses official xv6 RISC-V tag `xv6-riscv-rev5`, commit `7d7adbb1b0acbd67c9766a20d0f9900fef2789fa`, as the licensed course root and does not reproduce another institution's lab text or private solution.

### Rev5 compatibility audit

The tag was chosen because the filesystem constants and paths used by the course are concrete: `BSIZE=1024`, `NDIRECT=12`, `DIRSIZ=14`, `MAXOPBLOCKS=10`, and `LOGBLOCKS=30`; `begin_op`, `end_op`, `log_write`, `dirlookup`, `dirlink`, `writei`, and recovery are present. Four integration deltas must remain visible:

| rev5 boundary | consequence for the lab |
| --- | --- |
| no `rename` syscall or user ABI exists | adding the bounded syscall path is required work, not a missing setup patch |
| `skipelem` accepts at least 14 bytes by retaining only `DIRSIZ` bytes | the lab's overlength-final-component rejection requires validation from the untruncated path, before aliasing can occur |
| the filesystem has no general transaction abort; `bmap`/`writei` can allocate before a later ENOSPC result | all expected failures must precede publication, or a proved rollback/reservation mechanism must restore allocation and metadata exactly |

## Required interface and bounded semantics

Add a user-visible call with this contract:

```c
int rename(const char *old_path, const char *new_path);
```

It returns `0` on success and `-1` on failure. The required domain is narrower than POSIX and must be documented as such:

- `old_path` resolves to an existing regular file;
- `new_path` has an existing directory parent on the same xv6 filesystem;
- source and target parents may differ;
- the target may be absent or may name a regular file;
- replacing an existing target removes one link from the displaced target;
- if both names already identify the same inode, the operation succeeds without changing either link count;
- final components `.` and `..`, directory sources, directory targets, overlength final components, and invalid paths fail without namespace change; and
- no symbolic-link behavior is required because the pinned teaching baseline has no required symbolic-link interface for this project.

The success-state namespace is:

```text
before: old -> S, new -> D or absent
after:  old absent, new -> S
```

If `D` existed and differed from `S`, its link count decreases by one. `S` keeps the same link count: one directory edge is moved, not created or destroyed. Open descriptors for `S` and `D` retain their inode references.

> **No-change-on-error contract.** Every expected validation or capacity failure must leave the visible namespace and persistent link counts at their pre-call values. Kernel panic is not an accepted error path.

### Worked trace: replacement with open descriptors

Initial state:

```text
/a/old -> inode 20, nlink(20)=1, process P has fd 3 open on inode 20
/b/new -> inode 44, nlink(44)=1, process Q has fd 5 open on inode 44
```

After successful `rename("/a/old", "/b/new")`:

```text
/a/old absent
/b/new -> inode 20, nlink(20)=1
inode 44 has nlink=0 but remains live while Q holds fd 5
P's fd 3 and a fresh open of /b/new both reach inode 20
Q's fd 5 still reaches inode 44
```

Closing Q's descriptor permits inode 44 reclamation. Redirecting Q's open descriptor to inode 20 would violate open-file identity; leaving `nlink(44)=1` would leak persistent ownership.

### Contract checkpoint: two names, one inode

`/a/old` and `/b/new` are hard links to inode 20, whose link count is 2. What must rename do?

<details>
<summary>Reveal the boundary result</summary>

The operation succeeds as a no-op under the stated contract. Both names remain and `nlink(20)` remains 2. Treating `new` as a displaced different object and decrementing its link count corrupts the relationship between on-disk link count and directory references. This case must be detected by `(dev, inum)` identity, not pathname-string equality.

</details>

## Invariants to write before code

Your design memo must state and use these invariants:

**N1 — Directory validity.** Every nonzero directory entry names an allocated inode of the same filesystem.

**N2 — Regular-file link accounting.** After recovery with no live process state, each regular inode's `nlink` equals the number of directory entries that name it.

**N3 — Move conservation.** Renaming `S` from one name to another does not change `nlink(S)`.

**N4 — Replacement accounting.** Replacing distinct `D` removes exactly one namespace edge to `D`; reclamation waits for both zero links and zero in-memory references.

**N5 — Runtime namespace atomicity.** A lookup beginning after the operation's linearization point observes `new -> S` and no `old`; a lookup completed before that point may observe the pre-state. The implementation does not release a modified parent lock while the other parent still exposes an intermediate state.

**N6 — Crash state set.** After log recovery, the pair of names and link counts is exactly the pre-state or exactly the post-state—not a mixture.

**N7 — Lock-order acyclicity.** Every operation that simultaneously locks two parent inodes acquires distinct parents by ascending `(dev, inum)` order and releases them in reverse order.

**N8 — Log boundedness.** One rename never dirties more unique blocks than the transaction reservation permits; repeated updates to one block count once.

## Design the mutation in three phases

Do not use the following as copyable implementation code; it is a review decomposition.

### Resolve and retain identities

Within one filesystem transaction:

1. copy both user path strings into bounded kernel buffers;
2. resolve and retain references to both parent inodes and final components;
3. reject unrepresentable final names, `.` and `..`;
4. acquire one or two parent inode locks in canonical `(dev, inum)` order; and
5. re-run source and destination entry lookup while those locks are held.

The second lookup is not redundant. Path traversal produced references before both parent locks were acquired; another namespace operation may have changed an entry. All decisions used for mutation must be based on state protected by the locks held during mutation.

### Validate and reserve before publication

While parent locks exclude entry changes:

- obtain referenced source and optional destination inodes;
- reject non-regular types;
- detect same-inode no-op;
- verify link counts are positive and within representable range; and
- determine a writable destination entry slot.

If inserting `new` requires extending the destination directory, perform every allocation that can fail before clearing `old`. Account for the destination directory data block, its bitmap block, its inode block, source directory block, optional displaced-inode block, and any overlaps. A harmless reserved empty slot is not permission to exceed log capacity; report its treatment explicitly.

Compact xv6 does not offer general transaction abort. Once the first visible edge is changed, the remaining path should contain no expected recoverable failure. An implementation that calls an allocation routine after clearing `old` has already violated the no-change-on-error contract.

### Publish under locks and log coverage

With capacity secured and identities revalidated:

1. install or replace the destination entry with source inode number;
2. clear the source entry when it is a distinct slot;
3. decrement and persist the displaced inode's link count when destination identity differs;
4. keep source link count unchanged;
5. keep both parent locks until all namespace mutations are complete; and
6. route every modified buffer through the existing log rather than writing a home block directly.

The order of steps 1 and 2 is not the crash protocol—the log supplies crash atomicity—but destination-first avoids losing the only name if an internal assertion reveals an unexpected failure. Runtime readers cannot observe the temporary duplicate because the relevant parent locks remain held.

### Lock-order checkpoint

Thread A renames `/x/a` to `/y/a`; thread B simultaneously renames `/y/b` to `/x/b`. Both acquire the source parent first. Construct the wait-for cycle, then remove it using canonical order.

<details>
<summary>Reveal the deadlock trace</summary>

Argument-order acquisition permits:

```text
A holds inode(x), waits for inode(y)
B holds inode(y), waits for inode(x)
```

The wait-for graph has a cycle. If both compare `(dev, inum)` and lock the lower identity first, they request the same first lock; one waits before holding the second resource, so the two-node cycle cannot form. The same-parent case locks once. A timeout only detects the bug; it does not establish acyclic acquisition.

</details>

## Crash matrix, not random hope

Add deterministic failpoints around the existing log protocol. A test-only failpoint may halt QEMU or force reboot after a named event. It must be disabled in the submitted normal build and documented so it cannot trigger accidentally.

At minimum, inject after:

| cut | durable event | expected recovered state |
| --- | --- | --- |
| C0 | transaction admitted, no log record stable | pre-state |
| C1 | some rename block images stable, no valid commit | pre-state |
| C2 | all block images stable, no valid commit | pre-state |
| C3 | commit record stable, no home block installed | post-state |
| C4-k | commit stable, exactly `k` home blocks installed | post-state for every `k` |
| C5 | all home blocks installed, log not released | post-state |
| C6 | log released/checkpoint complete | post-state |

Rebuild or restore an identical filesystem image before each cut, and make rename the only outstanding filesystem operation so rev5's group commit cannot fold unrelated mutations into the crash oracle. After boot, run both behavioral checks and an offline or boot-time invariant checker. A workload that keeps running after a failpoint is not testing power-loss semantics.

### Crash-oracle checkpoint

Why is checking only whether `/b/new` exists insufficient after C4-k?

<details>
<summary>Reveal the hidden states</summary>

The name can exist while its inode is unallocated, its source name also remains, the displaced target's link count is wrong, or bitmap ownership is inconsistent. The oracle must inspect the complete pre/post tuple and global invariants: directory entries, inode types and link counts, block references, and bitmap ownership. Namespace appearance alone cannot detect a leaked or multiply owned object.

</details>

## Required invariant checker

Write a separate checker or a bounded kernel diagnostic that operates on a quiescent image. It must report evidence rather than repair silently.

Required checks:

1. every nonzero directory entry has an in-range inode number whose on-disk type is allocated;
2. counted regular-file directory references equal on-disk `nlink`;
3. every direct and indirect data-block reference is in range and marked allocated;
4. no data or indirect block has two owners in this no-sharing format;
5. every allocated non-reserved block is reachable from exactly one inode metadata path;
6. `old`/`new` states match exactly one row of the operation's pre/post oracle; and
7. the log header is structurally valid under the pinned baseline's format.

The checker must distinguish reserved filesystem blocks from leaked data blocks. It must not count `.` as a regular-file hard link or apply regular-file link rules blindly to directory parent links.

## Public behavior matrix

Implement deterministic tests for all rows. Each test starts from a fresh image or creates and removes its own fixtures without depending on test order.

| ID | setup | required result |
| --- | --- | --- |
| P1 | same directory, target absent | old absent; new has source bytes and inode identity |
| P2 | different directories, target absent | same post-state across parent boundary |
| P3 | target is distinct regular file and remains open | new reaches source; old target descriptor still reads displaced bytes |
| P4 | old and new are hard links to one inode | success no-op; both names and link count unchanged |
| P5 | old missing | `-1`; target and all counts unchanged |
| P6 | source or target is a directory | `-1`; entire tree unchanged |
| P7 | final name is `.` or `..`, empty, or overlength | `-1`; no truncated alias created |
| P8 | destination directory requires a new data block | success within measured log bound |
| P9 | no free block for required directory growth | `-1`; old name preserved and no leak |
| P10 | two opposite cross-directory renames repeated under watchdog | completion without deadlock; invariant checker clean |
| P11 | concurrent lookup loops around successful rename | each lookup result belongs to allowed pre/post observation set |
| P12 | every crash cut C0–C6 for absent and replacing targets | exact pre- or post-state; checker clean after recovery |

Tests may expose inode numbers through a test-only `stat` field or checker; do not infer identity only from equal bytes.

## Mutation tests against named wrong implementations

Create temporary faulty branches or patch toggles. The correct test suite must kill each mutant for the stated reason:

| mutant | defect | test that must fail |
| --- | --- | --- |
| M1 `clear-old-first` | removes source before target capacity is known | P9 observes lost source after ENOSPC |
| M2 `home-write-directory` | bypasses `log_write` for one directory block | C1/C2 or C4-k produces mixed pre/post namespace |
| M3 `keep-displaced-link` | never decrements replaced target | P3 checker reports link-count mismatch/leak |
| M4 `source-parent-first` | locks parents in argument order | P10 watchdog captures ABBA wait-for cycle |
| M5 `same-inode-is-replacement` | decrements link count when identities match | P4 reports two names but link count one |
| M6 `trust-first-lookup` | does not revalidate under parent locks | targeted concurrent unlink/link schedule changes wrong entry |
| M7 `allocate-after-clear` | destination growth can fail after publication begins | P9 leaves neither exact pre-state nor post-state |
| M8 `count-log-calls` | confuses helper calls with unique dirty blocks | P8 either rejects a fitting transaction or overruns reservation under boundary layout |

Do not keep faulty code in the final normal path. Preserve the mutation procedure and failing output as test evidence.

### Worked test design: kill M6 deterministically

A probabilistic loop may run thousands of times without hitting the race. Introduce a test-only barrier after the first source lookup but before acquiring/revalidating both parents. The test thread pauses there; a second thread replaces the source directory entry with a hard link to a different inode; the first resumes. A correct implementation either observes the changed identity during locked revalidation and applies the defined policy or fails without changing the wrong object. M6 mutates using stale identity and the checker exposes the mismatch.

The barrier belongs at a named state transition and is compiled out of release code. A sleep delay is not a deterministic schedule.

## Defense prompts and diagnostic outcomes

An evaluator selects two without advance disclosure:

- Change destination from absent to a second hard link of the source. Predict every count before running code.
- Move one `log_write` to a direct home write. Select the first crash cut that can expose it.
- Reverse two parent inode numbers while preserving pathname order. Show that acquisition order remains unchanged.
- Force destination directory growth from direct block 11 to indirect entry 0. Recompute the unique dirty set and its `MAXOPBLOCKS=10` inequality.
- Hold an open descriptor on the displaced target through recovery. Separate on-disk recovery state from lost process state.
- Remove the atomic-sector assumption for the commit header. State the additional mechanism required.

The defense is diagnostic. Failure to explain the submitted lock order or crash oracle triggers focused re-review; the website does not infer mastery from test output.

## Scope boundary and handoff

Directory rename requires cycle prevention, `..` updates, parent link-count changes, ancestor locking, and a stronger namespace model. Cross-filesystem rename requires a copy/delete protocol rather than one atomic local transaction. Symbolic-link policy changes path resolution and attacker control. None is an optional bonus hidden inside this brief; each needs a separately reviewed contract.

Before handoff, restore test hooks to disabled-by-default state, run the clean evaluator path from a new checkout, and have another person follow only `README.md`. Record every deviation. The final report must distinguish tests passed, claims argued from invariants, and claims left unproved.
