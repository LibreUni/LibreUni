# Scheduler Lab: Weighted Virtual Time in xv6

A scheduler can pass `usertests`, print plausible shares, and remain wrong. Placing a child below both its parent's charged debt and the scheduler floor rewards sequential fork/wait chains. Resetting virtual time after sleep lets an interactive task monopolize the CPU after every wakeup. Copying statistics to a bad user pointer while holding `p->lock` can freeze the process table. Selecting a candidate from an unlocked scan can run one process on two harts.

The lab treats a scheduling patch as a concurrent mechanism with evidence, not as a changed `if` statement.

> **Original lab brief.** The task, milestones, interface, workloads, wrong-implementation matrix, and rubric below are original LibreUni material. They were designed against the permissively licensed upstream xv6 source and do not reproduce MIT 6.1810 lab instructions or solutions.

## Deliverable and non-negotiable boundary

Implement a scheduler named **WVT** (weighted virtual time) in a detached checkout of xv6 rev5. Each runnable process has weight $w\in\{1,2,4,8\}$ and virtual runtime $v$. When a process leaves `RUNNING` after consuming measured processor time $\Delta t$,

> **Definition.** WVT orders runnable processes by charged virtual service; weight changes the rate of debt accumulation, not the amount of physical time in a timer interval.

$$
v \leftarrow v + \max\left(1,\left\lfloor\frac{\Delta t}{w}\right\rfloor\right).
$$

On one hart, select a `RUNNABLE` process with minimum $v$; break exact ties by PID. Larger weight accumulates virtual time more slowly and therefore receives a larger long-run share while continuously runnable.

The deliverable contains:

- the patch, based on the exact commit below;
- `schedtests`, a user-space test binary with machine-checkable summaries;
- optional test-only kernel hooks isolated behind `#ifdef SCHED_TEST`;
- raw CSV or TSV measurements and the script/notebook used to summarize them;
- a design memo of at most 2,500 words plus appendices; and
- answers to the defense questions.

No full implementation appears here. Pseudocode exposes proof obligations, not line-by-line placement.

### Trace the unmodified switch

Starting in user process A at a timer interrupt, list each lock/state/context cut until process B reaches user mode. Mark where A's runtime should be charged and where B's dispatch count should increase.

<ExerciseSolution>
A traps to its kernel stack; the timer path eventually calls `yield`. `yield` acquires A's lock and changes A from `RUNNING` to `RUNNABLE`; the transition helper should charge elapsed A runtime here using the dispatch timestamp and old weight. `sched()` switches A's kernel context to the per-CPU scheduler while A's lock participates in the handoff. On return to the scheduler, it clears current-process ownership and releases A's lock. The selector scans and revalidates B under B's lock, changes B `RUNNABLE→RUNNING`, increments B's dispatch count, records dispatch start, installs `c->proc`, and calls `swtch`. B resumes in its kernel continuation, releases its lock according to xv6's protocol, and eventually returns through its trapframe. Charging at timer entry alone misses voluntary block/exit intervals; incrementing dispatch after `swtch` returns charges the wrong time.
</ExerciseSolution>

## Contract: state accounting and user ABI

Use RISC-V's monotonic `time` counter as the lab's raw unit. Do not call the xv6 `ticks` lock while holding `p->lock`; the timer path can hold `tickslock` and wake processes, producing an inverse lock order. Reading `r_time()` avoids that dependency in this platform model.

Add per-process fields equivalent to:

```c
uint64 state_since;   /* raw time at last state-accounted transition */
uint64 run_time;
uint64 ready_time;
uint64 sleep_time;
uint64 dispatches;
uint64 vruntime;
uint64 dispatch_start;
int weight;           /* exactly 1, 2, 4, or 8 */
```

Expose only current-process control and observation:

```c
struct sched_sample {
    int pid;
    int state;
    int weight;
    uint64 sample_time;
    uint64 run_time, ready_time, sleep_time;
    uint64 dispatches, vruntime;
};

int sched_set_weight(int weight);
int sched_get(struct sched_sample *out);
```

`sched_set_weight` rejects all other values and updates elapsed `RUNNING` time under the old weight before changing it. `sched_get` acquires `p->lock` and performs exactly one `now = r_time()` read. Into a local kernel `sched_sample`, it sets `sample_time = now`, copies the stored counters, and adds `now-state_since` to the one counter selected by the current `RUNNING`, `RUNNABLE`, or `SLEEPING` state. It does not mutate the stored counters or `state_since`. It then releases the lock and performs rev5's four-argument `copyout`. The same `now` therefore anchors the reported state, all current-state accrual, and the sample timestamp. An invalid user destination returns `-1` and leaves the kernel usable.

The self-only API avoids inventing a credential model xv6 does not have. Children report samples to parents through ordinary pipes before exit.

{/* Source tracking: `r_time`, timer setup, `p->lock`, syscall dispatch, and four-argument `copyout` are xv6 rev5 mechanisms. The fields and ABI are original LibreUni design. */}

### Accounting invariant at two sample cuts

Let sample 1 and sample 2 come from the same process. If that process exists continuously between the cuts and every instant in the half-open interval belongs to exactly one of `RUNNING`, `RUNNABLE`, or `SLEEPING`, require

$$
\Delta sample\_time = \Delta run\_time + \Delta ready\_time + \Delta sleep\_time.
$$

This is an exact integer partition, not a statistical tolerance: each transition and each snapshot cuts the same raw `time` counter once, and snapshot work after that cut is outside the interval. The claim excludes intervals containing `USED`, `ZOMBIE`, reuse of a PID as a different process, or raw-counter wrap. `sample_time` is the guest RISC-V counter value, not host wall time or xv6 `ticks`. Keep raw integers in test output; decimal conversion can manufacture a residual that the kernel did not produce.

### Milestone A — one transition helper

Create one helper whose precondition is “`p->lock` held.” It reads time once, charges `now-state_since` to the old state, updates virtual runtime when leaving `RUNNING`, records the new state and timestamp, and performs new-state bookkeeping. Replace every relevant raw assignment or justify why construction/reap remains outside it.

Pseudocode obligation:

```text
transition(p, new_state):
    assert p->lock held
    now = time()
    delta = now - p.state_since
    charge delta to p.old_state
    if old_state == RUNNING:
        p.vruntime += weighted(delta, p.weight) with overflow policy
    p.state = new_state
    p.state_since = now
```

Do not paste this pseudocode into C without handling initialization, same-state calls, overflow, exit, and fork creation placement.

## Contract: WVT selection, creation, and wakeup

> **Definition.** The WVT policy includes selection, debt charging, creation placement, wakeup placement, tie behavior, and overflow; omitting any one leaves observable behavior undefined.

### Continuously runnable selection

On `CPUS=1`, choose the minimum `vruntime` among `RUNNABLE` processes, then PID. Revalidate state and ordering assumptions while holding the candidate's lock before changing it to `RUNNING`. Record a dispatch before `swtch`, not after it returns.

On `CPUS>1`, exact global minimum is not required: concurrent selectors observe a moving runnable set. Safety is required. No process may be selected by two harts; no stale candidate may be switched after it ceases to be runnable. Document the lock/revalidation protocol and quantify that fairness results are single-hart only.

### Fork creation placement

A new child inherits the parent's weight. At the creation cut, first materialize the parent's elapsed `RUNNING` charge under the old weight. Then place the child at exactly the greater of that charged parent value and the current scheduler floor:

$$
v_{child}=\max(v_{parent}, floor).
$$

Neither `v_child = 0` nor `v_child = v_parent` without the floor clamp satisfies the contract. The floor term matters when a parent sleeps in `wait` while a sequence of children consumes CPU: the sleeping parent's own debt no longer tracks that descendant work, but the global service frontier advances. Placement at $\max(v_{parent}, floor)$ prevents each new child from re-entering behind that frontier. It still does not provide group fairness when several descendants are runnable at once. State the lock order used to read/update parent debt, read the floor, and initialize the locked child.

### Wakeup placement

Maintain a nondecreasing scheduler floor representing recently selected virtual time. When a process becomes runnable after sleeping, preserve its old $v$ but clamp excessive credit:

$$
v \leftarrow \max(v,\; \max(0, floor-C)),
$$

where $C$ is a documented wakeup-credit bound, initially two baseline timer intervals in virtual-time units. A short sleeper can receive bounded latency credit; a process asleep for minutes cannot return at ancient virtual time and monopolize the CPU. All floor access needs a lock order with no reverse path.

### Overflow

Choose and defend one strategy:

- renormalize all live virtual runtimes by subtracting a common floor before the 64-bit danger region, under a quiescent/single-hart test protocol; or
- use a proven modular comparison and bound that guarantees no pair differs by $2^{63}$ or more.

“It takes a long time” is not an integer-correctness argument. A test-only hook must place values near the boundary without waiting years.

### Milestone C — policy and creation placement

Implement minimum selection, exact tie behavior, weight charging, inherited weight, and child creation at $v_{child}=\max(v_{parent}, floor)$ after charging the parent to the creation cut. Implement floor maintenance and a documented lock order for that cut. Keep a compile-time baseline policy if useful for controlled comparison; do not let two policy implementations silently use different accounting.

### Milestone D — bounded wakeup and overflow

Add wakeup clamping and the test-only overflow path. Record why the chosen $C$ is a policy value, not a theorem. Run all functional tests before collecting performance data.

Every test prints one line beginning `SCHEDTEST name PASS` or `... FAIL` and exits nonzero on failure. Calibrate tolerances for statistical service/latency tests from at least 10 baseline repetitions; do not widen them until a known-bad implementation passes. W6 is not statistical: its in-scope integer residual must be zero.

The weight-share test needs two directions. A hard-coded preference for one PID can accidentally produce a 4:1 ratio once; swapping weights and creation order kills that counterfeit.

### Test oracle details

**Barrier start.** Parent creates report pipes, forks children, then releases both through a start pipe so fork/setup time is outside the measurement. Each child sets its own weight, waits for the token, burns deterministic integer work until a common `uptime` deadline, snapshots itself, and writes the sample.

**Useful-work calibration.** Report both scheduler `run_time` and loop iterations guarded against optimization. A share claim needs agreement between service accounting and useful work; divergence exposes instrumentation or cache/compiler effects.

**Snapshot cut.** `sched_get` must return the one raw `sample_time` used to accrue the current state. For each pair, assert identity continuity and record both sampled states. Apply the exact conservation oracle only when the process remained inside the three live states; do not hide a nonzero residual behind timing tolerance. Invalid-pointer tests are separate because no sample is returned.

**Latency distribution.** The sleeper records elapsed time around each bounded sleep and subtracts the requested sleep interval under the lab clock model. Report median, p95, maximum, and raw samples. A mean alone does not kill one extreme wakeup.

**Safety assertion.** Under `SCHED_TEST`, maintain `on_cpu` under `p->lock`: assert zero before `RUNNABLE→RUNNING`, set to hart ID plus one, clear only when scheduler regains ownership. The assertion is instrumentation, not a substitute for the lock proof.

### Test-design checkpoint

Why does a single 4:1 run-time observation fail to distinguish WVT from a scheduler that gives PID 2 four quanta for every one quantum of any other PID?

<ExerciseSolution>
The observed ratio may be caused by PID bias, not weight. Swap weights between the same processes, reverse creation order, and repeat with a third equal-weight competitor. WVT predicts service follows weight under the controlled window; PID bias follows identity/slot. A discriminating test changes one causal variable while controlling alternatives.
</ExerciseSolution>

## Measurement protocol

Functional correctness precedes claims about fairness or performance.

### Controlled factors

Record commit, host CPU, host load policy, QEMU version, compiler, optimization flags, `CPUS`, timer interval, workload seed, warmup, run duration, and repetitions. Run policy variants in randomized or counterbalanced order. Keep console logging outside measured windows; scheduler tracing can dominate the scheduler.

### Required workloads

1. **Equal CPU:** two and eight continuously runnable weight-1 jobs.
2. **Weighted CPU:** weights 1:2, 1:4, and 1:8; repeat with identity/order swapped.
3. **Interactive:** one CPU hog plus sleepers with two sleep/run duty cycles.
4. **Fork adversary:** persistent job plus a sequential fork/wait chain; compare correct $\max(v_{parent}, floor)$ placement with zero-start and parent-only known-bad variants.
5. **Mixed:** CPU, sleeper, and short-lived process creation together.
6. **SMP safety:** CPUS=3 stress; no exact ratio claim.

### Required metrics

- per-process `sample_time`, run, ready, and sleep time from each coherent cut;
- dispatches and virtual-runtime trajectory sampled at bounded frequency;
- useful-work count;
- response/wakeup median, p95, and maximum;
- service-share error $|observed-target|$ over at least three windows;
- wall completion and context switches per unit of useful work; and
- exact live-state residual $\Delta sample\_time-\Delta run\_time-\Delta ready\_time-\Delta sleep\_time$, retained as a signed integer.

For weights $w_i$, target share is $w_i/\sum_jw_j$ only while the measured set remains continuously runnable. Remove sleeping intervals or model them; otherwise the denominator is false.

### Causal comparison

Compare pinned baseline and WVT using the **same accounting instrumentation**. If WVT improves weighted-share error but increases dispatches or scan cost, report both. If response improves only because the timer interval changed, the scheduler-policy claim is confounded. If useful work falls while run time is unchanged, inspect cache/branch/compiler effects before blaming context switching.

### Milestone F — results and uncertainty

Provide raw observations and a plot/table that retains distributions. For each major result write:

```text
claim → model prediction → measurement → uncertainty → competing explanation → follow-up
```

“WVT is fair” is not a result. “With two continuously runnable processes at weights 1:4, CPUS=1, 12 randomized 200-tick runs produced median high-weight share X with range Y; swapped identity changed it by Z” is auditable.

## Defense questions

1. Why is `dispatches++` immediately after `swtch` returns attributed to the wrong event?
2. A process changes weight from 1 to 8 halfway through a long uninterrupted run. Which weight charges the first half?
3. Why is child `vruntime=parent.vruntime` insufficient when the parent waits for each short-lived child, and what placement closes that reset path?
4. What behavior changes as wakeup credit $C$ moves from 0 to unbounded?
5. Why can exact global minimum be ill-defined for concurrent CPU selectors?
6. Which lock order could deadlock if accounting reads `ticks` while holding `p->lock`?
7. How does W5 exploit timer-only charging, and which measurement exposes it?
8. Why must `sched_get` use one time read under `p->lock`, then copy a local snapshot after releasing the lock?

<details>
<summary>Reveal defense diagnostics</summary>

1. Return occurs when the process later yields back; the dispatch happened before entering it.
2. Charge elapsed time to the change point under weight 1, reset the timestamp, then charge subsequent time under 8.
3. The waiting parent's virtual runtime stops advancing while each child consumes service, so every new child can inherit stale debt. Initialize the child at `max(parent.vruntime, floor)` to keep it at the current service frontier. Multiple simultaneous descendants still create multiple schedulable entities; group scheduling needs a hierarchy.
4. Zero removes latency credit and may penalize sleepers; unbounded lets ancient virtual time dominate after wakeup. A finite $C$ bounds both effects.
5. Runnable state and virtual time change while selectors operate; only a serialized global run queue defines one total decision point. Safety can remain exact with approximate concurrent policy.
6. Timer code can hold `tickslock` then acquire process locks during wakeup; `p->lock→tickslock` creates the reverse cycle.
7. Yield before each timer tick to consume CPU without virtual debt. Compare useful-work and `r_time`-based service against virtual-runtime increments.
8. One time read gives the state and all accrued counters a common linearization cut, making the three-state conservation equation exact. User memory access can fail and may invoke mechanisms forbidden while holding scheduler state; a local kernel copy preserves that cut without extending lock lifetime through `copyout`.
9. A full scan is $O(NPROC)$ per selection. Measure scheduler CPU time or useful throughput as runnable count grows while holding work constant.
10. Swapping weights while holding PID/order fixed fails to swap observed share, or reversing creation changes share more than weight does.

</details>

## Grading contract

> **Warning.** Safety blockers cap the result regardless of throughput because a fast double-running or lock-leaking scheduler is not an acceptable scheduler.

| Dimension | Points | Publication blocker |
| --- | ---: | --- |
| Baseline reproducibility and source map | 8 | wrong/unrecorded commit or broken baseline |
| State/accounting invariants | 16 | bypassed transition, double charge, missing/split-read `sample_time`, or nonzero in-scope residual |
| WVT policy completeness | 18 | child below $\max(v_{parent}, floor)$, no wakeup bound, undefined ties/overflow |
| Locking and SMP safety | 14 | double-running, stale dispatch, or lock-order deadlock |
| ABI and failure behavior | 10 | unchecked pointer, lock-held copyout, partial mutation |
| Test discrimination | 16 | tests do not kill W3/W4/W7/W8, statistical tolerances are post-hoc, or W6 tolerates a nonzero residual |

| Memo and defense | 6 | cannot explain own state/lock protocol |
| **Total** | **100** | |

Passing requires at least 70 overall **and** no publication blocker. Performance cannot compensate for a safety defect. A human reviewer must inspect authorship and defense; the page cannot certify either automatically.

## Handoff checklist

> **Remark.** Every checked item must name retained evidence; an unchecked limitation remains explicit rather than being converted into a claim.

- clean diff based on the pinned hash;
- upstream license retained;
- CPUS=1 and CPUS=3 baseline/regression outputs attached;
- all W1–W9 tests and at least four known-bad demonstrations attached;
- W3 rejects both `v_child=0` and parent-only placement without the floor clamp; creation-cut review confirms $v_{child}=\max(v_{parent}, floor)$;
- every successful sample records the single-read `sample_time`, and all in-scope paired residuals are zero;
- failure-injection matrix completed;
- raw measurements and summarizer reproducible;
- no debug print inside measured windows;
- no `SCHED_TEST` hook in the normal build;
- every new field initialized, inherited/reset, and reaped intentionally;
- memo states what remains unproved.

## Deliberate omissions

WVT is not Linux EEVDF or CFS. It has no eligibility lag, requested latency, hierarchy, CPU affinity, migration cost, load balancing, cgroups, realtime class, deadline admission, priority inheritance, energy model, or security policy. Single-hart weighted-share measurements do not establish multicore fairness. QEMU timing does not predict hardware cache behavior. These omissions are part of the defense: extending the policy without new invariants and tests would lower quality.

> **Remark.** The implementation may be correct inside this contract while remaining unsuitable for production; the memo must preserve that distinction.
